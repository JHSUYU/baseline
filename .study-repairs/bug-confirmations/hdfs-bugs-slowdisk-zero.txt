Case: hdfs-bugs-slowdisk-zero (attachment item 1; bug_study HDFS.txt #15)
Review date: 2026-10-07 UTC
Verdict: REAL SOURCE-LEVEL CORRECTNESS BUG. The observable write failure follows from
         reachable production code when a previously excluded SSD remains in the
         DataNode's exclusion list after the administrator sets the maximum to 0.
         The attachment's particular 10/10 native replay and GraphChecker SAT/CONFIRM
         claims are reported evidence, not independently reverified here because
         their raw test and run artifacts were unavailable in this workspace.

Required states and exact causal path
-------------------------------------
1. The published contract explicitly says that the default value 0 for
   dfs.datanode.max.slowdisks.to.exclude disables exclusion when choosing a
   volume: hadoop-hdfs-project/hadoop-hdfs/src/main/resources/hdfs-default.xml:
   2577-2584; DFSConfigKeys.java:760-763 also sets the default to 0.
2. Disk metrics must be enabled and a nonempty exclusion list must first be
   published while maxSlowDisksToExclude is positive. DataNodeDiskMetrics.java:
   83-87 stores the limit and the list separately; 108-175 runs the periodic
   detector. Lines 150-163 assign slowDisksToExclude only inside
   if (maxSlowDisksToExclude > 0). The existing addSlowDiskForTesting hook at
   263-270 can provide a controlled prior slow-disk sample; the production
   detector can also classify disks through detectAndUpdateDiskOutliers at
   178-205. The hook supplies an input state, not a replacement chooser.
3. An administrator may reconfigure the setting without restarting the DN.
   DataNode.java:362-370 advertises this property as reconfigurable;
   729-734 dispatches it; 955-961 parses the new value and calls
   diskMetrics.setMaxSlowDisksToExclude(0). That setter at
   DataNodeDiskMetrics.java:281-283 changes only the volatile integer. It
   neither clears nor replaces slowDisksToExclude.
4. On subsequent detector iterations with the limit equal to 0,
   DataNodeDiskMetrics.java:151 skips the only assignment to the exclusion
   list. Thus a list published before the transition remains nonempty while
   exclusion is supposedly disabled. If the detector finds no stats at all,
   lines 141-145 continue even earlier; that also cannot clear the list.
   This persistence lasts while the limit remains 0 and the same metrics
   object remains alive. It is not a claim that restart or further
   reconfiguration could never repair the state.
5. For a block targeting SSD, FsVolumeList.java:177-185 first collects volumes
   of the requested storage type, then 105-118 removes every volume whose
   path appears in the stale list and invokes the configured volume chooser.
   With exactly one SSD and that SSD in the list, the filtered list is empty
   despite the physical SSD still being present. The ALL_SSD policy prefers
   StorageType.SSD (BlockStoragePolicySuite.java:72-77); a normal client
   PIPELINE_SETUP_CREATE goes through BlockReceiver.java:218-222 and
   FsDatasetImpl.java:1664-1666 to this chooser.
6. With RoundRobinVolumeChoosingPolicy configured, its chooseVolume guard
   at RoundRobinVolumeChoosingPolicy.java:78-84 throws
   DiskOutOfSpaceException("No more available volumes") for that empty list.
   A client write targeting this DataNode fails despite the advertised
   disable-exclusion value. Other DISK writes can still work because their
   candidate list does not consist solely of the excluded SSD.

Why this is a correctness bug, rather than an intentional failure
---------------------------------------------------------------
The runtime invariant implied by the documented value 0 is that a former
slow-disk designation no longer removes a volume from selection. The setter
updates one part of the state, while the consumer unconditionally uses the
other part; no guard in FsVolumeList checks the limit. The end result is
semantically inconsistent even if the SSD remains genuinely slow. The same
guard is expected when exclusion is enabled and every requested-type volume
is deliberately excluded, but it is unexpected after exclusion is disabled.

Minimal targeted regression expected
------------------------------------
On a MiniDFSCluster with metrics enabled and one SSD: set max=1; establish
that the SSD path is in getSlowDisksToExclude(); invoke the public
DataNode.reconfigureProperty(key, "0"); wait at least two detection periods;
assert max==0, list empty, and a fresh ALL_SSD write succeeds. On inspected
source the list-empty assertion fails, and if that SSD is the sole SSD
candidate the write reaches the empty-volume guard. A proposed fix must
clear or disregard the old list on the transition and synchronize publication
and consumption consistently; simply waiting for another detector iteration
does not repair this state.
