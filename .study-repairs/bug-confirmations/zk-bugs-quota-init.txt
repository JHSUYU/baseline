zk-bugs-quota-init — partial quota initialization makes hard quota unenforceable
Source reviewed: Apache ZooKeeper checkout /users/ZhenyuLi/zookeeper at aafd344eeeb5090e0e24126ea9e28133a77c22b0 (2026-10-07 review).
Conclusion: CONFIRMED source-level correctness bug under an interrupted or ambiguous first create and zookeeper.enforceQuota=true. The exact attached five-node test and GraphChecker raw traces were not available in this workspace, so their stated pass and 10/10 counts are reported evidence, not independently rerun evidence. Novelty relative to all upstream releases/issues is not established by this review.

Contract and state. SetQuotaCommand.createQuota sets a limit for an existing application path. The metadata consists of separate zookeeper_limits and zookeeper_stats znodes under /zookeeper/quota/<path>. A hard count quota should reject a create that takes the subtree over its limit when enforcement is enabled. ZooKeeperServer.java:114,158 defines zookeeper.enforceQuota and shows that enforcement is disabled by default; the hard-limit consequence below specifically assumes it was enabled.

Trigger sequence.
1. The first createQuota call reaches SetQuotaCommand.java:235-244. It commits zookeeper_limits before issuing the separate create for zookeeper_stats. There is no multi-operation atomicity or rollback in this method. An interruption between the two calls, or a lost successful response to the first create, leaves limit present and stats absent.
2. On applying that limit node, DataTree.java:502-519 adds the application path to the quota prefix trie. DataTree.java:1242-1257 and :1280-1290 show that startup rebuilding also refuses to fabricate a missing stats node. The partial state can therefore survive a server restart.
3. The caller retries createQuota with the same input. Because the limit node now exists, SetQuotaCommand.java:253-274 takes the update branch. It calls getData(statPath) at :270 before any write that could repair stats. DataTree.java:711-715 throws NoNodeException for the absent node. Repeating the same call repeats the failure. An external delete/recreate or explicit repair of the metadata is required.
4. With quota enforcement enabled, ZooKeeperServer.java:2171-2189 locates the registered quota prefix for future creates. Its private checkQuota reads the limit but, on a missing stats node, logs and returns at :2233-2240 instead of denying or repairing the write. DataTree.updateQuotaStat at DataTree.java:375-390 also returns when stats is missing. Thus writes beyond a configured hard count or byte limit can commit while the usage remains untracked.

Why the target exception is evidence but not the whole bug. NoNode on the missing stats path is an expected low-level response. The bug is that a public quota operation can leave partial persistent metadata, its own retry cannot complete, and enforcement silently fails open. The relevant invariants are (a) a registered quota has its usage stat, and (b) an enabled hard limit is enforced. The two independent create RPCs and the missing-node early returns violate those invariants under the stated fault.

Attached evidence and limits. The supplied list names QuotaCoordinationRegressionTest.interruptedQuotaInitializationCannotBeRetriedAndDisablesEnforcement on five-node QuorumBase, a GraphChecker SAT/CONFIRM trace for REGION.860d3eb6...#6, and 10/10 native replays. Those source/log artifacts were not present under /users/ZhenyuLi/bug_study or /bigtemp/vnr3ne here. The source path above independently establishes the mechanism, but this review does not independently attest to the reported test counts. The original client failure may be InterruptedException or an ambiguous response; no failure is required in the service after the partial state is created.

Repair direction. Use an atomic multi-operation for limit and stats, or make retry reconcile a missing stats node and rebuild its count/byte values before reporting success. The service-side quota check should not silently accept writes when an enabled hard quota has no stat; it should repair or reject explicitly. A regression test must stop between the two metadata creates, retry the same API call, then verify both quota znodes and rejection of an over-limit child create.
