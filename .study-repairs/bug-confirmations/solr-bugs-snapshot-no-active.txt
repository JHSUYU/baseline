case: solr-bugs-snapshot-no-active
system/version: Solr 8.11.4 local source copy; also checked current upstream checkout 56ec140e363 (2026-09-30)
verdict: Source-confirmed real false-success defect when no replica is ACTIVE for a shard. The attached summary reports a two-node JUnit with actual node stop/restart on upstream 91cbb6a3, but raw test/log unavailable locally.

Relevant source (relative to .study-repairs/unit-test-pivot/source/solr-8.11.4/solr):
  core/src/java/org/apache/solr/cloud/api/collections/CreateSnapshotCmd.java:85-94 -- refuses an existing snapshot name, then writes InProgress metadata.
  core/src/java/org/apache/solr/cloud/api/collections/CreateSnapshotCmd.java:98-124 -- skips every non-ACTIVE replica; only sent core requests enter shardByCoreName.
  core/src/java/org/apache/solr/cloud/api/collections/CreateSnapshotCmd.java:126-182 -- despite comment requiring one successful replica per shard, failure computation only considers requests in shardByCoreName. Empty request/failure sets reach SnapshotStatus.Successful with an empty replicas list.
  core/src/java/org/apache/solr/cloud/api/collections/BackupCmd.java:186-208 -- a named snapshot with no matching live replica cannot be backed up.
  Current upstream CreateSnapshotCmd.java:105-126,130-196 retains the same skip/empty-success path.

Trigger and state transition:
  1. Stop the only node hosting a shard's replica, leaving that replica non-ACTIVE in ClusterState while another node accepts the collection API request.
  2. CREATESNAPSHOT(C,M) creates collection-level InProgress metadata. It skips the unavailable replica and sends no core snapshot RPC for that shard.
  3. Because no RPC was sent, the corresponding shard is absent from shardByCoreName and the failedShards calculation. When all shards are in this condition, both sets are empty and the command records Successful(M, replicas={}). The same omission can affect one unavailable shard in a multi-shard collection.
  4. After node recovery, retrying the same snapshot name hits snapshotExists and fails BAD_REQUEST, despite no core snapshot having been made. The metadata is unusable for the intended backup/restore operation.

Why this is a bug:
  A successful collection snapshot should contain at least one successful core snapshot for each shard. The implementation's own comment states this invariant, yet its failure accounting ignores shards with zero eligible requests. The durable false-success record also blocks a normal retry under the same name. Administrative deletion of the false snapshot followed by recreation can repair it, but retry alone cannot.

Evidence limits:
  Source establishes the false-success path and downstream name collision. The attachment reports TestSnapshotNoActiveReplicaFalseSuccess run2 1/0/0 with real node stop/restart; the test source and raw results were absent. This review does not prove the issue has never been reported or is present in versions beyond the two inspected source snapshots.
