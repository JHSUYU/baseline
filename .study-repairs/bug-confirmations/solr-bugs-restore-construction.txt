Trigger and state transition:
  1. RESTORE a valid backup B to absent target T. The new-collection path creates T, marks its shard CONSTRUCTION, and creates a real first replica/core.
  2. A later shard restore/transfer RPC fails once. The operation returns error before markAllShardsAsActive, leaving T present in ZooKeeper with a CONSTRUCTION shard. This is distinct from the earlier initial-replica failure branch, which explicitly cleans up T.
  3. Retrying identical RESTORE(B,T) sees that T exists and chooses RestoreOnExistingCollection. Shard count matches, transfer succeeds, and the request can report success.
  4. Existing-collection strategy never transitions CONSTRUCTION to ACTIVE. A public add to T has no active hash slice and is rejected BAD_REQUEST on every unchanged retry.

Why this is a bug:
  A failed first attempt leaves internal construction state that changes the control path of the next attempt. The retry reports success after restoring data but omits the activation step required for normal routing. Restoring to a fresh name or manually deleting T avoids the partial state, but normal retry to T is not self-healing. The attachment's fresh-name control is consistent with that diagnosis.

Evidence limits:
  Source confirms the missing transition and guard. The attachment reports TestRestoreRetryLeavesConstructionShard run6 1/0/0; its raw evidence was unavailable. A failure before the first core exists may take the explicit cleanup branch and is not this bug. This review does not establish independent novelty.
