zk-bugs-election-offer — a first leader-election start can leave a live but unowned offer
Source reviewed: Apache ZooKeeper checkout /users/ZhenyuLi/zookeeper at aafd344eeeb5090e0e24126ea9e28133a77c22b0 (2026-10-07 review).
Conclusion: CONFIRMED source-level recipe bug for the stated getChildren/getData race. The attached five-node regression result was unavailable for independent rerun, and the attached GraphChecker entry itself says no native replay was done for this case. This is a recipe-level liveness failure, not a ZooKeeper server getData correctness failure. Novelty across all upstream issues/releases is not established here.

Contract and state. LeaderElectionSupport creates an ephemeral sequential offer for its ZooKeeper session, then scans all offers to decide whether it is ELECTED or READY. Its field leaderOffer holds only one path. A failed initial start should not leave an offer that the recipe no longer tracks as an active contender, because lower-numbered offers make later contenders wait.

Trigger sequence.
1. LeaderElectionSupport.start at zookeeper-recipes/zookeeper-recipes-election/src/main/java/org/apache/zookeeper/recipes/leader/LeaderElectionSupport.java:119-140 calls makeOffer followed by determineElectionStatus in one try block. makeOffer creates n_1 and stores it in leaderOffer at :165-179.
2. determineElectionStatus gets a child-name snapshot at :188-200 and passes it to toLeaderOffers. That method reads each offer's data in a separate ZooKeeper getData call at :300-322. Suppose competing n_0 appears in the snapshot, then its owner normally deletes n_0 before this worker reads it. ZooKeeper correctly returns NoNode. The missing-node guard is DataTree.java:711-715 (the server's FinalRequestProcessor.java:717-723 may also reject the absent node first).
3. start catches the KeeperException and calls becomeFailed at :139 and :270-275. It neither deletes n_1 nor resumes election using a refreshed child list. No predecessor watch has yet been installed, since becomeReady is only reached after toLeaderOffers completes (:227-255). The failed worker still owns n_1 until explicit stop or session expiration.
4. A fresh contender creates a larger sequential offer and, on a normal scan, sees n_1 first. It becomes READY watching n_1, while no participant is ELECTED. A same-worker retry calls makeOffer again, creates n_2, and overwrites leaderOffer with n_2. stop at :147-161 then deletes only the remembered n_2; the old n_1 remains until its ZooKeeper session ends. This is stronger than a mere transient NoNode response.

Why the target exception is evidence but not the whole bug. A getData NoNode after a competing session deletes its znode is correct ZooKeeper behavior. The defect is recipe handling of that ordinary race: it moves to FAILED without revoking or reconciling its own already-created offer. The resulting orphan n_1 can prevent election progress while the owning session remains alive. A deliberate stop before retry can clean up n_1; the failure is not literally permanent, and session expiry also releases it.

Attached evidence and limits. The supplied list reports LeaderOfferReadRaceRegressionTest 1/0/0 on five-node QuorumBase, pausing at the real getData RPC, and GraphChecker SAT/CONFIRM for the second offer read. The test source and logs are absent from the available checkout, and /bigtemp/vnr3ne output is absent. GraphChecker's stated STATE_PAIRING_FLIPPED witness confirms the target NoNode guard if its report is accepted; it does not alone prove the later no-leader outcome. The later outcome follows the recipe source path described above. The available built-in LeaderElectionSupportTest#testNodes3 (test file :80 onward) exercises simultaneous starts but does not force this exact list/read disappearance.

Repair direction. On a NoNode while converting a child snapshot, rescan without creating another own offer, or stop and delete the current offer before publishing FAILED. Track every offer created by this instance until deletion is acknowledged, so a second start cannot hide the first path. A regression test should force n_0 deletion after getChildren, assert n_1 is not left untracked, start an independent contender, and verify an ELECTED state within a bounded time.
