Trigger and state transition:
  1. First ADD through time-routed alias A parses a date-math router.start. The update thread reads aliases snapshot V containing A, calculates fixed start, and schedules an asynchronous write based on V.
  2. Before that write runs, CREATEALIAS(B -> D) commits a later aliases version V+1 containing B. This is a valid independent control-plane operation.
  3. The async task reads current V+1 but its modification function returns V cloned with A's new property. It uses the current version number for setData. If the cached current version is stale, the BadVersion retry refreshes it, but the lambda still returns V's collectionAliases. Eventually the CAS can succeed and overwrite aliases.json without B.
  4. Queries or updates addressed through B fail as an unknown collection/alias while direct requests to D can succeed. Refreshing clients does not restore B because the durable aliases.json itself lost that entry.

Why this is a bug:
  The CAS protects against writing an old version number, but it cannot protect unrelated keys when the modification function builds its payload from a stale full-map snapshot. The correct update should apply A's property change to the function argument a, which contains the latest aliases mapping. The current code violates that contract and silently deletes a concurrently created alias.

Evidence limits:
  Source proves the lost-update interleaving. The attachment reports TestTimeRoutedAliasStartOverwritesConcurrentAlias run1 1/0/0 using a timing hook only after snapshot capture; that test and raw output are not present locally. This review does not prove global novelty, and ordinary runs without the described interleaving may never hit the bug.
