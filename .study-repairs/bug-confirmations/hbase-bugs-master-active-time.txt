ID: hbase-bugs-master-active-time (attachment #11; HBase.txt #14)
Review date: 2026-10-07
Verdict: PROVISIONAL candidate with a source-supported conditional liveness
          mechanism in HBase 2.6.6 and the inspected 4.0.0-alpha-1-SNAPSHOT
          checkout. Keep the attachment's "provisional new candidate, not counted"
          classification: its claimed MiniCluster pass and >170 retries are not
          independently verified here because the bug_study test source and raw
          log were unavailable. This is not counted as a confirmed new bug.

System and trigger
------------------
An active master M0 initiates OpenRegionProcedure P with active time T0. Before
the RegionServer reports OPENED, M0 loses leadership. A backup master M1 becomes
active so quickly, and its host clock is sufficiently behind M0's, that its
new active time T1 is less than T0. This is possible with a few seconds of
host skew; the default RS/master skew check tolerates up to 30,000 ms. The
trigger is the ordering T1 < T0, not a 5-second value specifically.

Code path and state
-------------------
* HMaster.finishActiveMasterInitialization assigns masterActiveTime from
  EnvironmentEdgeManager.currentTime(), a wall clock rather than a monotonically
  increasing leadership epoch. In the HBase 2.6.6 checkout this is HMaster.java:949;
  in the inspected 4.0.0-alpha-1-SNAPSHOT checkout it is HMaster.java:986.
* OpenRegionProcedure.newRemoteOperation includes the current Master's active
  time in RegionOpenOperation. The RegionServer carries that immutable value
  into AssignRegionHandler and PostOpenDeployContext. See the 4.0 checkout:
  OpenRegionProcedure.java:60-63, RSRpcServices.java:3942-3970,
  AssignRegionHandler.java:63-75,139-154. The 2.6.6 code has the same path.
* After HRegion.openHRegion succeeds, AssignRegionHandler invokes
  postOpenDeployTasks BEFORE rs.addRegion and finishRegionProcedure. See
  2.6.6 AssignRegionHandler.java:151-166 (4.0 checkout: 150-165).
  HRegionServer.postOpenDeployTasks sends the OPENED report with the saved T0;
  see 2.6.6 HRegionServer.java:2623-2654.
* MasterRpcServices.reportRegionStateTransition calls throwOnOldMaster before
  AssignmentManager handles the transition. The guard rejects when
  initiatingMasterActiveTime > currentMasterActiveTime, throwing
  MasterNotRunningException("Another master is active"). See 2.6.6
  MasterRpcServices.java:1795-1806,2584-2592 (4.0: 1890-1896,2620-2630).
  For T0 > T1, M1 rejects the legitimate report from M0's earlier term.
* HRegionServer.reportRegionStateTransition constructs the request once outside
  its retry loop. On ServiceException it resets the stub and retries but never
  changes the saved initiatingMasterActiveTime. See 4.0 HRegionServer.java:
  2366-2420; the 2.6.6 path has the same structure. Waiting cannot make T0 <=
  T1 because T1 is fixed for M1's tenure.
* M1 may replay P's open request, but HRegionServer.submitRegionProcedure
  rejects the same procId while the original handler remains in
  submittedRegionProcedures. See 2.6.6 HRegionServer.java:4162-4185 and
  RSRpcServices.java:3998-4003. The original handler has not reached
  finishRegionProcedure because it is blocked reporting OPENED.

Failure and invariant
---------------------
The RegionServer has opened the HRegion internally but does not add it to
onlineRegions until the OPENED report succeeds. The Master cannot accept the
report, and retrying its request does not create another handler. A client Get
to that RS can receive RegionOpeningException from
HRegionServer.getRegionByEncodedName while regionsInTransitionInRS remains
opening (2.6.6 HRegionServer.java:3690-3706). This violates expected
availability after a tolerated master failover and has no progress under the
same M1 tenure. It may recover after a further failover or RS restart; do not
describe it as an unconditional permanent data loss. The handler's fatal
exception abort path is reached if reportRegionStateTransition eventually
returns failure; while its retry loop remains active, the observed symptom is
an indefinitely opening region.

Evidence boundary and reproduction
----------------------------------
The source independently establishes the non-monotonic epoch guard and retry
deadlock under T0 > T1. The attachment reports a MiniCluster regression named
TestMasterActiveTimeFailoverSkewMiniCluster with 1/0/0 and >170 retries, using
an override of getMasterActiveTime rather than modifying production code.
Those particular test and log facts are attachment claims, not inspected raw
artifacts in this review. A definitive runtime confirmation should capture
both active-time values, the same procId/OPENED request on retries, the
RegionOpeningException, and recovery when either the epoch relation or
failover condition is removed. This review does not establish whether the
issue is already reported upstream.
