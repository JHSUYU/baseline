zk-bugs-container-reuse — stale container-cleanup path deletes a replacement znode
Source reviewed: Apache ZooKeeper checkout /users/ZhenyuLi/zookeeper at aafd344eeeb5090e0e24126ea9e28133a77c22b0 (2026-10-07 review).
Conclusion: CONFIRMED source-level correctness bug for a cleanup request queued across delete/recreate of the same path. The attached two-test five-node reproduction was unavailable for independent rerun; GraphChecker's supplied list says this case was accepted but not yet built as a GraphChecker case. Novelty across all upstream issues/releases is not established by this review.

Contract and state. ContainerManager should remove an empty eligible container, while preserving a newly created node at the same pathname. DataTree's container set and node stats distinguish a particular incarnation of a znode. ContainerManager.getCandidates at zookeeper-server/src/main/java/org/apache/zookeeper/server/ContainerManager.java:185-225 snapshots only path strings after checking emptiness and age/cversion. A new container with cversion=0 is deliberately protected for maxNeverUsedIntervalMs; a persistent znode is not a container-cleanup candidate at all.

Trigger sequence.
1. Old container P has become empty after it previously had a child, so its cversion > 0 and P enters getCandidates' returned set (:185-199). checkContainers iterates that set later at :140-160, creates DeleteContainerRequest(P) at :145, and sends it at :149. The request includes the path, not the old P's czxid, cversion, ephemeral owner or other generation identity.
2. Before postDeleteRequest, a client deletes old P and creates a new empty P. The replacement may be a fresh container protected by its age/cversion, or a persistent node with user data. This normal path reuse removes old P from the live container set; it does not remove the already captured P from the manager's local candidate set.
3. PrepRequestProcessor.pRequest2Txn's deleteContainer arm at zookeeper-server/src/main/java/org/apache/zookeeper/server/PrepRequestProcessor.java:328-347 fetches the *current* node for path P. It checks only childCount > 0 and EphemeralType == NORMAL. It never verifies that P is still the selected container generation, nor that the current node is a container. EphemeralType.get(0) returns VOID at EphemeralType.java:168-186, so a new persistent P also passes. The server builds DeleteTxn(P) at :340.
4. DataTree.java:945-951 applies that transaction through deleteNode(P); DataTree.java:545-605 removes the current node and its data. A subsequent client read correctly gets NoNode via FinalRequestProcessor.java:717-723 / DataTree.java:711-715. The incorrect operation was the stale internal delete, not the NoNode response.

Impact and limits. The newest P may contain user data and is deleted despite never being selected as an eligible container. That is data loss of a successfully created znode. If it is a new empty container, it is deleted before the intended grace period. A new nonempty P is protected by childCount > 0, so the bug requires a replacement with no children at the moment the stale request is prepared. It also requires the cleanup request to reach the server after the replacement create has committed. An explicit application retry could create P again, but does not recover data already deleted.

Attached evidence and limits. The supplied list reports ContainerReplacementCoordinationRegressionTest's two tests as 2/0/0 on a five-node quorum, pausing only the genuine ContainerManager.postDeleteRequest. Those test sources and original logs are not present in the available workspace. The source implementation independently proves that the stated ordering deletes the replacement, but this review cannot independently attest to the reported test count or GraphChecker detection; the supplied list explicitly says no GraphChecker case was built.

Repair direction. Carry the selected node generation (at least czxid, and preferably type) in DeleteContainerRequest and reject it if the current P differs. Recheck that the current node is actually a container or TTL candidate and still satisfies eligibility before constructing DeleteTxn. A regression test should select old P, delete/recreate P through a public client while the cleanup request is paused, then release it and verify the new persistent P's bytes and the new container's grace-period survival.
