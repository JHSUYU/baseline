## Source and issue boundary

At original Solr 8.11.4 revision `e27f44e3d78dfcec230c97e0a1240e3751daeff9`, `ZkCmdExecutor.java:68-97,137-139` catches the connection-loss exception and sleeps **1500 ms** before its next attempt. `ZkStateReader.java:2301-2319` updates the local alias snapshot only after its watched `getData` returns; `:2220-2224` exposes that snapshot by volatile read. `RoutedAliasUpdateProcessor.java:129-135` reads only that local snapshot and throws for missing properties, while `:120-123` wraps the failure as a server error. Thus the observed target 202 ms after the injected failure lies inside the genuine retry interval. `CreateAliasCmd.java:75-87` explicitly acknowledges eventual propagation, but says a newly created alias should be usable immediately; the original test creates the alias then immediately indexes (`TimeRoutedAliasUpdateProcessorTest.java:132-138`). The source-level interpretation is a transient per-node alias-cache visibility window becoming a non-retried HTTP 500.

Official [SOLR-12256](https://issues.apache.org/jira/browse/SOLR-12256) concerns `AliasesManager.update()` returning a stale ZK value without `sync()`; this trace instead blocks a watched read during its retry, and `update()` already invokes `sync()` in this revision. Official [SOLR-12258](https://issues.apache.org/jira/browse/SOLR-12258) concerns unresolved collection/alias lookup in V2 request routing, while this request resolves a physical core and fails later in the routed update processor. Official [SOLR-12413](https://issues.apache.org/jira/browse/SOLR-12413) concerns startup after manually deleting/recreating `/aliases.json`. The original test class is annotated `@BadApple(SOLR-13059)` (`TimeRoutedAliasUpdateProcessorTest.java:73`), but [SOLR-13059](https://issues.apache.org/jira/browse/SOLR-13059) documents a different `testSliceRouting` “no core retrieved” failure. These issues show adjacent known consistency/test flakiness, not an exact duplicate for the observed stack; this bounded comparison does not prove novelty.

**Verdict:** a well-evidenced, one-fault, same-reader candidate for a request-visible transient alias-cache gap. `new_bug=false` pending further validation. The failure is not evidence of a permanently stale cache or exhausted retry, and synthetic exception injection is not proof that a real ZooKeeper connection interruption would produce the same ordering. Minimal remaining verification: keep the embedded cluster alive through the first 1500 ms retry and issue a second request to the **same physical node/client** after retry completion; repeat the exact scenario with a real lower-level connection interruption or proxy fault; then compare current Solr behavior and search duplicates more broadly. Preserve all five raw runs and do not merge them into fuzz-effective counts.
