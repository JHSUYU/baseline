# HBASE-32 s272: independent provisional lock audit

**Classification:** source-backed recovery-stall candidate, pending exact fresh-fixture replay and known-issue comparison. This audit is read-only; it does not turn the injected B7 `DoNotRetryIOException` or the 360-second timeout into a new-bug claim. The unchanged `TestRegionReplicaFailover#testLotsOfRegionReplicas` did not finish before the timeout. The s272 original archive (`cases/HBASE-32/work-upstream/evidence-s272-original-remote-receipt.json`) has equal node0/node1 SHA-256 `055a3444b755e72df7a72003e1d76b222b7ac2b5c19e9f6c89a4abcc2e06ee99` and 19 per-file matches; local log archive SHA-256 is `a388539c98e8b628db36c5c19dc532a0c8dd4fa8a21252774e894856c380a076`.

The same replica-2 raw primary region appears in the two selected fault events (`work-upstream/logs/s272.log.gz:10391,12674`) and B7 target rethrow (`:12710`). The first `MASTER_OPENED_RPC` fault selected RS `ms1140.utah.cloudlab.us,43323,1791373804663`, which hosted `hbase:meta` in its pre-fault OPEN record (`:1264`). The second fault triggered the direct expected B7 exception, followed by the selected RS abort (`:12815`); expiration began at `:14019`.

Unlike s203, this run proves the previously missing **same `ServerStateNode` identity** edge. Diagnostic source/lock trace logs RPC handler JVM thread 314 READ ACQUIRED on node `72dae815`, server RS43323 at `:13468` (sequence 605). RegionServerTracker thread 666 logs WRITE BEFORE_LOCK on **the same node and server** at `:14020` (sequence 741). No READ RELEASED or WRITE ACQUIRED for that node appears before the shutdown hook at `:27186` (11:55:44 UTC). Immediately after shutdown, the handler releases READ (`:30673`), the tracker acquires WRITE (`:30672`), and only then the first SCP is scheduled with `carryingMeta=true` (`:30678`, 11:56:13 UTC). Event sequence numbers are not a strict ordering across different threads at that post-shutdown instant; their UTC timestamps establish release before acquire.

All four independent pre-shutdown dumps at 130, 200, 300, and 350 seconds show stable wait edges. The tracker is parked in `AssignmentManager.submitServerCrash:1980` for RW AQS `<0x00000007b7891620>`. Handler 314 is parked in `AssignmentManager.reportRegionStateTransition:1262 → updateRegionTransition:1298 → RegionStateNode.lock:337` for region AQS `<0x00000007b879fe28>`, which `PEWorker-14` owns. That worker is in `RegionRemoteProcedureBase.execute:323 → AssignmentManager.persistToMeta:2290 → RegionStateStore.updateRegionLocation:238 → HTable.put:565 → RpcRetryingCallerImpl.callWithRetries:184`; the log's `PEWorker-14` retry at `:13826` addresses the aborted meta RS43323. Dump SHA-256 values in time order are `b86b4bcc9727b034b3b999a7f4e45885851ddbc8f6b608adc8d9836527b77d4a`, `b44533e5b04c12bf3079175ac481bfcc71d5b3e79d52e87d9b2e2ed151106f0e`, `ef0a0d60c6311950084774e7b7d5343c8acd5ecd05b407ad4fc27f79e2d359a4`, `6a13071acb9003853f6cda655926066e4b920cd10543670fd99ab34b7c24148c`.

Exact HBase 2.6.6 source (checkout `d5f63f523c`) makes the dependency explicit: `AssignmentManager.reportRegionStateTransition:1256–1278` holds a server READ lock across `updateRegionTransition`, while `submitServerCrash:1980–2008` requires WRITE before submitting SCP. `RegionRemoteProcedureBase.beforeExec:289` holds the region lock through the meta persistence in `execute:323`, releasing in `afterExec:295`. `ServerCrashProcedure.java:163–194` processes a crashed meta-hosting server by splitting meta logs and assigning meta. Thus the observed chain is tracker WRITE → handler READ → PEWorker region lock → failed meta write → delayed meta recovery by unscheduled SCP. This is an observed recovery dependency cycle sustained through four dumps, although the RPC retry policy means it is **not yet proof of an infinite Java monitor deadlock**.

[HBASE-21508](https://issues.apache.org/jira/browse/HBASE-21508) fixed stale transition reports racing with SCP, and supplied the current read/write fencing; s272 reveals a potential liveness consequence within that fencing. [HBASE-24526](https://issues.apache.org/jira/browse/HBASE-24526) describes a meta assignment already underway while PEWorkers are stuck on meta updates; here the first SCP that could assign meta is delayed until shutdown, a narrower stage distinction. These differences support investigation, not a novelty declaration. s203 had the same partial raw wait pattern twice but lacked same-node identity; its four trace-only diagnostic controls passed, including one fault to a meta host with all READ holders drained before WRITE. s272 is the first trace-positive run. Require at least one independent same-plan replay with unchanged JUnit, exact actor/lock trace and pre-timeout dumps, and verify the known issues before marking a new bug.
