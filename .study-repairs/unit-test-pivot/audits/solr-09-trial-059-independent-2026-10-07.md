# SOLR-09 stage-2 trial 059: independent candidate review

Read-only review on 2026-10-07, updated after replays `h` and `d` completed. This document does not change the case owner’s result or run another cluster. **Disposition: exact selected exception observed twice, but a new correctness bug is not confirmed.** The stronger evidence is for a delete request that returned an error after the target replica was removed, not for an unrecovered replica. Its cause and repeatability still need actor-matched replay and an independent post-operation state observation.

## Raw identity and sequence

The workload is the unchanged Solr 8.11.4 `DeleteReplicaTest.deleteReplicaAndVerifyDirectoryCleanup` in a four-Jetty `MiniSolrCloudCluster`. Its [source](../source/solr-8.11.4/solr/core/src/test/org/apache/solr/cloud/DeleteReplicaTest.java) creates a two-replica collection, calls synchronous `DELETEREPLICA` on the current leader, then checks leader replacement and deletion of the old instance/data directories (lines 149–170). The healthy original-class JUnit passed (`failures=0`). Trial 059 ran 74.201 seconds, had three applied faults, one exact target check after the last fault, and a failing JUnit.

### Runtime actor identity limit

F0's trace records the exact core URL and node. F1/F2 selectors and events record path, caller and relative ordinal, but **no node ID, thread ID, or `ZkStateReader` object ID**. The log's F1 exception stack runs in the Overseer command thread (`n:127.0.0.1:39759_solr`), so F1 can be associated with that command's reader use by stack and thread context, though not with a stable reader object ID. F2 appears in `zkCallback-69-thread-1` without node MDC. Four embedded nodes can execute the same ZK callsites. This proves fault-type/callsite/path order, but not which runtime reader got F2. Consequently “3/3 strict” means selector-strict, **not** semantically identical reader placement across runs.

## Source path and observed recovery

In original [DeleteReplicaCmd.java](../source/solr-8.11.4/solr/core/src/java/org/apache/solr/cloud/api/collections/DeleteReplicaCmd.java), a live target first receives CoreAdmin `UNLOAD` (lines 248–252). The callable processes that response and waits up to 30 seconds for the replica to disappear from its `ZkStateReader`; if it does not, it enqueues `DELETECORE` and waits another 30 seconds (lines 254–266). It returns false only after both waits fail, then line 277–279 throws the selected exception. There is **no CoreAdmin HTTP retry** in this path. The `IOException` at F0 is consequently an expected failure of the first deletion channel, but the code deliberately tries the fallback. A later false result is not implied by F0 alone.

The [JUnit log](../cases/SOLR-09/http-stage2/evidence/campaign/trial-059/junit.log) records an injected CoreAdmin error at 12.457 s, a `DELETECORE`-related collection-state update around 42.47 s, and a `ZkController` watcher logging that **the same target core** `deletereplica_test_shard1_replica_n1` was removed from cluster state at 42.474 s. The core then closes, and `core_node4` registers as new shard leader at 45.018 s. At 72.473 s, the Overseer command thread still reports the same `core_node3` as `not_removed` and the API returns `Error waiting for corenode gone`. These are different watcher/command threads and likely different `ZkStateReader` instances; the log does not expose the reader object identities or the Overseer's cache contents. After the test, the target instance/data directory is absent from retained trial scratch while the surviving replica's directory remains. The original JUnit exits on the API error before its leader and directory assertions, so there is no JUnit postcondition observation taken while the cluster is running.

The observed timing is consistent with the [Overseer wait predicate](../source/solr-8.11.4/solr/core/src/java/org/apache/solr/cloud/api/collections/OverseerCollectionMessageHandler.java) (lines 432–458) timing out against its own local `ZkStateReader` despite the state update being visible to another watcher. In [ZkStateReader.java](../source/solr-8.11.4/solr/solrj/src/java/org/apache/solr/common/cloud/ZkStateReader.java), the relevant watcher catches `ConnectionLoss` and logs it (lines 1374–1392), while `waitForState` waits on a watcher latch until timeout (lines 1877–1924). This is a plausible mechanism for stale local feedback after F1/F2; the raw trace does **not** show an Overseer cache snapshot or prove precisely which watch/update was missed.

Solr 8.11's [DELETEREPLICA reference](https://solr.apache.org/guide/8_11/replica-management.html) describes removal of the state entry and default core/directory cleanup. Trial 059 has evidence of those effects but returned an error. This is a potentially misleading operation result, yet an injected transport failure can also make a synchronous API return an error after partial or eventual completion; the reference does not promise that an error means no deletion occurred. The trial does not establish durable state corruption or failed recovery.

## Existing issues and replay limit

[SOLR-16257](https://issues.apache.org/jira/browse/SOLR-16257?focusedCommentId=17576777&page=com.atlassian.jira.plugin.system.issuetabpanels:comment-tabpanel) describes a specific `collectionWatches`/`watchedCollectionStates` map race that can leave a collection state stale; it was fixed for 9.1. The timeouts and stale-looking local feedback here are compatible with its symptom, but trial 059 does not record the two maps or the documented interleaving, so it is **not proven to be that known bug**. [SOLR-12087](https://issues.apache.org/jira/browse/SOLR-12087) describes a deleted core whose replica entry persists in `state.json` as DOWN. Trial 059 instead records state removal on the replica node and new leader election, so its observed state does **not** match that issue's central failure; a ZK snapshot would make the distinction conclusive.

The owner's clean replays `a` and `c` matched **zero** planned faults because their chosen leader/core differed from the literal F0 selector. Replays `b` and `e` matched only F0; they cannot test the triple-fault mechanism. Replays `d` and `h` both applied 3/3 selectors and checked the same `core_node3`/`..._n1` target after F2. `d` returned `removed` and passed the original JUnit; `h` returned `not_removed`, threw the same target exception as trial 059, and failed the original JUnit. Thus `h` is a **second selector-level observation** of the candidate and `d` is a **selector-level counterexample**.

All three show a successful-looking state removal on a `ZkController` watcher. The two failing runs then spend another roughly 30 seconds before the Overseer's second wait returns false. The passing `d` run's wait observes removal almost immediately after F2. This narrows the discrepancy to the command-side state observation/wait path, but the logs cannot tell whether the Overseer's cached `DocCollection` had updated or whether F2 hit the same reader in each run. The F1 stack maps to an Overseer command thread in all three runs; the F2 callbacks have no node MDC or object ID. Callback pool numbers differ, but they are per-run names and cannot be equated with physical actors. The selected F0 core is the same logical leader in each run, while its ephemeral port changes. No authoritative `state.json` or command-side cache snapshot was captured before teardown. In original 059 and `h`, retained scratch lacks the removed core's directory and retains the surviving core's directory; this supports eventual cleanup but is not a live-cluster JUnit assertion.

The audit did not influence these replays.

For confirmation, a V2 trace/replay must bind F0 to the **actual elected leader's core/node** and F1/F2 to specific physical nodes and reader instances, prove all three applications and exact final target in order, and capture before teardown: the authoritative ZK `state.json`, Overseer's local `DocCollection`/watch state, and the target node's core and directories. Compare API return with those observations. The selector-strict outcomes are 2 failures and 1 pass, but their reader-level identities are unproven; this remains an **unconfirmed, possibly timing/placement-sensitive candidate**. Do not mark it as a confirmed new bug without actor-level causal evidence and a clear violated postcondition.
