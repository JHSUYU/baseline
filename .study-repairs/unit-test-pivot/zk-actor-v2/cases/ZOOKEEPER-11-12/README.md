# ZOOKEEPER-11/12 actor-aware V2 adapter

This case-local adapter reuses the shared read-only `ActorRegistry` and `Probe` in `zk-actor-v2/src`. It runs the unchanged ZooKeeper 3.8.7 three-peer `CurrentEpochWriteFailureTest#testReadCurrentEpochFromAcceptedEpochTmpFile` once per healthy seed or fault plan, then evaluates two **separate** target gates and effective-trial counters.

- **ZOOKEEPER-11:** `QuorumPeer.loadDataBase:1169` checks `currentEpoch.tmp.exists()` while the zxid epoch exceeds `currentEpoch`. Its source-specific `IOException` is thrown at bytecode line 1175 if the temporary file is absent.
- **ZOOKEEPER-12:** `QuorumPeer.loadDataBase:1193` checks `acceptedEpoch < currentEpoch`; its source-specific `IOException` is thrown at bytecode line 1197.

The unchanged test chooses `servers.mt[0]` as `firstServer`, deliberately writes that peer's `currentEpoch` and `currentEpoch.tmp`, then restarts the cluster. The ASM hook reads that actual `MainThread` object's `QuorumPeer.myid` and snapshot directory. `loadDataBase` registers each actual QuorumPeer receiver with the shared registry. Every file selector includes peer SID, exact normalized epoch filename (`currentEpoch`, `acceptedEpoch`, or their `.tmp` forms), operation, bytecode site, and actor-local ordinal. `FileReader` and `AtomicFileWritingIdiom` hooks pass the actual QuorumPeer receiver and File. `AtomicFileOutputStream` hooks inspect its actual `origFile` and `tmpFile` fields, including the rename site. An unknown file owner, mismatched receiver/file owner, or invalid atomic pair is ineligible. Raw peer IDs and file paths remain in the trace for audit.

This fixes concrete drift in the historical global-ordinal trials: ZK11's `readLongFromFile:2186@@1` referred to healthy peer2 but trial-026 applied on peer0; ZK12's same key moved healthy peer0 to trial-026 peer1. In ZK12 trial-005, only peer1/2 checks executed after a peer0 fault. V2 counts a target only if the actual original `firstServer` peer0 executes that **same selected check after the last fault**. Old trials remain historical and never count toward V2.

Run `python3 build_adapter.py` and `python3 smoke_v2.py` offline. The builder locks the original Git revision and original test, QuorumPeer, and AtomicFileOutputStream class hashes; it verifies the rewritten classes with `-Xverify:all` and tests wrong-peer, wrong-file, and wrong-target matching. Neither command launches the cluster. Once a ZooKeeper port/JVM slot is assigned, run `python3 calibrate_v2.py --run --worker-id N --worker-count M`. This executes two fresh original embedded-cluster JUnits and requires successful JUnit results, all three peer bindings, the actual firstServer SID, exact raw File provenance, coverage, and both healthy target guards. Then run `python3 campaign_v2.py --run --worker-id N --worker-count M` inside tmux. The campaign checkpoint is `zk1112-actor-v2-runs/zk1112-v2-state.json`; completed trial receipts are recovered after interruption, while a partial run is archived and its plan requeued.

Each check targets **80 effective trials with at most eight ordered faults**, conditionally extending that check to 128/max10 if the last eight effective trials add code or actor-bound file-I/O coverage. A shared JUnit trial can count for both checks only when both exact peer0 guards occur after all planned faults. The total selection cap is 480; queue exhaustion or the cap is reported separately from budget completion. A target throw is recorded as a candidate for source review/replay, not automatically a new bug. The campaign selects production epoch-file reads, writes, temporary-file open, and rename. The original test's two setup writes are recorded for provenance but excluded from fault selection because failing the setup itself removes the target. Socket and ZooKeeper API I/O are outside this adapter's current scope.

Two fresh original JUnit healthy calibrations ran on node2 in isolated port slot 16/16. Both passed in about 17 seconds and each recorded the peer0 ZK11 and ZK12 guards, 97 bound file-I/O events, and all three QuorumPeer bindings; the two runs shared 97 exact selectors. The raw File receiver and selected I/O are audited in each emitting thread because independent peers interleave in the global trace. The historical ZOOKEEPER-11/12 campaigns and shared ZK01/02 sources were not changed.

The campaign scores code and file-I/O novelty only when the original selected peer0 check executes **after the final applied fault**. Trial 010 applied four faults, then reached both peer0 guards; its three new `QuorumPeer.loadDataBase` lines are valid feedback. Trial 011 applied five faults but reached neither guard; it contributed zero feedback and no mutation. A completed-boundary migration recovered trial 011 once, audited that the coverage and I/O seed sets did not change, and recorded old/new controller and calibration hashes in `evidence/migration-strong-loss-penalty.json`. Trial 012 showed one fault on peer2 `acceptedEpoch` write also lost both targets; trial 013 moved the same I/O family to peer1 and retained both selected peer0 checks.

The first loss penalty grouped by the first fault alone. Trial 007/008/010 showed this was too broad: the same first fault had target-retaining extensions, including the three-line gain in trial 010. A second completed-boundary migration after trial 027 narrows the penalty to the **entire tested parent plan plus the actual actor of the next fault**. Three exact losses with that key and no target-retaining sibling of that key lower normal-turn priority; every tenth selection remains an exploration turn. The migration checks that recovering target-lost trial 027 changes neither coverage/I-O feedback nor effective counts. These migrations retain the two original healthy traces and all completed trials without replay.

A third completed-boundary migration after trial 038 adds a similarly precise **last-fault site** feedback key: callsite, actual actor, exact epoch file and operation, actor-local ordinal, and injected exception type (`java.io.IOException`). The peer0 `currentEpoch.tmp` existence I/O in `QuorumPeer.loadDataBase:1169` lost both targets in trials 011, 016, 029, 034, and 038, with no retaining trial at that site. It is downweighted on ordinary turns only, while the one-in-ten exploration opportunity remains. The migration verifies the 37 completed result rows, full pending queue, effective counts, coverage and I/O seeds, raw healthy traces, and controller/calibration hashes; trial 038 is recovered once and contributes zero feedback. See `evidence/migration-loss-sites.json`.
