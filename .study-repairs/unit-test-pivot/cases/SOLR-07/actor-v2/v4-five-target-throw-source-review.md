## Source-constrained causal reading

`CoreContainer.createFromDescriptor:1473` calls `registerCore`, which puts the newly created core into `solrCores` before synchronous `ZkContainer.registerInZk` (`CoreContainer.java:1249–1269`, `ZkContainer.java:202–241`). `ZkController.register` can then wait for leader and collection state at lines 1265–1313; the injected ConnectionLoss is observed in that read path, including an explicit `Probe.io` stack under `ZkStateReader.getLeaderUrl` / `ZkController.getLeader` in trial 038. Only after the wait does line 1317 reacquire the local core; line 1326 throws if `cc.getCore` is null.

`SolrCloudTestCase.shutdownCluster` is `@AfterClass` (`SolrCloudTestCase.java:287–295`) and calls `MiniSolrCloudCluster.shutdown` (`MiniSolrCloudCluster.java:632–652`), which stops each Jetty. `CoreContainer.shutdown` logs shutdown, marks `isShutDown`, and calls `solrCores.close` (`CoreContainer.java:1034–1090`). `SolrCores.close` clears the core map before closing each core (`SolrCores.java:88–124`). On a SolrCloud node `CoreContainer.getCore` returns null when the name is absent (`CoreContainer.java:1962–1990`). This gives a concrete explanation for the observed `corePresent=false` when a blocked registration request resumes during/after teardown. `ZkController.register:1370–1372` then attempts `unregister`; the errors in 038/048/252 show this catch path after shutdown. An `AlreadyClosedException` may also be swallowed in `ZkContainer.registerInZk:214–223`, so no `ZkContainer` error line is required for 064/247.

The injected ConnectionLoss is a **separate earlier event**, not the target exception. The original JUnit failure is the client HTTP timeout, not a `SolrCore is no longer available` assertion. The target exception is a secondary effect of a pending registration request overlapping orderly test teardown. The timeout may reflect an undesirable state-watch recovery after synthetic ConnectionLoss: `ZkStateReader.StateWatcher.refreshAndWatch:1373–1395` catches and logs ConnectionLoss without a local re-registration in that catch. This observation alone does not prove a product defect or novelty, particularly because the fault hook synthesizes an exception before the real I/O and exact-plan reproduction has not succeeded.

The bounded replay audit for trial 038 (`node2:.../actor-v2/trial038-replays-audit.json`) records five tries: 0, 0, 1, 0, 0 of two planned faults applied; all five JUnit runs passed and none hit the target exception. All are non-strict and therefore neither confirm nor refute the original exact sequence. No strict replay of any of the five target throws is established by this audit. A new-bug claim would require an exact replay in which the check fails **before** `###Ending` / cluster shutdown, or a separately justified operational failure with source-level root cause and an appropriate oracle. The frozen evidence supports `novelty=pending`, `new_bug=false`.
