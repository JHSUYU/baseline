# HDFS-28 alternate original HA JUnit: healthy calibration

This directory is an **independent, fault-free calibration only** of released Hadoop 3.4.3 `TestPipelinesFailover#testLeaseRecoveryAfterFailover`. It is a source-reviewed fallback for the HDFS-28 `BlockRecoveryWorker.getDatanodeID` guard. Its two runs and any later fault budget have no overlap with the current `testFailoverRightBeforeCommitSynchronization` HA ledger, the older `TestBlockRecovery2` phase, or their denominators.

`healthy_gate.py` invokes the existing case-local ASM/JaCoCo `run_original.py` with `--test-method testLeaseRecoveryAfterFailover`. Each seed gets its own output, MiniDFSCluster scratch, dynamic cluster ports, raw trace, JaCoCo data, JUnit log, and manifest. The calibration takes the shared `unit-test-pivot/jvm-start.lock`, waits for an active HA JUnit to finish, checks at most four existing Java processes and at least 10 GiB free, then holds the lock through this short healthy JUnit so the HA controller can resume at the next trial boundary. It never edits the current HA checkpoint, queue, seen IDs, or running JVM.

The runner is resumable at completed-seed boundaries: a completed healthy seed with a passing manifest and raw files is reused; a partial seed is left untouched for manual review. `healthy-receipt.json` records raw/source hashes. `validate_healthy.py` independently requires two passing original JUnit executions, contiguous traces, an observed 3-DataNode cluster, the same HDFS-28 source guard, an owner-bound recovery root, and RPC points before a later guard on that root in each seed. It also requires shared RPC site families and matching released test/overlay provenance. Failure of any check means this JUnit is not admitted as a fallback workload.

The source rationale and the current queue limitation are recorded in `../audits/hdfs28-original-junit-alternatives.md`. A separate campaign, if needed, must initialize a fresh queue/seen ledger and per-case effective denominator from these validated seeds; these healthy calibrations do not count as fault trials or bug observations.

## Two bounded single-fault pilots

`pilot-plans.json` fixes two distinct one-fault `IOException` selectors from the two healthy traces. Pilot 01 uses healthy-a's `initReplicaRecovery` application RPC at sequence 23, physical owner `dn2`, first recovery attempt; pilot 02 uses healthy-b's Hadoop IPC request at sequence 26, physical owner `dn0`, first recovery attempt. Both site families occur in both healthy seeds, and each selected point precedes another HDFS-28 guard in its own actor/recovery root. Their exact selector IDs are `ad2b315ff43a0d8cc6a0a7d4` and `705a661100d2938211f182d0`.

`pilot_gate.py --pilot 1` or `--pilot 2` launches one original JUnit with the same shared JVM start lock, Java count, and 10 GiB disk gate as the live HA campaign. It releases the lock after the pilot JVM starts, preserving other campaigns' scheduling. Each pilot has its own `pilot-NN/` scratch and raw artifacts. A completed manifest is reused, and an interrupted partial run is left for manual review. `audit_pilot.py --count 1|2` independently checks source/JAR provenance, exact runtime actor-bound fault application, a later same-owner/recovery-root HDFS-28 guard, JUnit result, JaCoCo feedback, and raw SHA. A target throw is a candidate requiring replay and source review. These pilots remain outside both the current HA effective count and any later alternate-JUnit 80/128 denominator.
