# HDFS-28 original JUnit fallback shortlist

This is an offline source review for a possible fallback if the current HA campaign reaches its cumulative attempt ceiling with fewer than 80 HDFS-28 effective trials. It does not add a tested workload or alter the running denominator.

The released Hadoop 3.4.3 `BlockRecoveryWorker.RecoveryTaskContiguous.recover()` invokes `getDatanodeID(bpid)` at the start of each location iteration (source lines 125–132), then calls `initReplicaRecovery` on that location. The HDFS-28 guard is the `bpos == null` check inside `getDatanodeID` (lines 536–540). Thus a fault during the first location's RPC can leave later same-task location iterations and their HDFS-28 guard calls reachable; a final fault after the last location cannot. This explains the observed HDFS-28 timing gap without treating later attempts or a different physical DataNode as equivalent.

The strongest unused original HA JUnit candidate in the same released test class is `TestPipelinesFailover#testLeaseRecoveryAfterFailover` (source lines 275–321). It starts a `MiniDFSCluster` with three DataNodes via `newMiniCluster(conf, 3)`, writes an under-construction file, fails the active NameNode over, and calls `loopRecoverLease` to drive block recovery. It avoids the extra delayed `commitBlockSynchronization` and second recovery phase in the current `testFailoverRightBeforeCommitSynchronization` (lines 327–411). **This is a source-based hypothesis, not a measured yield improvement.** If needed, run two fresh fault-free instrumented calibrations of that exact released method, require the same actor/recovery-root HDFS-28 guard and pre-guard RPC points, and keep its evidence and denominator separate from the current JUnit.

`TestPipelinesFailover#testPipelineRecoveryStress` (lines 429 onward) also exercises recovery, but it uses many concurrent test threads and repeated failovers. Its larger event space makes exact actor/root selector replay harder, so it is a lower-priority fallback. The earlier `TestBlockRecovery2#testRecoveryTimeout` phase already has separate historical evidence and should not be counted again in the current HA budget.
