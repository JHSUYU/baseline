## Why HDFS-28 needs its own discovery lane

`BlockRecoveryWorker.RecoveryTaskContiguous.recover` calls
`getDatanodeID(bpid)` at the start of each replica-loop iteration
(`BlockRecoveryWorker.java:131`). In a V4 healthy trace, `RECOVERY_BEGIN`
is seq 3 and the first HDFS-28 check is seq 4, before any V4 fault point.
The second HDFS-28 check follows first-replica initialization; each healthy
run exposes only 4–6 eligible RPC/file I/O events before it. All 18 historic
HDFS-28 effective trials used one fault. The remaining 32 single-fault
selectors are marked later than the observed target, and none of the 757
queued two-fault plans has a second fault before a same-owner HDFS-28 check
in its strict parent's trace. A new fault can still reveal a retry not seen
in its parent, so zero is a feasibility warning, not a proof of impossibility.

V5 therefore needs two explicit queues:

1. **HDFS-28 producer/retry lane.** Audit the command/heartbeat or
   replica-recovery producer that supplies `RecoveringBlock` before the first
   check, and response-side I/O before later replica-loop checks. Add a
   fault point only when its runtime event carries the same block ID,
   recovery ID, coordinator DataNode identity, BP ID, and startup episode as
   the selected target. An unbound message, endpoint, or storage identity
   fails closed. The first two new original-JUnit healthy traces must show
   stable producer-to-target identities and a real pre-check I/O; otherwise
   this lane stays disabled. Newly observed retry I/O after a fault can enter
   the queue only with an exact same-owner target in its parent trace.
2. **HDFS-29/30 second-fault lane.** Preserve all 789 pending V4 plans, but
   initially prioritize the 196 pairs whose second fault occurs before a
   same-owner HDFS-29/30 check in their strict parent trace. Retain a bounded
   exploration share for the other 593 plans because a fault may expose a
   recovery path absent from its parent. Recompute the target relation from
   each newly executed raw trace; never infer it from a plan label alone.

## Isolated migration and run gate

Create a new `phase-v5/` work directory with copied source and a new overlay
digest; keep `phase-v4/` immutable. Fix V4's malformed `TARGET_THROW` JSON
suffix in the copied probe, audit any added producer/response hook against
released source and bytecode, then pass an offline ASM/selector smoke test.
Run two healthy original JUnit calibrations in separate scratch directories
with `-Xverify:all`, trace and production JaCoCo. Compare both to V4's
healthy actor/block/target signatures and ensure the new overlay produces
valid JSON, stable fault selectors, and no unexpected target throw. If the
added hooks change existing V4 selector semantics or production coverage
IDs, do not import its effective counts until the raw V4 evidence can be
revalidated under the new schema; keep it as historical evidence.

Only after that gate, initialize V5 state by copying the verified V4 queue,
`seen_sequences`, production coverage union, and all 128 completed receipts
**as read-only ancestry**. Save the source SHA-256 list and exact import
counts in a migration manifest. Use fresh `phase-v5/runs/` paths for new
attempts; old receipts keep their immutable V4 paths. The first new
completed attempt is numbered 129. Resume from a durable active manifest
without rerunning its original JUnit. A new controller writes only V5 state
and V5 trial logs; case `result.json`/checklist are reconciled after the
independent final audit.

The quality budget is **per target check**, measured in strict ordered
fault plans that retain the exact same-owner, same-block target **after the
last fault**: base 80 effective/max 8 faults, conditionally 128/max 10 when
the last eight effective trials add production branch coverage or eligible
I/O. This is distinct from V4's 128-attempt cap. Track attempted, distinct,
strict, target-retaining, JUnit outcome, elapsed time, coverage gain, and
fault depth separately. A V5 safety cap of 600 additional attempts or eight
hours prevents an unattended queue from running forever; hitting that cap
with a target below its effective goal leaves it `budget_recheck_pending`,
not `quality_complete`. Source review and exact-plan clean replay are
required for a novel selected target exception.

The node1 startup-storage V2 and HDFS-12/Solr campaigns retain their own
tmux, scratch, and dynamic ports. V5 must wait for a separate host/JVM slot
and two passing healthy calibrations before fault trials begin.
