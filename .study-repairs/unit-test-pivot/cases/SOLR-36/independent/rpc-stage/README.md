# SOLR-36/37 parent-to-child HTTP stage

This is a separate fault stage for the unchanged Solr 8.11.4 embedded-cluster `ShardSplitTest#test`. Its original base class fixes four shard Jetty servers and starts a separate control Jetty with embedded ZooKeeper. The first stage injected only native ZooKeeper I/O exceptions. This stage observes the HTTP add and delete-by-id requests on the direct target path:

In the two original healthy target traces, all SOLR-36 guard events belong to `collection1/shard1_0` or `collection1/shard1_1` (56/36 and 60/40). This is why the HTTP selector is restricted to the original test's `collection1/shard1` parent and these child shards.

`DistributedZkUpdateProcessor.doDistribAdd` or `doDistribDeleteById` → `getSubShardLeaders` → `cmdDistrib.distribAdd` or `distribDelete` with `synchronous=true` → `SolrCmdDistributor.submit` → `Http2SolrClient.request` → child `doDefensiveChecks`.

The case-local ASM probe sits immediately before the original `Http2SolrClient.request` invocation in `SolrCmdDistributor.submit`. It reads the actual originating request core from `Req.cmd.getReq().getCore()`; MDC is not used for HTTP identity. The original `setupRequest` compares `ZkStateReader.getLeaderRetry(...).getName()` with `CloudDescriptor.getCoreNodeName()`, and `doDistribAdd`/`doDistribDeleteById` set `DISTRIB_FROM_PARENT` only under `isLeader && !isSubShardLeader`. At the send gate the probe requires the request core's `CloudDescriptor.isLeader()`, exactly one active leader in that core's local `ClusterState` parent slice, the raw sender replica equal to that leader, and the sender's physical node equal to the leader node. It reads only a non-lazy `ClusterState.CollectionRef` and refuses lazy/missing/ambiguous collection state, avoiding `getCollectionOrNull()`'s possible collection fetch. Solr's `Replica.isLeader()` can consult a per-replica-state supplier; the original `setupRequest` already calls `getLeaderRetry` on this path, and the raw healthy traces remain available to audit any observer I/O. The selector uses the verified role `SOLR/PARENT_LEADER/collection1/shard1`; each receipt separately records the raw sender replica, raw leader replica, sender node, exact child replica, and actual child HTTP URL. The child URL must equal the selected `Replica.getCoreUrl()`. Add and delete-by-id, `distrib.from.parent=shard1`, site, child replica, resource, and per-family ordinal still match exactly. A matched `TIMEOUT` throws `SocketTimeoutException` inside the original `submit` exception handler; a matched `DELAY` waits 5, 15, or 30 seconds before the original HTTP call. No test method or cluster operation is changed.

Two fresh healthy JUnit runs must each pass and observe both exact target guards plus both parent-forward HTTP command families. Each family must have exact selectors in the intersection of the two runs. The campaign uses its own `campaign/state.json` checkpoint and JaCoCo feedback; every selected trial records plan, trace, JUnit result, elapsed time, exact injection, same-logical-child target guard after injection, and exact target throw. The ZooKeeper and HTTP stage counts remain separate in both checklist rows.

The first two original healthy runs passed in 101.32 and 100.917 seconds and observed 90 and 98 exact guard evaluations, but that earlier probe logged the parent sender without including it in the injection match. Its JAR, build record, and seed audit are preserved in `legacy-sender-unbound/`; its raw healthy traces remain at `healthy-01` and `healthy-02`. They do **not** calibrate the current HTTP campaign.

The raw sender-aware probe ran the unchanged original JUnit three times. All passed and reached both checks. `healthy-sender-01`/`03` elected parent `core_node4`; `healthy-sender-02` elected `core_node3`. A first fault plan calibrated to raw `core_node4` was unmatched in two more unchanged JUnit attempts, both electing `core_node3`; JUnit passed, injection count was 0, and raw probe gains are excluded from coverage feedback. The complete 1-plan/2-attempt checkpoint, JAR, seed selection, and SHA-256 file inventory are frozen under `legacy-raw-sender-pilot/` (state SHA-256 `407d4eff1f39377dab28a459b0e9f5c79fbc15d1db281759af0467fd16e8cb12`). These are historical data and are not replayed or counted in the current role-verified budget.

The role-verified version starts a fresh `campaign/` checkpoint with `healthy-role-*` original JUnit seeds. Its compiled Java 8 offline smoke verifies that a different current leader can match the same role, while wrong leader replica/node, ambiguous or inactive leader, wrong child replica, and wrong command cannot consume a fault plan. Healthy calibration must also show both guards and both HTTP command families, with raw sender equal to the unique active leader on every candidate receipt. The first fault run is one selected plan with at most two JUnit attempts; the broader budget resumes only after a strict injection and same-child target guard after the fault.

The selected trial is written to the checkpoint before its JVM starts. On restart, the runner keeps that exact selector and reuses an attempt only if its complete `run.json` exists; finished trials are never selected again. The runner hash, agent JAR, and healthy trace digests are pinned in the checkpoint.

For `DELAY`, the postfault window begins at the matching `FAULT_EFFECT` event after the sleep, when the original HTTP call can proceed. For `TIMEOUT`, it begins at the matched `IO_OBSERVED` event because the timeout throws synchronously. The first role-verified fault reached SOLR-36's exact ACTIVE/FROMLEADER guard and 503 throw after this boundary; the original JUnit passed and verified document and shard state after client retry. Source review classifies this exact path as `expected_target_rejection`, `new_bug=false`; other exact throws still pause for separate review. Its immutable raw trace and source review are in `campaign/candidates/0001-role-v2/`. `campaign/migrations/0001-effect-time-reviewed-503/` records the old/new runner and state hashes and an offline recount before the same 1-plan checkpoint resumed. No completed trial was rerun.

The HTTP agent uses the same internal class names as stage one, but a Java 8 `-verbose:class` preflight with the original classpath confirmed that both `research.solrsubshard.Agent` and `Probe` load from the HTTP stage's own agent JAR. Its SHA-256 is recorded in `agent-build.json`. The stage is therefore not accidentally using the earlier ZooKeeper-only probe.

`run_stages.py` starts with a 24-selected-plan/2-fault pilot, then resumes the same atomic checkpoint to **80 effective trials per check and 8 ordered faults**. An effective trial requires a strict exact injection and that case's exact target guard after the last fault on the same logical child. Unmatched and target-lost plans still count toward selected plans, attempts, and elapsed time, but never toward the effective budget. The driver raises the selected-plan cap monotonically until it reaches 80 effective trials, the exact selector queue is truly exhausted, an exact target exception pauses for review, or a 256-selected-plan safety ceiling requires an explicit incomplete status. No completed plan is selected again. If the last eight effective trials at 80 add an original production probe or a new HTTP selector repeats in at least two effective trials, it continues to 128 effective trials/10 faults. The stage status and result table expose selected plans, attempted original JUnits, strict injections, and effective trials separately. The initial 24-plan cap is a checkpoint, never a completed-case result.

The finished 24-plan pilot used 30 original JUnit attempts, took 3,231.556 seconds, and strictly matched 22 plans. SOLR-36 reached its exact same-child guard after the final fault in 20 plans; SOLR-37 did so in 6. All 14 observed SOLR-36 exact throws match the reviewed ACTIVE/FROMLEADER protective 503 with original JUnit recovery; SOLR-37 exact throws remain zero. The pilot added 300 original production JaCoCo probes and five exact HTTP selectors. Fault modes were sharply different: 8/8 `TIMEOUT` plans were strict and 6 reached SOLR-37 after the fault (805.228 seconds total), while 14/16 `DELAY` plans were strict and none reached SOLR-37 after the delay's `FAULT_EFFECT` (2,426.328 seconds total). This is consistent with `doDefensiveChecks` checking child ACTIVE before the range condition; a long send delay can move the child past the range-check window.

Stage two therefore selects a `TIMEOUT` plan in three of each four rounds when available, reserving every fourth round for `DELAY` and its code/I/O exploration. When a strict trial still reaches SOLR-37 after the fault, mutation may add a later ordered `TIMEOUT` at a newly observed HTTP point; delay mutations remain available. This is only a scheduler change. The audited migration under `campaign/migrations/0002-timeout-stage2/` preserves all 24 completed plan IDs, the 144 queued plans, and the coverage/selector sets. It records the byte-for-byte pilot runner and checkpoint (`235a40b48f3db29308a31e41b03850fadf7ebcdeccc8a68c00261979289e273e` and `6c044dad0ab8baf0b84f25ea473fbb3f904c46aa16c865aed9c48461bfa87652`) and the stage-two runner/checkpoint (`777428d0560f4ce3145dc9cd8c59dc8e57bb192975d57ffee6eb73c2586dda01` and `8c3dd1ea7bd60870a13018d646c3e225d619e56b71a22617d0980e8fd4b29720`). The original JUnit campaign resumed at new plan 25 without replaying 1–24.
