# SOLR-36/37 parent-to-child HTTP stage

This is a separate fault stage for the unchanged Solr 8.11.4 embedded-cluster `ShardSplitTest#test`. Its original base class fixes four shard Jetty servers and starts a separate control Jetty with embedded ZooKeeper. The first stage injected only native ZooKeeper I/O exceptions. This stage observes the HTTP add and delete-by-id requests on the direct target path:

In the two original healthy target traces, all SOLR-36 guard events belong to `collection1/shard1_0` or `collection1/shard1_1` (56/36 and 60/40). This is why the HTTP selector is restricted to the original test's `collection1/shard1` parent and these child shards.

`DistributedZkUpdateProcessor.doDistribAdd` or `doDistribDeleteById` → `getSubShardLeaders` → `cmdDistrib.distribAdd` or `distribDelete` with `synchronous=true` → `SolrCmdDistributor.submit` → `Http2SolrClient.request` → child `doDefensiveChecks`.

The case-local ASM probe sits immediately before the original `Http2SolrClient.request` invocation in `SolrCmdDistributor.submit`. Its exact selector contains **both** the parent sender replica read from `Req.cmd.getReq().getCore().getCoreDescriptor().getCloudDescriptor()` and the child collection/shard/replica from `Req.node`; the dynamic child core URL is recorded separately. It refuses a parent send without this real request-core identity. The sender is part of the per-family ordinal and of each fault-plan match; MDC is only diagnostic for ZooKeeper events. It filters for the original `distrib.from.parent=shard1` add or delete-by-id request, with distinct command markers and resource families. Trial 58's exact target throw came from `processAdd`; trial 78's came from `doDeleteById`. A matched `TIMEOUT` throws `SocketTimeoutException` inside the original `submit` exception handler; a matched `DELAY` waits 5, 15, or 30 seconds before the original HTTP call. `StdNode` created by `getSubShardLeaders` has `maxRetries=0`, so the timeout is recorded by the distributor and the original client/test recovery path determines the outcome. No test method or cluster operation is changed.

Two fresh healthy JUnit runs must each pass and observe both exact target guards plus both parent-forward HTTP command families. Each family must have exact selectors in the intersection of the two runs. The campaign uses its own `campaign/state.json` checkpoint and JaCoCo feedback; every selected trial records plan, trace, JUnit result, elapsed time, exact injection, same-logical-child target guard after injection, and exact target throw. The ZooKeeper and HTTP stage counts remain separate in both checklist rows.

The first two original healthy runs passed in 101.32 and 100.917 seconds and observed 90 and 98 exact guard evaluations, but that earlier probe logged the parent sender without including it in the injection match. Its JAR, build record, and seed audit are preserved in `legacy-sender-unbound/`; its raw healthy traces remain at `healthy-01` and `healthy-02`. They do **not** calibrate the current HTTP campaign.

The sender-aware probe has now run the unchanged original JUnit three times. All three passed and reached both exact target guards. `healthy-sender-01` and `healthy-sender-03` observed the same raw parent replica `core_node4` and the same two child replicas; their full selector intersection has 49 points, with 31 Add and 18 DeleteById points and all four parent/child command families. `healthy-sender-02` elected raw parent `core_node3`, so the full exact-selector intersection with either selected run is empty. The source path `DistributedZkUpdateProcessor.doDistribAdd`/`doDistribDeleteById` enters `cmdDistrib` only under `isLeader && !isSubShardLeader`; `setupRequest` compares `ZkStateReader.getLeaderRetry(...).getName()` to `CloudDescriptor.getCoreNodeName()`. A role-relative parent-leader abstraction could be source-justified, but this calibration deliberately keeps the actual raw sender replica in the fault match. `seed-selection.json` records the exact selected/excluded attempts and SHA-256 trace digests; `seed-audit.json` retains all three JUnit outcomes and raw identities. The selected pair is `healthy-sender-01`/`healthy-sender-03`, and no HTTP fault trial has started. Node2 was released temporarily to other original-JUnit campaigns after calibration.

The selected trial is written to the checkpoint before its JVM starts. On restart, the runner keeps that exact selector and reuses an attempt only if its complete `run.json` exists; finished trials are never selected again. The runner hash, agent JAR, and healthy trace digests are pinned in the checkpoint.

The HTTP agent uses the same internal class names as stage one, but a Java 8 `-verbose:class` preflight with the original classpath confirmed that both `research.solrsubshard.Agent` and `Probe` load from the HTTP stage's own agent JAR. Its SHA-256 is recorded in `agent-build.json`. The stage is therefore not accidentally using the earlier ZooKeeper-only probe.

`run_stages.py` starts with a 24-selected-plan/2-fault pilot, then resumes the same atomic checkpoint to **80 effective trials per check and 8 ordered faults**. An effective trial requires a strict exact injection and that case's exact target guard after the last fault on the same logical child. Unmatched and target-lost plans still count toward selected plans, attempts, and elapsed time, but never toward the effective budget. The driver raises the selected-plan cap monotonically until it reaches 80 effective trials, the exact selector queue is truly exhausted, an exact target exception pauses for review, or a 256-selected-plan safety ceiling requires an explicit incomplete status. No completed plan is selected again. If the last eight effective trials at 80 add an original production probe or a new HTTP selector repeats in at least two effective trials, it continues to 128 effective trials/10 faults. The stage status and result table expose selected plans, attempted original JUnits, strict injections, and effective trials separately. The initial 24-plan cap is a checkpoint, never a completed-case result.
