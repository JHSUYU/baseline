# SOLR-36 original-test campaign

The target is Solr 8.11.4 `DistributedZkUpdateProcessor.doDefensiveChecks` line 986/987. When a child shard leader is already `ACTIVE`, it rejects a `FROMLEADER` add tagged as coming from its parent with a 503 `SolrException`. The mapped original embedded-cluster JUnit is `ShardSplitTest#test`. Two unchanged, passing healthy executions reach the exact guard. The independent ASM recorder observes the exact guard operands and throw, while original release-JAR JaCoCo coverage and observed I/O guide the fault sequence. No GraphChecker skeleton or runtime graph is used.

The first stage injects ZooKeeper native `ConnectionLoss` at exact logical replica/resource/site/ordinal selectors. Trial 58 applied four exact faults, then observed an `ACTIVE` child guard and exact line-987 throw on a parent-forward **add**. Trial 78 applied one collection-scoped fault on a shard2 core, followed by the exact throw on a separate shard1_0 core during parent-forward **delete-by-id**. Both original JUnits passed; the failed requests were accepted after Solr's stale-state retry. In each trial, the parent and target child were separate logical cores hosted by the same physical Jetty. Eight byte-identical replays of trial 58 and four of trial 78 all strictly applied their plans and passed the original JUnit, while none reproduced the exact target throw. The source and test behavior supports temporary collection-state snapshot disagreement with protective 503 responses; the trial 78 fault's influence on the target is unproven. See `independent/campaign/candidate-0058-review.md` and `candidate-0078-review.md` with their frozen trace/replay evidence. These are **not confirmed new bugs**.

The ZooKeeper campaign is checkpointed at 78/80 unique trials pending a shared-node handoff. A separate parent-to-child HTTP stage will exercise both original add and delete-by-id calls at the `SolrCmdDistributor.submit` send boundary, with its own healthy calibration, checkpoint, elapsed times, exact identity, and post-fault target oracle. Results from both stages are reported separately before closing this check.
