# SOLR-05: `ZkController.register` replica-null check

- System: Solr 8.11.4.
- Selected site: `solr/core/src/java/org/apache/solr/cloud/ZkController.java:1274`, in `register(String, CoreDescriptor, boolean, boolean, boolean)`.
- Check: `if (replica == null) throw new SolrException(SERVER_ERROR, "Error registering SolrCore, replica is removed from clusterstate")`.
- Workload: unchanged `AddReplicaTest.testAddMultipleReplicas`, which uses the original three-node `SolrCloudTestCase` embedded cluster and executes several replica registrations.
- The test deliberately expects a separate `FAILED` capacity request. Its expected failure is not counted as this selected target exception.
- Source review: `register` first waits for the replica in cluster state, then reads cluster state again for the selected null check. This test creates and adds replicas but does not request deletion. The selected throw therefore requires a fault-driven removal or state change between those steps; an unrelated JUnit failure is insufficient.

The original test passed without instrumentation in 14.90 seconds. An instrumented healthy run passed in 18.04 seconds; the final callsite-aware healthy seed passed in 18.12 seconds. The seed reached the selected check nine times; `replica` was present at each check. Its trace recorded 1,122 I/O and target events and 17,319 covered Solr production probes (filtered against release production JARs).

`probe/weave.py` copies clean Solr sources into `probe/generated` and adds observation and fault hooks only at the chosen guard and `SolrZkClient` ZooKeeper I/O methods. It does not change the original JUnit workload. This is a coordination-I/O slice for this check; the campaign does not claim full HTTP or file-I/O interception. Each fault selector contains operation, exact observed ZooKeeper path, and occurrence ordinal. Faults must match in sequence order. `probe/campaign.py` runs the same JUnit for each selector sequence, derives new I/O behavior identities and JaCoCo coverage from the actual run, and atomically checkpoints after every trial. I/O novelty uses the first stable Solr callsite, operation, and normalized resource path. Ephemeral ZooKeeper sequence suffixes, election member names, and test node ports are normalized only for novelty feedback; the occurrence ordinal selects the exact injection point but never counts as a new I/O family. Only ordered, fully applied sequences that still reach the target after the final injection contribute feedback. During the expanded budget, each such sequence may add one later I/O fault even without immediate novelty; a sequence with new production coverage or stable I/O behavior may add up to three. A later occurrence of the same operation and resource remains a distinct exact injection selector but never counts as new I/O behavior. New child selectors carry the previous applied fault ID, a count of matching I/O operations since that fault, and the seed run’s global hit ordinal. The trace records that anchor, the actual global hit ordinal, and separate matched/applied events; the campaign validates a unique ordered pair for each requested fault. Historical selectors keep their original global-ordinal semantics. `result.json` is updated after every completed trial for the 102-case checklist. An interrupted trial reruns from its queued selector with a fresh trial scratch directory; completed trial numbers are not replayed.

The base budget was 64 trials and up to six I/O exceptions per sequence. Strict, target-retaining trial 61 added 29 production JaCoCo probes and trial 62 added one stable callsite-operation-resource I/O family, so the same checkpoint expanded to 128 trials and ten ordered I/O exceptions. Target-exception markers are candidates until replay and source review establish whether they indicate a bug. Trial logs, exact selectors, traces, coverage files, times, and checkpoint state are under `evidence/campaign/`. ## Completed result

The 128 fault trials took 9,960.685 seconds in total (including per-trial collection and queue work). The original selected check executed in all 128 trials, but only 99 trials matched and applied every planned fault in strict order. Of those, 77 still executed the target after the final fault. `probe/audit.py` independently reread all 128 raw traces and agreed with every saved strict, post-fault target, and target-exception flag. The maximum observed ordered sequence was ten applied faults; trials 84, 108, and 126 applied all ten and still retained the target.

Relative to the final healthy seed, eligible trials added 391 covered Solr production JaCoCo probes and four stable callsite-operation-resource I/O identities. Merging the eligible JaCoCo executions added 43 covered production methods and 149 covered branches. The selected `register` method was covered in the healthy seed and in the combined campaign; its 34/52 covered branches did not increase. No run entered the selected `replica == null` throw after the final fault, so there is **no candidate new bug for SOLR-05 under this test and fault scope**. A fault-induced JUnit failure or an exception at another site was not counted as the selected failure.

The selected check depends on replica membership in ZooKeeper-backed cluster state. The case-local hooks cover six `SolrZkClient` read/write methods and do not claim full Solr HTTP, filesystem, or ZooKeeper I/O interception. This test adds replicas and never explicitly removes the selected replica; the negative result does not establish that the selected branch is unreachable under other workloads or fault types. Exact trial selectors and outcomes remain in `evidence/campaign/state.json`; the independent audit and method/branch summary are in `evidence/campaign/audit.json` and `evidence/campaign/coverage-summary.json`.
