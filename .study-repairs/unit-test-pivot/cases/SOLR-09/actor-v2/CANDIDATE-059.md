# SOLR-09 selected-guard candidate, actor-aware review

Status: **reproducible fault-induced missing-refresh candidate; upstream novelty review unresolved**. This is not yet a confirmed new upstream bug.

The unchanged Solr 8.11.4 four-node `DeleteReplicaTest.deleteReplicaAndVerifyDirectoryCleanup` selects the leader replica and calls `DELETEREPLICA`. The selected production branch is `DeleteReplicaCmd.deleteCore`'s synchronous `if (!callable.call())` at original line 278. `callable` first sends `UNLOAD`, waits 30 seconds for the replica to leave cluster state, queues `DELETECORE` as fallback, and waits another 30 seconds. The branch throws `Could not remove replica` when both waits return false.

The path/callsite-only stage-2 trial 059 first exposed this branch. That trace could not establish which embedded node owned the two ZooKeeper calls, so it remains coarse discovery evidence. Actor-aware V2 binds the selected Overseer handler's `ZkStateReader.getZkClient()` object before the command and verifies the same object at the selected guard. Two independent healthy original-JUnit traces show the role-relative order `target_replica_http UNLOAD → target_overseer StateWatcher GET_CHILDREN_STAT → target_overseer fetchCollectionState GET_DATA → selected guard` on one Overseer client per run. Raw node names contain changing Jetty ports and are audit fields only.

The separate non-budget V2 replay uses this three-fault plan:

1. Throw `IOException` before the exact CoreAdmin `UNLOAD` HTTP request to the selected replica.
2. Throw `ConnectionLossException` at `StateWatcher.refreshAndWatchChildren` on `/collections/deletereplica_test/state.json`, relative hit 1 after fault 0, `actor=target_overseer`.
3. Throw `ConnectionLossException` at `ZkStateReader.fetchCollectionState` for that path, relative hit 2 after fault 1, `actor=target_overseer`.

Five of the first six role-relative runs applied all three faults in order and reached the guard after the last fault. Runs 02 and 06 threw the selected exception; runs 03–05 returned normally. Thus the behavior is sensitive to event timing despite identical logical selectors. These six runs are excluded from the V2 fuzz denominator. Raw evidence and the machine-readable summary are under `evidence/replay-role-trial059/`.

In run 02, the exact raw sequence is F0 at event 601, F1 at 605, F2 at 640, then `TARGET_CHECK not_removed` at 697 and `TARGET_EXCEPTION` at 698. F1, F2, and the selected check all report Overseer `SolrZkClient` ID `12084476`; F0 identifies the current target replica core and HTTP node. The JUnit log reports another node removed that replica from cluster state around 43.859s, while the selected guard fails around 73.857s. The handler's `StateWatcher.refreshAndWatch` catches `ConnectionLossException` and only logs it; `registerDocCollectionWatcher` explicitly refreshes only when it creates a new `collectionWatches` entry. These source paths support a lost refresh/stale cache hypothesis.

`evidence/replay-actual-zk/` is a separate, non-budget diagnostic. It copies the frozen V2 classes to a distinct classpath and reads ZooKeeper's `state.json` using the same client **after** the original `callable.call()` Boolean and `TARGET_CHECK` event are fixed. Run 04 applied all three faults in order, reached `TARGET_CHECK not_removed` at event 688, and threw the selected exception. An un-watched direct `getData` on the **same** bound Overseer client at event 689 returned server state version 8 with `replica_present=false` at event 690; the selected exception was recorded at event 691. The selected Boolean was already fixed before this read. This directly establishes a stale selected-reader view in that run. The original test log names that same selected core `deletereplica_test_shard1_replica_n2` on `core_node4`, shows its cluster-state removal at 39.614 seconds, and logs its core closing at 39.616 seconds; the selected failure occurs at 69.616 seconds. A filesystem snapshot at the selected guard is still needed because the test cleans scratch directories during teardown.

`differential-control/` uses a separate modified-production classpath. It performs a fresh-state read only after both original 30-second waits return false; if the server lacks the target replica, it changes the pending selected Boolean to success. Its first strict three-fault run printed `SOLR09_DIFFERENTIAL_FRESH_STATE replica=core_node2 present=false version=8`; the selected guard then returned `removed` and the unchanged JUnit passed. This is an attribution control and does not substitute for original-code replay.

`evidence/replay-map-state/` adds only a read of the selected reader's two maps after the original `callable.call()` Boolean is fixed. Its run 03 strictly applied F0/F1/F2, with the two ZK faults and selected guard sharing client ID `1929060688`. The guard reported `not_removed`; the direct same-client server read found the selected `core_node3` absent at znode version 8; the selected exception followed. Both `collectionWatches` and `watchedCollectionStates` lacked the collection in that **guard-time** snapshot. This absence alone does not identify the root cause: each `waitForState` removes its temporary watcher in a `finally` block when it times out. A separate diagnostic snapshots those maps immediately before that cleanup to distinguish a lost watch from the known map race. Both diagnostics are outside the fuzz denominator and use separate classpaths.

`evidence/replay-timeout/run-08/` resolves the cleanup ambiguity. It uses a separate diagnostic classpath containing the original 8.11.4 `ZkStateReader` with only a read-only hook immediately before its two timeout throws. F0/F1/F2 were applied in order at events 601/605/640; F1/F2, both pre-timeout snapshots, and the selected guard share Overseer client ID `2061091092`. At events 631 and 697, **before** the temporary watcher is removed, `collectionWatches` contains `deletereplica_test` with one watcher and zero core references, while `watchedCollectionStates` has no collection entry (`cached_version=-1`). After the second timeout, the original selected guard reports `not_removed` at event 703. A direct same-client ZK read after that Boolean is fixed finds the selected `core_node3` absent at znode version 9 at event 705; the selected exception follows at 706. At guard time the selected core's instance and data directories are absent on all four embedded nodes, including its original `node4` directory; the JUnit log identifies that exact directory when the core opens and logs its cluster-state removal/core closing around 40.7 seconds. The original test fails on the selected exception around 70 seconds. Diagnostic source, raw trace, JaCoCo, JUnit log, and per-run receipt are retained; this run is not in the V2 fuzz denominator.

The relevant original 8.11.4 source is `DeleteReplicaCmd.java:250–282` (UNLOAD, two waits, selected throw), `OverseerCollectionMessageHandler.java:432–448` (each wait's predicate), and `ZkStateReader.java:1877–1920` (watch registration, timeout, unconditional cleanup). In `ZkStateReader.java:1768–1790`, an existing `collectionWatches` entry prevents a fresh `StateWatcher.refreshAndWatch`; `StateWatcher` catches `ConnectionLossException` at lines 1610–1612 without scheduling a retry. These are the paths exercised by F1/F2 and the two recorded timeouts.

Related official reports differ in their stated mechanisms. [SOLR-12087](https://issues.apache.org/jira/browse/SOLR-12087) describes a replica that **remains** in the ZooKeeper cluster state after its core is deleted; our direct server read shows the selected replica **absent**. [SOLR-9440](https://issues.apache.org/jira/browse/SOLR-9440) describes stale cache after removing the last collection watcher, fixed before Solr 8.11.4. [SOLR-16257](https://issues.apache.org/jira/browse/SOLR-16257?focusedCommentId=17576777&page=com.atlassian.jira.plugin.system.issuetabpanels%3Acomment-tabpanel) reports a `zkCallback`/watcher-removal race that can leave cached collection state without an active watch and trigger the same `waitForState` timeout symptom; its fix is listed for 9.1. Our run 08 records the inverse pre-cleanup state, **watch present but cached state absent**, after two injected `ConnectionLossException`s prevent initial refresh. The [upstream fix](https://github.com/apache/solr/commit/97458a503bc0e5a4f52c0dc4b211d4d79cd1bccd) merges cached state into each watch to make map removal atomic; it does not visibly change the register-only-on-new-watch refresh rule or the ConnectionLoss catch. That difference suggests a distinct trigger path, but the known issue has overlapping symptoms and we have not proved whether its fix prevents this fault sequence on newer versions. [SOLR-17004](https://issues.apache.org/jira/browse/SOLR-17004) changes `waitForState` to check an existing cache before registering watchers and lists a fix in 8.11.3, preceding this 8.11.4 test. [SOLR-11535](https://issues.apache.org/jira/browse/SOLR-11535) concerns redundant concurrent state callbacks. **Upstream novelty remains unresolved.**

The old stage-2 campaign and the V2 campaign may overlap on node0; at the start of the actor-aware replays the host load was about 9.5 on 16 cores with 51 GiB memory available. After the main V2 finished and the paused old controller was stopped, a separate bounded replay ran on the frozen original-business-logic V2 classpath. It stopped at attempt 03 after a **strict three-fault, post-final-target selected exception**. Pre-run one-minute host load was 7.13 (16 logical cores), with three other Java processes, compared with about 7.77 at diagnostic run 08. The selected failure took 71.934 seconds. Raw events 601/602, 605/606, and 639/640 match and apply F0/F1/F2; events 697/698 record `not_removed` and the selected exception. F1, F2, and the guard share concrete Overseer client ID `15002221`; F0's HTTP core/node equal the bound selected replica. The JUnit log contains `Could not remove replica : deletereplica_test/shard1/core_node4` and `Error waiting for corenode gone`. Attempts 01 and 02 were not strict and are not evidence against the candidate. The replay summary, all three raw traces, JUnit logs, and JaCoCo files are under `evidence/replay-low-load/`; run 03 trace SHA-256 is `d0252fce3a7a4c2deca81ff88a44c1c72f7699d3caa7df8e6140c35ba6a925c7`. This lowers the concern that the exception required the earlier heavier host load, while the mechanism's novelty relative to SOLR-16257 still requires upstream-version testing or review.

The root case result counts only the completed V2 main campaign as qualified fuzz trials. Its 161 attempts produced 130 strict injections, 128 strict post-final-target trials, 3,063.996 seconds of runtime, and no main-campaign selected exception. The role-relative and lower-load replays and the modified diagnostic/control classpaths are separate non-budget evidence; old stages are `legacy_coarse`.
