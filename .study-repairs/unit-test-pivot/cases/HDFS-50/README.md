# HDFS-50: duplicate snapshot name check

- **System/version:** Apache Hadoop HDFS 3.4.3.
- **Original cluster workload:** `org.apache.hadoop.hdfs.TestSnapshotCommands#testCreateSnapshot` from Hadoop's released `hadoop-hdfs-3.4.3-tests.jar`. Its `@BeforeClass` starts a `MiniDFSCluster`; the test creates `sn0`, attempts a duplicate `sn0`, modifies the directory, then creates `sn1`. No workload assertion or operation was rewritten.
- **Target:** `DirectorySnapshottableFeature.addSnapshot`, source line 199, `if (i >= 0)` and its same-name `SnapshotException`. The direct branch hook records `snapshot`, `searchResult`, thread, and global event sequence before the conditional jump. Entry, return and explicit throw are recorded separately.
- **Healthy baseline:** Original JUnit passed (exit 0, 12.156 s). The target method ran three times: `sn0` insertion (`duplicate=false`), expected duplicate `sn0` (`duplicate=true`, one same-name `SnapshotException`), and `sn1` insertion (`duplicate=false`). This expected throw is the oracle baseline; its recurrence after a fault is not a new bug.
- **Fault scope:** Exact observed HDFS IPC response and NameNode edit-log sync operations. An isolated ASM overlay adds only the I/O, target, and explicit throw probes to the released Hadoop classes. The controller matches `(marker, siteId, sourceKey, occurrence, hitOrdinal)` and records observed/matched/applied events. Each trial runs the same original JUnit in a fresh in-process `MiniDFSCluster`, with a case-local data directory and JVM.
- **Coverage:** JaCoCo 0.8.15 records production HDFS and IPC probe IDs and resolves them to covered methods, lines and per-method branch counts. New covered IDs guide later fault choices. This is regular code coverage; it does not claim that every newly covered line is recovery code.
- **Campaign:** `probe/campaign.py` starts from I/O observed before the **second `sn0` call's duplicate-name branch**, adds one fault per mutation before that same call's branch, prefers points near the target while sampling earlier operations, and checkpoints after every trial. Default budget is 48 trials and four I/O faults per sequence. If new I/O or production coverage is still appearing near that boundary, resume the same checkpoint at 96 trials and six faults. Only exact applied sequences with this same dynamic check (`sn0#2`) after the last fault contribute to feedback. A later `sn1` call cannot make an otherwise lost target trial valid.

The natural duplicate `sn0` throw is distinguished by its call order and snapshot name (`sn0#2`). An extra same-name throw or a throw on another snapshot after an exact applied fault is a **candidate** requiring replay and source review. A JUnit failure from the injected `IOException` alone is not marked as a coordination bug.

Evidence is under `evidence/`: healthy trace/coverage and JUnit log, per-trial plans/traces/coverage/logs in `runs/`, and the atomic `campaign-state.json`. The checked-in `trial-ledger.csv` has elapsed time, exact selector, matched/applied status, target outcome, coverage gain and evidence paths for all 48 trials; the checked-in `result.json` is the compact case summary. The campaign ran in tmux session `hdfs50-campaign` on node0. To extend its budget, run `python3 probe/campaign.py` from this case directory after updating `campaign-state.json`; already completed trial IDs are read from the checkpoint.

## Completed result

The 48-trial budget finished in 522.992 seconds including the healthy run. Forty fault sequences matched and applied in full; 22 then reached the same `sn0#2` duplicate-name branch. All 22 took `duplicate=true` and emitted exactly the one `SnapshotException` already expected by the original test. No additional target exception or confirmed bug was found. JaCoCo feedback gained 6 covered production methods, 22 per-method branch counts, and 40 probe IDs over the healthy seed. The deepest successfully applied sequence had two I/O exceptions (the configured limit was four). The final 12 trials added no production coverage, so the conditional 96-trial extension was not used. Trials losing `sn0#2` were excluded from feedback.

## Source assessment

This selected check is a weak ad hoc coordination candidate. The requested snapshot name arrives through an HDFS RPC, but `searchSnapshot(nameBytes)` is a `Collections.binarySearch` over the same `DirectorySnapshottableFeature.snapshotsByNames` list, and `addSnapshot` inserts into that list directly after the check. The original test deliberately repeats the same name and asserts the error. The source does not show the multi-hop, cross-node or control-plane relationship characteristic of the stronger ad hoc coordination examples. The campaign still exercises the selected site so the 102-check ledger has a measured result, with this semantic classification kept separate from bug status.
