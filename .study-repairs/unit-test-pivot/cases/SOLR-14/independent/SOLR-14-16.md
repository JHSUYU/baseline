# SOLR-14/15/16: original shard split test

The unchanged Solr 8.11.4 `org.apache.solr.cloud.SplitShardTest#doTest` is the common workload. Its original `@BeforeClass` starts one Jetty Solr node and embedded ZooKeeper. The test creates a two-shard collection, splits `shard1` into five children, and issues two invalid `shard2` split requests whose remote exceptions are expected by the original test.

Two independent healthy executions under the case-local ASM/JaCoCo recorder passed JUnitCore's exact `ran=1, ignored=0, failures=0` gate in 21.663 and 22.448 seconds. The original source revision is `e27f44e3d78dfcec230c97e0a1240e3751daeff9`; the test source and release JAR hashes are in [build.json](build.json). Neither runtime classpath contains GraphChecker or a static region skeleton. The first failed instrumented startup had an ASM stack-frame verification error and was stopped; it is excluded from the healthy and fault counts.

The [first](healthy-04/events.jsonl) and [second](healthy-05/events.jsonl) valid traces have identical logical selectors despite different physical Jetty ports. Both record a `shard1` `/live_nodes` read followed by SOLR-14's line 165 check, then a second `shard1` read followed by the outer SOLR-15/16 line 524 check. The two reads returned the same ZooKeeper ephemeral owner. The final line 536 and 539 guards for SOLR-15 and SOLR-16 were not entered in either healthy run. Two later expected-invalid `shard2` requests reach SOLR-14's first check; their events are distinguished by the collection/shard source key and will not count as a post-fault `shard1` target reach.

The runtime fault identity contains the exact ASM call site, collection, shard, logical parent-leader role, normalized `/live_nodes/PARENT_LEADER` resource, and hit ordinal. The physical host and port are recorded separately. The exact target throw is the `SolrException` created at the selected original source line, not an arbitrary test failure. The line 538/543 exceptions protect a split after parent-leader loss or ZooKeeper session change, so a thrown exception alone would require source review and replay before a bug mark.

Two direct `SolrZkClient.exists` calibration trials injected a `ConnectionLossException` once, using a stable `shard1` selector at the first and second live-node reads respectively. Both plans matched and applied exactly, but the original split request aborted before the selected check could execute after the fault. Neither produced a target throw. The trials took 11.347 and 20.030 seconds; their traces and JUnit logs are under [calibration](calibration/). They demonstrate the reachability limit of an exception directly on either live-node read. The next recorder revision observes additional ZK I/O families on the original split path so the fuzzer can search faults that preserve the target.

The wider runtime adapter records original `SolrZkClient` reads and writes and derives a caller site, normalized ZK path, and collection/shard source identity. Two new healthy JUnit seeds again passed with the same exact target counts. They observed 555 identical stable fault selectors across runs; a temporal target hint and source filter yielded 69 initial points in 26 I/O families. The case-local [fuzzer](fuzz.py) stores a resumable state after each trial, chooses new fault families with JaCoCo production probe feedback, mutates ordered sequences only when the target path is preserved, and records each check and each exact throw independently. The budget is 80 trials and up to eight ordered faults, shared by the three check decisions.

The first five wider-adapter trials all matched strictly but aborted before a shard1 target check. Trial 6 injected one exact `ZkStateWriter.writePendingUpdates#setData` collection-state fault; the original JUnit passed and the shard1 line 524 outer check still executed after the fault. It added 30 JaCoCo probes in original `ZkDistributedQueue`, `Overseer.ClusterStateUpdater`, `ZkStateReader`, and `ZkStateWriter` classes. An offline union of the original release JARs confirms two new production methods and 12 new production branch outcomes over the two healthy seeds (5,360→5,362 methods; 6,939→6,951 branch outcomes). The selected line 536/539 final guards and throws remained absent. After this first validation stage, the scheduler was changed to interleave direct split and collection-state I/O families; its first five results and prior scheduler hash are frozen in `campaign/stage5-state.json` and `campaign/stage5-progress.json`. The 80-trial run resumed from trial 6 without rerunning completed trials.

As a supplemental original cluster workload, `ShardSplitTest#testSplitStaticIndexReplication` ran unchanged with its embedded ZooKeeper and multiple Jetty nodes. Its [healthy-04](supplemental/shardsplit/healthy-04/run.json) completed `ran=1, ignored=0, failures=0`. The first three setup attempts exposed missing release/test classpath entries (Solr analysis extras, `NvlValueSourceParser`, and `DebugAgg`); these are excluded from fault counts. The repaired run recorded 2,692 ZooKeeper I/O events and two shard1 target checks, with the same ephemeral owner on both live-node reads. It did not enter the SOLR-15/16 final guards. The test restarts a Jetty only after the split, so this healthy run does not establish the leader-loss window between the two reads.

The unchanged original `ShardSplitTest#testSplitWithChaosMonkey` also completed [chaos-01](supplemental/shardsplit/chaos-01/run.json), [chaos-02](supplemental/shardsplit/chaos-02/run.json), and [chaos-03](supplemental/shardsplit/chaos-03/run.json), with different JUnit random seeds, each `ran=1, ignored=0, failures=0` (64.444, 48.465, and 64.441 seconds). Its watcher did stop the parent leader during the split, but all three executions recorded the same ephemeral owner on the two `/live_nodes` reads; SOLR-14's first guard and the line 524 outer guard each executed once, while the SOLR-15/16 final guards remained absent. The first two traces share 58 exact observed ZK I/O selectors between the two reads. [chaos-plan-01](supplemental/shardsplit/chaos-plan-01-selection.json) selects an original `ZkShardTerms.refreshTerms#getData` before the second read, verified at the same selector in all three healthy traces, for a bounded one-shot exception trial. This supplemental test's own leader stop is part of its baseline, so an exception observed in its healthy execution would not be a novel injected-fault result.

The first supplemental [fault trial](supplemental/shardsplit/chaos-fault-01/run.json) matched and applied its sole `ConnectionLoss` at that exact `ZkShardTerms.refreshTerms#getData` selector. It did not reach the second live-node check after the fault; the original JUnit failed while the sub-shard core creation and restart failed. This is a target-lost trial, with zero selected target exceptions, and is excluded from any bug claim. A second selected original I/O, `ShardLeaderElectionContext.waitForReplicasToComeUp#getChildren`, is [documented](supplemental/shardsplit/chaos-plan-02-selection.json); its caller catches `KeeperException` and retries after 500 ms, making it a better bounded timing perturbation candidate. The generic ZK probe records exact logical ZK path and call site, but has no physical Jetty-node field for this asynchronous callback, so a strict match proves the logical operation identity rather than a specific replica identity. This supplemental test's own leader stop is part of its baseline, so an exception observed in its healthy execution would not be a novel injected-fault result.

The second supplemental [fault trial](supplemental/shardsplit/chaos-fault-02/run.json) applied exactly one `ConnectionLoss` at the retryable `getChildren` point and the unchanged original JUnit passed. The line 524 outer guard executed after the fault, but its condition remained false and neither final guard nor target throw executed. Its actual trace then observed another call to the same site/path at `hitOrdinal=2`; [chaos-plan-03](supplemental/shardsplit/chaos-plan-03-selection.json) adds a second ordered fault at that newly exposed call. This is an incremental sequence mutation from an observed target-path-preserving run, with no change to the original test body.

The third supplemental [fault trial](supplemental/shardsplit/chaos-fault-03/run.json) applied both ordered `getChildren` exceptions exactly. The line 524 outer guard still executed after the second fault, with neither final guard nor selected throw. Original JUnit reported three failures while Jetty restart repeatedly logged a bound-port problem; this is not a selected target exception. The trace exposed a third retry-loop call, so [chaos-plan-04](supplemental/shardsplit/chaos-plan-04-selection.json) appends one more ordered exception and remains a bounded target-window experiment.

The fourth supplemental [fault trial](supplemental/shardsplit/chaos-fault-04/run.json) applied all three ordered `getChildren` exceptions exactly and the unchanged original JUnit passed. The line 524 outer guard still executed after the faults, with no final guard or target throw. The trace exposed `hitOrdinal=4`; [chaos-plan-05](supplemental/shardsplit/chaos-plan-05-selection.json) adds it as a fourth ordered fault. Each child was generated only after its predecessor's actual I/O appeared; no previously completed sequence was replayed as a new trial.

The fifth supplemental [fault trial](supplemental/shardsplit/chaos-fault-05/run.json) applied all four ordered retry-loop exceptions exactly; original JUnit passed, but the line 524 outer guard again took its nonfatal path. I stopped this same I/O family after the four-fault child because it repeatedly delayed sub-shard election without revealing either final target branch. The watcher that stops the leader depends on sub-shard progress, so delaying that progress also delays the test's node stop; increasing this identical retry count has weak evidence of moving the stop into the selected leader-read window. Other native ZooKeeper I/O and timing faults remain untested.

At the first wider-campaign coverage audit, 49 trials had completed and six strict trials preserved the shard1 target path. A union of those six JaCoCo execution files with the two healthy seeds, analyzed against the original Solr and Lucene release JARs, covered 5,362 production methods and 6,959 production branch outcomes; the healthy seeds covered 5,360 methods and 6,939 branch outcomes. The verified gains are therefore two production methods and 20 branch outcomes, separate from the fuzzer's 45 new production probe identifiers. The [machine-readable audit](campaign/production-coverage-audit.json) lists the included trial numbers.

The completed entry-level campaign ran 80 trials, 79 with exact applied injection. Ten strict trials retained the shard1 outer check after the last fault, five retained SOLR-14's first check, and none entered SOLR-15/16's final guards or selected throws. The final original-release JaCoCo union for those ten strict target-preserving trials added two production methods and 23 branch outcomes over the two healthy seeds. The earlier six-trial figure above is retained as a checkpoint history; the linked machine-readable audit now contains the final 80-trial recount.

Fault-model limit: the frozen ASM agent throws at entry to selected `SolrZkClient` I/O methods. In original Solr 8.11.4, those methods call `ZkCmdExecutor.retryOperation` around the lower-level `keeper.*` call when `retryOnConnLoss=true`. Thus the main trials test an exception crossing the application-level `SolrZkClient` boundary and bypass that method's internal retry. They do not establish the outcome of one transient failure at the underlying ZooKeeper operation. The supplemental `ShardLeaderElectionContext.waitForReplicasToComeUp#getChildren` caller has its own catch-and-retry loop, which the observed ordered sequence exercises. Neither a negative result from this campaign nor 80 completed trials alone closes the lower-level retry fault space.

## Independent retry-internal follow-up

A second, separately frozen case-local ASM agent instruments the original `SolrZkClient` `exists`, `getData`, `getChildren`, and `setData` lambda bodies used by `ZkCmdExecutor.retryOperation`. Its `ConnectionLossException` is thrown from inside the callable that Solr itself retries. The prior JAR and its checkpoint are unchanged. The new build uses original release classes and JaCoCo without GraphChecker, a static skeleton, or a modified test body; its source and JAR hashes are stored in `native/build.json` on node2.

Two original `SplitShardTest#doTest` healthy runs passed in 21.199 and 20.377 seconds. They observed 72 common strict selectors across 27 I/O families before the shard1 outer guard. An exact one-fault calibration at the first `/live_nodes/PARENT_LEADER` `exists` lambda applied at event 306, and the same native call immediately reappeared at event 307 with the next hit ordinal and thread ID; [the machine-readable audit](native/calibration/audit.json) checks these identities. The original JUnit passed in 25.646 seconds and reached the line 165 and line 524 checks after the fault; no selected target exception occurred. This confirms that the new injection actually exercises Solr's internal retry path. The native fuzzer has its own `native/campaign/state.json` checkpoint and the same observed-I/O/production-JaCoCo feedback. It completed 48 trials with up to eight ordered faults; because trial 48 added two original production branch outcomes, the same checkpoint was extended to 80 trials and up to ten faults without repeating 1–48.

An initial no-fault run of the unchanged multi-node nightly `ShardSplitTest#testSplitWithChaosMonkey` under the new native probe failed its original JUnit gate (`ran=1, ignored=0, failures=3`) while the restarted Jetty reported an address-in-use error. This is a failed calibration, not an injected result or a selected target exception. The earlier unchanged test passed three times under the original case-local probe. We will only use native multi-node fault trials if a later no-fault run passes and produces stable selectors.

Two later no-fault native-probe runs of that unchanged multi-node test did pass the exact original JUnit gate, in 61.497 and 76.613 seconds, with one shard1 first check and one outer check each. Their exact second `/live_nodes/PARENT_LEADER` `exists` selector matched despite different physical Jetty ports. The physical addresses are stored separately in [the selector evidence](supplemental/shardsplit/native-chaos-plan-01-selection.json). We used that stable selector for a one-shot native `ConnectionLoss` test before the outer guard; its result is being audited separately from the main 48-trial queue.

The first native multi-node fault trial applied one exact retry-internal `ConnectionLoss` at that second live-node read. The unchanged original JUnit passed in 75.920 seconds, the line 524 outer guard executed after the fault, and the selected line 536/539 guards and 538/543 throws did not execute. The [trial audit](supplemental/shardsplit/native-chaos-fault-01/audit.json) also records the physical live-node path. Its trace exposed a same-thread second attempt at the identical logical read before line 524, so [a two-fault child sequence](supplemental/shardsplit/native-chaos-plan-02-selection.json) adds only that observed retry. This is separate from the 48-trial single-node native queue.

The two-fault child reached SOLR-15's exact line 536 guard and line 538 `SolrException` once after both strict faults; original JUnit passed in 110.931 seconds. Replaying the same ordered sequence under the same original JUnit and random seed reproduced the exact target throw and also passed in 80.667 seconds. In both executions, the first read of the parent leader's live znode returned an ephemeral owner and the second returned `null` after the original test's monkey stopped that parent leader. The original command marks both child shards `RECOVERY_FAILED` before deliberately throwing; both state updates and failed split status appear in the logs. The unchanged original test explicitly allows the split to fail under its node stop, then unconditionally checks shard consistency and equal control/cloud document counts. The [source and replay review](supplemental/shardsplit/solr15-native-candidate-source-review.json) therefore classifies this reproducible target exception as an expected protective abort, **not a new bug**. SOLR-14's first-read null branch and SOLR-16's changed-owner branch remain unexercised.

For this same unchanged multi-node JUnit, an [original-release JaCoCo union](supplemental/shardsplit/native-chaos-coverage-audit.json) across two passing healthy runs measured 9,712 covered production methods and 14,910 branch outcomes. The one-fault run added 12 methods and 21 branch outcomes; the two-fault run added a further nine methods and 57 branch outcomes. Thus the faults exposed 21 new production methods and 78 branch outcomes relative to those healthy seeds, including the reviewed SOLR-15 abort path. The replay is verification and is not counted again as a distinct coverage-gain trial.

An interim original-release JaCoCo union at 10 strict target-preserving v1 trials and eight native trials, plus the native retry calibration, measured 5,439 covered production methods and 7,105 branch outcomes in the four healthy seeds. The v1 trials added two methods and 21 branch outcomes; the native phase then added four methods and ten branch outcomes, for six methods and 31 branch outcomes combined. This audit reads the original Solr/Lucene release JARs and excludes test classes. The counts are a moving checkpoint, not final coverage figures; `audit_all_coverage.py` will rerun them at campaign completion.

The final native retry campaign completed 80 distinct trials, all with exact ordered injection; 78 preserved the shard1 outer check after the last fault and 14 reached SOLR-14's first guard afterward. No single-node trial reached the SOLR-15/16 final guards or selected throws. The first faults spanned 26 I/O families, and sequence depth reached six faults. Trials 61–80 added no new production probes or I/O families, so this particular queue was stopped at its budget. The 80 trial numbers are unique and contiguous in [the resumable checkpoint](native/campaign/state.json); the per-trial plans and outcomes remain on node2, with compact copies under `native/campaign/trials/` here.

The [final original-release JaCoCo union](native/campaign/production-coverage-audit.json) uses four passing healthy seeds, ten strict target-preserving entry-level trials, the native retry calibration, and 78 strict target-preserving native trials. It covered 5,439 production methods and 7,105 branch outcomes in the healthy seeds. Entry-level faults added two methods and 21 branch outcomes; native retry faults then added five methods and 15 branch outcomes, for a combined gain of seven methods and 36 branch outcomes. The unchanged multi-node chaos test has its own separate baseline and coverage union above and is not added to this count.

The release-JAR union is conservative: ASM changes the runtime bytecode identity of `SplitShardCmd` and `SolrZkClient`, so JaCoCo data for those two classes cannot be matched to their original JAR bytes. Their exact target checks and I/O outcomes are counted from the case-local trace instead. The reported production method and branch gains therefore exclude probe-only synthetic branches and may undercount production behavior in the two woven classes. SOLR-14's first-read-null branch and SOLR-16's later ephemeral-owner-change branch remain unobserved; no negative conclusion is drawn for those two checks.

The original chaos test also has a specific timing limit. Its monkey waits until the child shard has more than one replica before stopping the parent leader (`ShardSplitTest.java:449–460`); `SplitShardCmd` performs SOLR-14's first parent live-znode read before it creates those children (`SplitShardCmd.java:164–169`). Its parent Jetty restart occurs only after the split request returns or aborts (`ShardSplitTest.java:491–506`). Therefore that original workload does not itself provide either an early parent stop before SOLR-14's first read or a parent restart between the first and second reads for SOLR-16. The exception-only native faults did not supply those events. This explains why the two branch outcomes remain an explicit workload/fault-window gap despite the completed budgets.
