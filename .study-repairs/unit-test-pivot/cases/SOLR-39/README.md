# SOLR-39: routed-alias coordination check

- System: Solr 8.11.4, clean source commit `e27f44e`.
- Selected site: `solr/core/src/java/org/apache/solr/update/processor/RoutedAliasUpdateProcessor.java:247`, `RoutedAliasUpdateProcessor.lookupShardLeadersOfCollections`.
- Selected condition: `if (collections == null)` raises `newAliasMustExistException`. The method reads the alias-to-collections mapping while routing an update; the original test creates, modifies, and uses the alias.
- Original workload: unchanged `TimeRoutedAliasUpdateProcessorTest.test`, inherited from `RoutedAliasUpdateProcessorTest` / `SolrCloudTestCase`. It starts four embedded Jetty Solr nodes and ZooKeeper, creates a time-routed alias, indexes across its collections, changes alias membership, and checks routing. It intentionally expects errors for an old and a future-dated document; those are not this target oracle.

## Healthy reach and runtime configuration

The inherited abstract test class has `@AwaitsFix(SOLR-13696)`. With Lucene's default `tests.awaitsfix=false`, JUnit reports `run=1, failures=0` but skips the entire workload through an assumption. The independent runner sets `-Dtests.awaitsfix=true` and the source's `-Dsolr.disableConfigSetsCreateAuthChecks=true` compatibility flag so this unchanged original test can clone its `_default` configset. The real uninstrumented JUnit passed in 26.984 seconds; the instrumented healthy seed passed in 28.025 seconds and reached this exact guard **4 times**, always on its nonthrowing branch. The initial skipped and configset-failed attempts were setup diagnostics and are not campaign trials.

## Fault campaign

The three checks share one case-isolated run directory, `cases/SOLR-10/work`, and one original JUnit execution per fault sequence. `probe/weave.py` adds only target markers and six `SolrZkClient` method hooks; the fault is `KeeperException.ConnectionLossException` at an exact observed operation, ZooKeeper path, and hit ordinal. Traces include stable production callsites. No causal graph or Docker cluster is used. The sampled relevant I/O includes `/aliases.json`, routed-alias collection state and properties, and Overseer control paths; no full HTTP or filesystem interception is claimed.

The queue starts from the healthy trace and mutates only fault sequences observed in a real run. JaCoCo production probe coverage and stable callsite-operation-resource I/O novelty guide additional sequences. A trial contributes feedback for **this check** only if all requested faults matched and applied in order, and this check executed after the final fault. The base budget is 80 trials with at most eight ordered faults; if trials 73–80 retain a target and add production coverage or stable I/O behavior, the same checkpoint expands to 128 trials and ten faults. `result.json` separately records this check's post-fault reach, coverage, exception candidates, and elapsed time. The three result files show the same shared campaign elapsed time; these values are not additive.

The campaign and automatic restart supervisor ran in tmux session `solr103940-campaign`; `solr103940-sync` refreshed the 102-check table.
