# HBASE-32 `testLotsOfRegionReplicas` r003: independent timeout review

Status: **candidate requiring a clean longer replay**, not a confirmed new bug. This review reads the original run only; it did not run or change the campaign. Source inspected is HBase 2.6.6 checkout `d5f63f523c` in `/users/ZhenyuLi/.graphchecker-sources/hbase-2.6.6`.

## Exact trigger and workload

The original unmodified `TestRegionReplicaFailover#testLotsOfRegionReplicas` starts a three-RegionServer MiniHBaseCluster in `@BeforeEach` and creates a table with `NB_SERVERS * 20 = 60` regions and ten replicas (`TestRegionReplicaFailover.java:64,80-87,315-326`). It then reads from those replicas. `actor-healthy.log` ends with `HBASE32 JUNIT found=1 succeeded=1 failed=0`; the healthy run took 60.13 seconds, and its create-table procedure completed all 600 region-assignment children.

r003 uses one selector, `RPC_FLUSH_REGION~dGVzdExvdHNPZlJlZ2lvblJlcGxpMix02lw~replica-1~target-1~rpc-1~FlushRegionCallable.call:81~DO_NOT_RETRY_IOEXCEPTION`. In `work-lots/logs/r003.log:11865-11885`, the RPC reports `FAULT_MATCHED` and `FAULT_APPLIED` at sequence 211, then `TARGET_GUARD` at 213 and `TARGET_B7_RETHROW` at 217. These carry the same complete `raw_primary_region` and `replica_id=1`; this is an exact target hit, not a nearby exception. The `RegionReplicaFlushHandler.java:128-138` catch returns only for `TableNotFoundException` or a disabled table and otherwise rethrows. `handleException` at lines 80-93 then aborts its RegionServer for this IOException. The first abort at `r003.log:11941` is consequently the expected source-level response to the injected exception. That RS (`ms1105...:45061`) carried `hbase:meta`, as the later server-crash log confirms.

## Why the test waited

`CreateTableProcedure.java:126-135` adds a child assignment procedure for every new region and advances to the enabled-table state only after those children finish. The original test's main thread waits in `HBaseAdmin$ProcedureFuture.waitProcedureResult` → `Admin.createTable` → `TestRegionReplicaFailover.java:326` in both `r003.thread-dump-1.txt:8577-8582` and `r003.thread-dump-2.txt:8807-8812`.

The faulted run completed only 197/600 assignment children, with the last success logged at 02:08:35.687, seconds after injection. At 02:13:28 the master still reported 403 regions in transition (`r003.log:23971`). Both pre-timeout dumps show many procedure workers retrying `hbase:meta` writes through `RegionStateStore.updateRegionLocation` and `RpcRetryingCallerImpl`; 25/30 worker stacks include `TransitRegionStateProcedure.openRegion` in the respective dumps. This is a recovery stall after the abort, not an ordinary continuation of the healthy 60-second test. The large 600-assignment workload may amplify the stall, and a 360-second ceiling alone cannot establish permanence.

More specifically, the aborted RS closed its ZooKeeper connection at 02:08:47 (`r003.log:14103`); `RegionServerTracker` observed its ephemeral znode deletion and entered `ServerManager.expireServer` at 02:08:47 (`r003.log:14099-14100`). Yet the first `ServerCrashProcedure` for that server was logged only at 02:14:25 (`r003.log:32348`), after the timeout initiated shutdown. In both pre-timeout dumps, the same `RegionServerTracker-0` thread waits at `AssignmentManager.submitServerCrash:1980` for that server's `ServerStateNode.writeLock` (`thread-dump-1.txt:3556-3574`, `thread-dump-2.txt:3764-3782`). The source uses this write lock to fence `reportRegionStateTransition` before scheduling the crash procedure (`AssignmentManager.java:1976-1984`). Two master RPC write handlers in both dumps are inside `reportRegionStateTransition`, waiting for `RegionStateNode.lock` (`thread-dump-1.txt:6340-6380`). `reportRegionStateTransition` holds a `ServerStateNode.readLock` across transition processing (`AssignmentManager.java:1256-1278`); `TransitRegionStateProcedure.beforeExec/afterExec` holds a `RegionStateNode` lock around `regionOpening` and its `hbase:meta` write (`TransitRegionStateProcedure.java:394-404`, `AssignmentManager.java:2176-2182`). This suggests a lock-wait chain that delays meta recovery, but the original `jcmd Thread.print` dumps do **not** show ownable-synchronizer ownership or identify which server each in-flight report belongs to. They do not prove a closed deadlock cycle or its permanence.

[HBASE-21508](https://issues.apache.org/jira/browse/HBASE-21508) is already fixed in HBase 2.2.0 and concerns a race between server-crash processing and a late transition report from a dead RS, potentially assigning one region twice. Its [v4 patch](https://issues.apache.org/jira/secure/attachment/12949445/HBASE-21508-v4.patch) introduced the read/write fencing that remains in this 2.6.6 source. The present observation is a possible **wait involving that fencing**, not evidence that HBASE-21508 recurred. The source comment at `AssignmentManager.java:1252-1255` explicitly warns about deadlocking on the meta region if transition reports are serialized with an exclusive server lock; the current read lock addresses that older concern, but these dumps cannot yet show whether a different cycle exists here.

The run's 360-second timeout sent SIGTERM at 02:14:01 (`r003.log:25199`). Two other RS aborts at 02:14:11/14 and their `LocalConnectionClosedException` guards occur during shutdown cleanup; they are not evidence that the one-fault cluster exhausted its tolerance before timeout. The original run exited 124 with no final JUnit result.

## Minimal clean replay and decision rule

On an otherwise free cluster slot, rerun the **same compiled HBase 2.6.6 JAR and agent**, unchanged original JUnit method, exactly the one saved fault selector, fresh `HBASE32_RUN_ROOT`, and `HBASE32_RUN_TIMEOUT=600`. Keep replay artifacts separate from the fuzz checkpoint and verify agent/JAR hashes against `work-lots/replay-r003-plan.json`. The existing `work/run.sh run replay-r003 '<selector>'` accepts these environment variables; `work-lots/replay.py` prepares this isolated replay. Sample `jcmd <pid> Thread.print -l` before shutdown (for example at 200, 300, and 500 seconds) and preserve raw logs, JaCoCo exec, exit code, and all dumps. `-l` adds ownable synchronizers; Java read-lock ownership and the specific report server may still need targeted instrumentation if the chain persists.

For each replay, verify fault/guard/B7 full raw-region identity, pre-shutdown live RS count, first SCP scheduling time for the aborted meta RS, new meta location, progress of pid 20's 600 child assignments, and original JUnit outcome. If the 600-second replay completes, classify r003 as a slow recovery/short timeout. If it remains stuck with a live master and two RSs, independently repeat once and inspect lock ownership/report identities before calling a new coordination bug. Do not count timeout-cleanup aborts as injected faults or as pre-timeout cluster failure.
