# HBASE-32 `testLotsOfRegionReplicas` r003: independent timeout review

Status: **the identical-plan longer replay passed; r003 is not a confirmed bug**. This review only reads the original run and independent replay; it did not run or change the campaign. Source inspected is HBase 2.6.6 checkout `d5f63f523c` in `/users/ZhenyuLi/.graphchecker-sources/hbase-2.6.6`.

## Exact trigger and workload

The original unmodified `TestRegionReplicaFailover#testLotsOfRegionReplicas` starts a three-RegionServer MiniHBaseCluster in `@BeforeEach` and creates a table with `NB_SERVERS * 20 = 60` regions and ten replicas (`TestRegionReplicaFailover.java:64,80-87,315-326`). It then reads from those replicas. `actor-healthy.log` ends with `HBASE32 JUNIT found=1 succeeded=1 failed=0`; the healthy run took 60.13 seconds, and its create-table procedure completed all 600 region-assignment children.

r003 uses one selector, `RPC_FLUSH_REGION~dGVzdExvdHNPZlJlZ2lvblJlcGxpMix02lw~replica-1~target-1~rpc-1~FlushRegionCallable.call:81~DO_NOT_RETRY_IOEXCEPTION`. In `work-lots/logs/r003.log:11865-11885`, the RPC reports `FAULT_MATCHED` and `FAULT_APPLIED` at sequence 211, then `TARGET_GUARD` at 213 and `TARGET_B7_RETHROW` at 217. These carry the same complete `raw_primary_region` and `replica_id=1`; this is an exact target hit, not a nearby exception. The `RegionReplicaFlushHandler.java:128-138` catch returns only for `TableNotFoundException` or a disabled table and otherwise rethrows. `handleException` at lines 80-93 then aborts its RegionServer for this IOException. The first abort at `r003.log:11941` is consequently the expected source-level response to the injected exception. That RS (`ms1105...:45061`) carried `hbase:meta`, as the later server-crash log confirms.

## Why the test waited

`CreateTableProcedure.java:126-135` adds a child assignment procedure for every new region and advances to the enabled-table state only after those children finish. The original test's main thread waits in `HBaseAdmin$ProcedureFuture.waitProcedureResult` → `Admin.createTable` → `TestRegionReplicaFailover.java:326` in both `r003.thread-dump-1.txt:8577-8582` and `r003.thread-dump-2.txt:8807-8812`.

The faulted run completed only 197/600 assignment children, with the last success logged at 02:08:35.687, seconds after injection. At 02:13:28 the master still reported 403 regions in transition (`r003.log:23971`). Both pre-timeout dumps show many procedure workers retrying `hbase:meta` writes through `RegionStateStore.updateRegionLocation` and `RpcRetryingCallerImpl`; 25/30 worker stacks include `TransitRegionStateProcedure.openRegion` in the respective dumps. This is a recovery stall after the abort, not an ordinary continuation of the healthy 60-second test. The large 600-assignment workload may amplify the stall, and a 360-second ceiling alone cannot establish permanence.

More specifically, the aborted RS closed its ZooKeeper connection at 02:08:47 (`r003.log:14103`); `RegionServerTracker` observed its ephemeral znode deletion and entered `ServerManager.expireServer` at 02:08:47 (`r003.log:14099-14100`). Yet the first `ServerCrashProcedure` for that server was logged only at 02:14:25 (`r003.log:32348`), after the timeout initiated shutdown. In both pre-timeout dumps, the same `RegionServerTracker-0` thread waits at `AssignmentManager.submitServerCrash:1980` for that server's `ServerStateNode.writeLock` (`thread-dump-1.txt:3556-3574`, `thread-dump-2.txt:3764-3782`). The source uses this write lock to fence `reportRegionStateTransition` before scheduling the crash procedure (`AssignmentManager.java:1976-1984`). Two master RPC write handlers in both dumps are inside `reportRegionStateTransition`, waiting for `RegionStateNode.lock` (`thread-dump-1.txt:6340-6380`). `reportRegionStateTransition` holds a `ServerStateNode.readLock` across transition processing (`AssignmentManager.java:1256-1278`); `TransitRegionStateProcedure.beforeExec/afterExec` holds a `RegionStateNode` lock around `regionOpening` and its `hbase:meta` write (`TransitRegionStateProcedure.java:394-404`, `AssignmentManager.java:2176-2182`). This suggests a lock-wait chain that delays meta recovery, but the original `jcmd Thread.print` dumps do **not** show ownable-synchronizer ownership or identify which server each in-flight report belongs to. They do not prove a closed deadlock cycle or its permanence.

[HBASE-21508](https://issues.apache.org/jira/browse/HBASE-21508) is already fixed in HBase 2.2.0 and concerns a race between server-crash processing and a late transition report from a dead RS, potentially assigning one region twice. Its [v4 patch](https://issues.apache.org/jira/secure/attachment/12949445/HBASE-21508-v4.patch) introduced the read/write fencing that remains in this 2.6.6 source. The present observation is a possible **wait involving that fencing**, not evidence that HBASE-21508 recurred. The source comment at `AssignmentManager.java:1252-1255` explicitly warns about deadlocking on the meta region if transition reports are serialized with an exclusive server lock; the current read lock addresses that older concern, but these dumps cannot yet show whether a different cycle exists here.

The run's 360-second timeout sent SIGTERM at 02:14:01 (`r003.log:25199`). Two other RS aborts at 02:14:11/14 and their `LocalConnectionClosedException` guards occur during shutdown cleanup; they are not evidence that the one-fault cluster exhausted its tolerance before timeout. The original run exited 124 with no final JUnit result.

## Clean replay outcome

The owner reran the **same compiled HBase 2.6.6 JAR and agent**, unchanged original JUnit method, exactly the one saved fault selector, fresh run root, and a 600-second ceiling on node2. The saved `work-lots/logs/replay-r003.summary.json` verifies the agent/JAR hashes against `replay-r003-plan.json`. I also checked the raw replay log: `FAULT_APPLIED` at line 11873, the same complete raw primary-region name in `TARGET_GUARD` at 11874 and `TARGET_B7_RETHROW` at 11875, `ServerCrashProcedure` for the aborted meta-hosting RS at 12709, and `CreateTableProcedure` success at 29274. All 600 child assignments completed, and the original JUnit reported `found=1 succeeded=1 failed=0` at line 41723. The replay exited 0 after 77.58 seconds. Only the one intended RS aborted before test completion.

Thus the exact fault can recover normally; the original 360-second stall is nondeterministic. Its source and thread evidence remain useful for diagnosing a possible intermittent wait, but **the observed 124 timeout is not sufficient to mark a new bug**. A separate same-plan replay that again stalls, including `Thread.print -l` before timeout and actor identity for the in-flight transition reports, would be needed to establish reproducibility and a closed lock cycle. Do not count timeout-cleanup aborts as injected faults or as pre-timeout cluster failure.

## r011: a distinct-plan timeout with the same wait pattern

The node1 campaign later tested a different single-fault selector, `RPC_FLUSH_REGION~dGVzdExvdHNPZlJlZ2lvblJlcGxpMix3BD8~replica-1~target-1~rpc-1~FlushRegionCallable.call:81~DO_NOT_RETRY_IOEXCEPTION`. In `work-lots/logs/r011.log:7073,7077,7097`, `FAULT_APPLIED`, `TARGET_GUARD`, and `TARGET_B7_RETHROW` share the complete raw primary-region identity and replica 1. The injected exception caused the intended meta-hosting RS (`ms1105...:37931`) to abort at line 7145. Its ZooKeeper ephemeral znode was deleted and expiration began at 02:25:09 (`r011.log:7839-7840`). `CreateTableProcedure` pid 20 had entered `CREATE_TABLE_ASSIGN_REGIONS` at line 2710. Only 72 of its 600 child assignments finished before shutdown; the last success was line 7283 at 02:24:57.639. At 02:29:50 the master still reported 528 regions scheduled to transit (`r011.log:16622`), and the JUnit main thread remained in `Admin.createTable` at original test line 326 (`r011.thread-dump-2.txt:9811`).

Three pre-shutdown `jcmd Thread.print -l` samples (`r011.thread-dump-live.txt`, `r011.thread-dump-2.txt`, and `r011.thread-dump-3-pretimeout.txt`) show the *same* lock objects and waiters throughout. `RegionServerTracker-0` waits in `AssignmentManager.submitServerCrash:1980` for `ServerStateNode.writeLock` AQS object `0x00000007bd949328` (`r011.thread-dump-2.txt:3449-3468`). Master RPC handlers #314 and #313 wait in `reportRegionStateTransition` for `RegionStateNode.lock` objects `0x00000007bd8e8130` and `0x00000007bd8e53e0` (`r011.thread-dump-2.txt:6907-6953`). The `-l` ownership section maps those two region locks to `PEWorker-7` and `PEWorker-2`, respectively. Both workers are retrying `hbase:meta` writes inside `RegionRemoteProcedureBase.execute:323` → `AssignmentManager.persistToMeta:2290` → `RegionStateStore.updateRegionLocation:203/238` → `HTable.put` → `RpcRetryingCallerImpl.callWithRetries:184`. This establishes the region-lock half of a persistent wait chain, not a closed deadlock cycle.

The RS-side log at `r011.log:7719,7738,7757` shows timed-out `ReportRegionStateTransition` calls with `server { port: 37931 start_code: 1791339880121 }` and CLOSED transitions, so reports from the aborted meta RS were outstanding. The raw master log and `Thread.print -l` do **not** tie those particular requests to handlers #314/#313, and Java's shared `ReentrantReadWriteLock` read holders do not appear in the ownable-synchronizer listing. Thus we cannot establish that either stalled handler holds the **aborted server's** read lock that blocks its SCP write lock. `Thread.print -l` also does not tell how long the meta retry would otherwise last. A minimal diagnostic replay can add case-local master-side logs in `AssignmentManager.reportRegionStateTransition` around `serverNode.readLock().lock()` and its `finally` release (`AssignmentManager.java:1256,1277-1278`): include monotonic time, thread ID/name, `serverName`, `System.identityHashCode(serverNode)`, the first transition's region/transition code/proc ID, and an enter/acquired/released phase. Add matching before/acquired/released logs around `submitServerCrash`'s `serverNode.writeLock().lock()` (`AssignmentManager.java:1980`) with the same node identity and server name. This keeps the original JUnit method and fault plan intact while supplying the missing actor and lock correlation; diagnostic logging itself may alter timing, so retain the uninstrumented replay as the outcome test.

`r011.exit=124`; GNU `timeout` and JVM cleanup consumed 406.65 seconds in total (`r011.log:17841` begins the shutdown hook at 02:30:23; `r011.log:23510` first schedules the meta RS SCP at 02:30:47, **after** shutdown began). The other two RS aborts at lines 18416 and 26360 followed the shutdown hook and are cleanup effects, not additional injected faults. A node1 resource spot check reported a load average around 4.4 on 16 cores, about 57 GiB available memory, and zero swap use; a later spot check after r011 showed load 7.49/5.08/4.35 and the same free memory. This does not suggest gross CPU or memory exhaustion, but it is not continuous telemetry for the stalled interval.

The owner then reran r011's **identical saved selector** in a fresh node2 root with the same compiled agent and HBase server JAR and a 600-second ceiling. `work-lots/logs/replay-r011.summary.json` records `fully_applied=true`, one same-actor guard and B7, one pre-shutdown RS abort, 600 successful child assignments, `exit=0`, and original JUnit `found=1 succeeded=1 failed=0` in 76.97 seconds. The raw log agrees: `FAULT_APPLIED` at line 9099, exact same raw region within this replay's `TARGET_GUARD` and `TARGET_B7_RETHROW` at lines 9105/9133, intended RS abort at 9241, prompt meta-hosting RS SCP at 10761, pid 20 create-table success at 31104, and JUnit pass at 41412. The per-run region ID differs between node1 and node2, as expected from a fresh test root; the saved selector and within-run runtime identity match.

**Current classification:** r003 and r011 are two different exact one-fault plans that each stalled for 360 seconds on node1, then each passed an independent clean same-plan replay on node2 in about 77 seconds. They show a scheduling-sensitive recovery stall worth investigating, with a stable *partial* lock wait chain, but **no reproducible fatal outcome or proven closed deadlock cycle**. Do not mark either as a new bug. If further investigation is budgeted, run at least one repeated uninstrumented same-plan trial on node1 under isolated resources and correlate the report-server read-lock actors using the narrow diagnostic logging above; a longer timeout alone has not established an invariant failure.
