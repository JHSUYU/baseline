# HBASE-32 B7 upstream I/O scope audit

Date: 2026-10-07 UTC. System: HBase 2.6.6, unchanged `TestRegionReplicaFailover.testLotsOfRegionReplicas`, 3 RegionServers, 60 regions with 10 replicas. Target: `RegionReplicaFlushHandler.triggerFlushInPrimaryRegion` line 136 (`throw ex`). This audit is source plus healthy-run evidence; it does not count other I/O families as fault tested.

## Evidence and exact scope

The original healthy log is `work-lots/logs/actor-healthy.log` on node1. It contains 542 `HBASE32 TARGET_ENTER` lines, 555 `HBASE32 IO seq=` lines, no B7 rethrow, and an original JUnit pass. For the actual 60-region test table (`testLotsOfRegionRepli2`) it contains 540 target entries, 552 client flush-RPC probe records, and 552 server `RSRpcServices: Flushing` records. For example, target region entry at line 4938 and the first flush RPC at lines 1655–1656 (the latter two belong to the test fixture's earlier table). The server flush records for that earlier region are at lines 1659–1660. The exact instrumented event is the invocation of `AdminService.flushRegion` in `FlushRegionCallable.call:81`, recorded immediately before the invoke; a recorded call is not itself proof that the server completed the operation.

The healthy log also contains HDFS NameNode audit entries for `testLotsOfRegionRepli2`: 6,063 `listStatus`, 3,366 `getfileinfo`, 370 `mkdirs`, 181 `create`, 181 `delete`, 61 `open`, 60 `rename`, and 60 `setTimes`. For example, the first table-path metadata operations are lines 1669–1672, and a `.tabledesc/.tableinfo` `open` is line 4845. These are *actual MiniCluster file-system requests*, but the aggregate includes table creation, region opening, and teardown. The existing log lacks per-request region/target context, so it cannot attribute every HDFS request to a particular B7 target.

The check is therefore **not covered across all related I/O** by the current campaign. JaCoCo for two production classes is feedback for the trials that were actually run, not evidence of the absence of other executable fault sites. The log counts are observational and should not be treated as independent causal-edge instrumentation.

## Independent supplemental phase, prepared design

Use a separate case-local agent/JUnit run directory and fresh healthy seed, queue, JaCoCo union, valid denominator, and result field. Keep the current main 80-effective flush-RPC campaign and its checkpoint untouched. The passive implementation is in `work-upstream`: it logs the actual Master stub invocation with server/procedure/attempt, distinguishes `ReversedClientScanner.next` (a logical attempt that can return cached data) from the lower `ClientService.scan` invocation, and distinguishes WAL flush-marker method entry from actual `wal.appendMarker` and optional `wal.sync` start/return. It logs the raw region, stable table/start-key, replica or flush action, and call ordinal. The fault-path `MetaTableAccessor.getTableState` hook is immediately before `Table.get(Get)`; no fault is injected during passive calibration. Add file HDFS operations only where a concrete region path can be mapped to the same target; start with WAL marker and region-open metadata, rather than all 10,000+ table-path requests.

After passive calibration, generate unique selectors only from events observed before or during a *specific target invocation* and preserve raw primary/secondary region, region replica ID, target ordinal, server actor and call ordinal in the trace. `META_SCAN_NEXT_ATTEMPT` is not by itself an RPC fault point; only the lower `META_SCAN_RPC` can be used as such. Apply one exception at a new source family per sequence; a second exception may target newly exposed `getTableState` `Get` or a recovery I/O. Because an IOException from that `Get` bypasses B7 line 136, classify it as a separate guard-path diagnostic, not as a B7-effective trial. Require full plan application, same exact postfault target identity, and B7 throw as a distinct outcome. Preserve raw logs and JaCoCo, mark target-lost/cluster-invalid outside the effective denominator, and enforce the same tolerance constraint used by the main campaign. Do not merge supplemental coverage or counts into current 80-effective result. Start with Master report and region-location/`hbase:meta` family because both are directly upstream of B7; WAL marker follows only after the passive run proves per-region occurrence and a safe exact injection point.

An implementation caveat: injecting before `stub.flushRegion` simulates a client-visible exception without executing the server operation. Server WAL/HFile fault tests must inject on the server side at a real append/sync/write and let HBase propagate the resulting exception. Otherwise they would only repeat the current RPC exception experiment.
