# HBASE-32 independent upstream passive calibration

The unchanged `TestRegionReplicaFailover.testLotsOfRegionReplicas` passed twice on node0. Both runs used an independent data directory and JaCoCo file; neither injected a fault. The raw logs, `.exec` files, and exit receipts are in `upstream-passive-healthies.tar.gz` (SHA-256 `346b61959ef9fdeaaeb80fdf39129acef4483562b23137e74578a5c81e4a4d82`). Structured summaries are `upstream-passive-healthy.json` and `upstream-passive-healthy2.json`. The first calibration exposed an instrumentation gap; the second fixed it and is authoritative for I/O family counts.

In healthy #2, all seven upstream classes were woven without `PROBE_FAILED`; the original target probe and independent target probe both recorded 542 invocations. The test table `testLotsOfRegionRepli2` accounts for 540 target invocations. The actual Master OPENED report callsite executed 600 times: 60 regions × 10 replicas, including the 540 secondary regions that invoke the target. Those records contain the raw secondary/primary names, replica ID, server name, procedure ID, and report attempt ordinal. A Master report fault can suppress or delay its region's target, so postfault target retention remains mandatory.

The primary flush path executed 540 `CANNOT_FLUSH` WAL marker attempts for the test table. All 540 reached `wal.appendMarker`, returned from it, reached `wal.sync`, and returned from it; all were under `RSRpcServices.flushRegion`. This confirms actual WAL I/O boundaries and the empty-memstore path in this original read-only JUnit. The passive marker records identify the raw primary region, action, ordinal and server RPC thread. The current calibration does **not** yet identify which concurrent secondary replica sent each primary flush RPC; a separate request-attribute actor tag has been prepared for a third healthy validation before these WAL points can count as strict same-replica trials.

`ConnectionImplementation.locateRegionInMeta` executed 311 logical `ReversedClientScanner.next` calls on the target thread for the test table. The lower `ClientService.scan` hook recorded 1,021 actual RPC invocations with a scan start row matching that table: 529 OPEN, 1 NEXT, and 491 CLOSE. All 529 OPEN and the 1 NEXT occurred on threads without the target's `ThreadLocal` identity. Of the CLOSE calls, 308 remained on a target thread and 183 were unlinked. This explains why healthy #1, which required a target-thread stack to log the lower RPC, misleadingly recorded only CLOSE. A table/start-key match is not enough to attribute an asynchronous OPEN/NEXT to a particular replica and target invocation; these unlinked calls remain excluded from precise injection selection until context propagation is validated.

The healthy target had zero `MetaTableAccessor.getTableState` `Table.get` attempts and zero lower `ClientService.get` calls from that path. The separate one-DNR diagnostic is intended to establish whether this guard-dependent I/O appears after the flush exception; it is outside every fuzz budget and does not establish a new bug by itself.

The supplemental injection phase will maintain a fresh checkpoint, trial IDs, coverage union, and effective denominator. It can select exact Master OPENED report events. WAL append/sync selection requires the third healthy actor-tag validation. The current 80-effective flush-RPC campaign remains separate. HDFS table-path operations and asynchronous meta-scan OPEN/NEXT are observed but lack per-target identity in this calibration and are not counted as covered fault sites.
