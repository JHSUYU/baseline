# HBASE-31: region-server start-code guard

- Target: HBase 2.6.6 `RSRpcServices.throwOnWrongStartCode(long)` at `RSRpcServices.java:2008–2015`. A mismatch throws `ServiceException` whose cause is `DoNotRetryIOException` with the different-server start-code message.
- Original embedded-cluster JUnit: `org.apache.hadoop.hbase.regionserver.TestRegionMove.testDisableAndMove` (two region servers). A case-local ByteBuddy healthy probe records the guard only during the test and on Open/Close/ExecuteProcedures requests mentioning the test table. One passing 43.01-second run evaluated the guard 14 times with equal requested and actual start codes. Two startup calls outside the test are excluded.
- The independent healthy hook is in `independent/src/HBase31Probe.java`; its runtime evidence is `node1:.../HBASE-31/independent/healthy.log`. It uses no GraphChecker skeleton, woven classes, or runtime JAR.
- Fault executions are shared with the new HBASE-12 original-JUnit campaign, whose combined case-local agent records this guard alongside exact request/response I/O fault identity and JaCoCo production coverage. HBASE-31 must have its own target-after-fault classification and per-trial ledger. An exception caused directly by an injected I/O fault is not the target oracle: the guard itself must observe a mismatched start code and throw the exact exception.
- The source passes a region server's start code in RS open/close requests. Under an exception-only fault model without a region-server restart, a mismatch may remain unreachable; all target-retaining trials and their elapsed times still need to be recorded before making that determination.
- A separate source search found `TestRegionServerNoMaster.testOpenCloseRegionRPCIntendedForPreviousServer`, an original regression test annotated HBASE-9721. It constructs a `ServerName` with start code `1`, calls close/open on the current server, and **expects** this exact guard exception twice. This establishes a known intended outcome and suggests that this candidate is a simple request-header freshness guard rather than the multi-hop ad hoc coordination the study seeks. The active TestRegionMove mirror remains useful as fault-model evidence, but the HBASE-9721 test's expected exception cannot be labeled a new bug.
- We also ran that **unmodified** regression JUnit with the independent observer: it passed in 47.25 seconds. The target saw two requests with start code `1` against the current server start code, and both threw `ServiceException` with a `DoNotRetryIOException` cause. Runtime trace: `node1:.../HBASE-31/independent/regression.log`. Consequently the checklist status is `source_excluded` with screening reason `screened_out_non_adhoc`; the passive TestRegionMove mirror's fault counts are evidence only, not completed ad hoc-check trials.
- `independent/mirror_unique.py` writes one atomic checkpoint per completed HBASE-12 unique JVM run, including the requested and actual start codes for each target hit. `independent/resume_mirror.sh` resumes that projection after interruption; the original JUnit executions remain in HBASE-12's isolated case directory.
