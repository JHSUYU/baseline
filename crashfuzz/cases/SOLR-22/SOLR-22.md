# SOLR-22: commit-generation check

The target is `IndexDeletionPolicyWrapper.getAndSaveCommitPoint(Long)` in Solr 8.11.4 (`e27f44e3d78dfcec230c97e0a1240e3751daeff9`). Its source conditional checks whether a requested commit generation is absent while `latestCommit` has advanced; the target `IllegalStateException` is thrown at line 177.

## Original workload and exact oracle

The workload is the unchanged `org.apache.solr.cloud.TestPullReplica#testAddDocs`, including its original `RandomizedRunner`, setup, and rules. It uses a two-Jetty `MiniSolrCloudCluster` with embedded ZooKeeper, PULL replicas, commits, restart, and replication. Two independent healthy executions each ran exactly one original JUnit test, passed, reached the target, and had no target throw.

The case-local ASM recorder marks the source conditional at line 175 and the exact exception thrown in this method. A target check reached after a fault and an exact target exception are separate outcomes. `ReplicationHandler.getFileList` may catch an expected invalid-generation exception; any target throw still requires source review and replay before a bug mark.

## Target state window

`onCommit` updates `latestCommit`, calls the delegate deletion policy, and then updates `knownCommits`. This ordering creates a possible latest-new/known-old state window. The delegate `SolrDeletionPolicy.updateCommits` primarily updates in-memory metadata and marks `IndexCommitWrapper` deletions. Lucene performs actual `Directory.deleteFile` calls after the policy callback returns. In both healthy runs, the recorder observed no Directory I/O or target checks inside the interval between the two updates.

The campaign records faults applied inside this interval and target checks inside it separately. The initial counter treated an I/O on any thread as inside an active window; [window recount](independent/window_recount.py) requires the writer thread for Directory I/O and the same policy object and logical core across threads for concurrent target checks. Across all 80 trials, the raw counter gave 52 overlapping I/O events, but the corrected count is zero. No injected fault or same-policy target check occurred inside the 783 complete `onCommit` windows. The [seed audit correction](independent/window-audit.json) shows that the one raw I/O hit in healthy seed 7 belonged to another thread.

Two additional unmodified original embedded-cluster tests were healthy-smoked under the same independent agent: `TestPullReplicaErrorHandling#testPullReplicaDisconnectsFromZooKeeper` and `#testCantConnectToPullReplica`. Both passed exactly one JUnit method and reached this target (58 and 223 checks). They observed 2,590 and 11,510 Directory operations, respectively, but no Directory I/O or concurrent same-policy target check inside any of their 6 and 26 `onCommit` windows. Their [first](independent/supplemental/testPullReplicaDisconnectsFromZooKeeper/run.json) and [second](independent/supplemental/testCantConnectToPullReplica/run.json) run records are retained. Neither provides a target-relevant fault seed. A separate [onInit audit](oninit-smoke) of `TestPullReplica#testAddDocs` and `#testKillPullReplica` found 34 complete state intervals with no same-writer Directory I/O or same-policy target check. These observations leave a concrete target-relevant I/O coverage gap; zero target throws is not a high-quality exclusion.

## Additional original cluster test search

Source review found a stronger concurrent workload in the original `TestStressThreadBackup`: one Jetty with embedded ZooKeeper, 20 backup iterations, and a separate thread committing and optimizing the same index. Both `#testReplicationHandler` and `#testCoreAdminHandler` ran as original JUnit methods, passed, and reached the exact guard 20 and 22 times. They produced 113,875 and 104,000 Directory I/O events and 209 and 203 complete `onCommit` windows. Neither had a Directory call on the writer thread or a same-policy target check in that interval. A same-core, other-thread read overlapped 3 and 13 windows, respectively. Those calls came from backup copy and index validation, and do not mutate the deletion policy's latest/known/deleted state.

The original four-Jetty `TestSolrCloudSnapshots#testSnapshots` also passed. It reached the guard 42 times and recorded 886 Directory I/O events and 17 complete `onCommit` windows, again with no writer I/O or same-policy target check inside the interval. The complete [alternate test audit](independent/alternate-test-audit.json) preserves the three original test source and class hashes, agent hash, run times, raw trace hashes, identity/window counts, and source references. Its [runner](independent/stress_smoke.py) and [same-core window audit](independent/stress_window_audit.py) use only the case-local ASM agent and original release classpath; GraphChecker is absent.

The source ordering is `updateLatestCommit`, deletion-policy delegate, then `updateKnownCommitPoints` in `IndexDeletionPolicyWrapper.onCommit`. The source comment for the older-generation race calls its requisite caller a hypothetical future use case. The default `SolrDeletionPolicy.updateCommits` scans commit metadata and marks deletions without a Directory call. Backups use the latest or a named snapshot commit; the named-snapshot save holds the policy monitor. `ReplicationHandler.getFileList` catches the selected `IllegalStateException` for invalid explicit generations. `TestPullReplica#testSearchWhileReplicationHappens` is empty. These source facts and the original cluster traces provide no observed target-relevant Directory selector for a further exception campaign. The case is recorded as `no_usable_cluster_test`, with the previous 80-trial original workload campaign preserved and no new fault trials counted. This conclusion is limited to the audited workloads and Directory operations; it does not rule out a custom deletion policy or an external explicit-generation request.
