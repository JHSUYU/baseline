## Strict differential gate

The translated three-fault plan preserves the original logical order: (F0) selected replica CoreAdmin `UNLOAD` POST returns an `IOException` response before the network send; (F1) selected command reader `GET_CHILDREN_STAT` for the collection `state.json` throws `ConnectionLossException` at `StateWatcher.refreshAndWatchChildren`; (F2) the same reader's `GET_DATA` for the same path throws `ConnectionLossException` at `fetchCollectionState`, at the frozen relative second hit after F1. Source line numbers differ between revisions; selectors use class and method identity, operation, resource path, actor, and phase-relative ordinal. Raw trace must prove the same concrete reader object at both ZK faults and selected guard, ordered full application, and a selected target check after F2. Unmatched or target-lost attempts do not count.

Each qualifying failure must retain two *pre-cleanup* wait snapshots, the original guard Boolean and exception, a same-client unwatched `state.json` read **after** that Boolean, and the original JUnit outcome. A direct state read is observational and cannot alter the selected Boolean. Compare multiple fresh parent/fix runs because the 8.11.4 candidate is timing-sensitive. A target exception alone is not a new-bug verdict; only a strict fixed-version failure with the same missing-refresh state and authoritative replica absence supports that SOLR-16257 does not fix this path. If the fixed build passes, inspect other refresh sources before attributing the difference to the patch.

## Same 8.11.4 experimental causal control

The official `ZkStateReader.java` patch does **not** cleanly apply to the 8.11.4 source (`git apply --check` fails at the first hunk). Its file patch is 461 lines, with 178 additions and 94 deletions; the 8.11.4 reader has about 22 uses of the two maps. A full manual semantic port would be a separate implementation and needs an independent API and behavior audit.

For a smaller causal A/B, `build_same8114_causal.py` copies the existing observational 8.11.4 timeout diagnostic classes and changes only the `ZkStateReader.waitForState` timeout branch. If that exact reader still has a collection watch but no cached collection state, it calls the existing `StateWatcher.refreshAndWatch()` up to three times synchronously until the existing latch is satisfied. The existing `ConnectionLossException` and `SessionExpiredException` handling remains inside that method, and the original `DeleteReplicaCmd` Boolean and JUnit method remain untouched. `CAUSAL_REFRESH` events mark the intervention; this is an **experimental causal fix**, not a backport or test of the official SOLR-16257 patch. The generated reader diff is 17 added and one replaced line at the timeout branch, and `FeedbackProbe` gets one observational event method. The source and class SHA-256 values are in `same8114-causal/build_receipt.json` and `identity_receipt.json`. Both baseline and causal original JUnit bytecode have SHA-256 `6df0acda88ac37234fc9509063bf084d86c0be69bce4616355d09da03ef68f0b`; both selected `DeleteReplicaCmd` bytecode files have SHA-256 `3cc89f4be535c150957cc6535ee5f4a649ef0de3a12a1a5a72788cda864b2d2e`.

Node1 has the exact 8.11.4 source/resources and all 268 runtime classpath entries under this case's separate directory. `run_same8114.py` runs one original embedded-cluster JUnit per fresh scratch, Java 8 `-Xmx3g`, ephemeral listeners, 240s cap, the frozen F0→F1→F2 actor plan, trace and JaCoCo receipts. Count only runs where all three faults apply to the same selected Overseer client and the target guard executes after F2. A pass in the causal overlay can support a recoverable stale-state mechanism only if the matched baseline actually failed; it does not establish upstream novelty on its own.

`analyze_same8114_coverage.py` recomputes JaCoCo feedback from each raw `jacoco.exec` against the exact 8.11.4 production classes for that mode. The original 8.11.4 candidate `actor-v2/evidence/replay-timeout/run-08` applied the same ordered F0/F1/F2 family at events 601/605/640. On the selected Overseer reader, its first 30-second wait saw a watch with no cached collection state at 631, and the second 30-second wait still saw that state at 697. This is the retained timing-sensitive candidate.

In this baseline A/B fault, F0/F1/F2 applied at 596/600/636 and the first wait had the same watch-present/cache-absent state at 626, but the original guard returned `removed` at 649 before a second 30-second timeout; direct ZooKeeper was absent (version 6). The causal A/B fault similarly applied F0/F1/F2 at 594/598/630; after its bounded refresh attempts, the guard returned `removed` at 661, again before a second timeout, with ZooKeeper absent (version 6). Thus the intervention was exercised, but the baseline already recovered on this schedule. The comparison does not establish that the intervention caused recovery, and the single original exception does not establish a new upstream bug. Repeated strict A/B would require a clean resource window and separate source/replay review.
