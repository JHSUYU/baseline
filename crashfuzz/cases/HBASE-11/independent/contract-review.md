# HBASE-11 independent contract review

**Classification:** Reproducible ambiguous RPC completion and expected duplicate-transition rejection. The evidence does **not** establish a correctness bug in HBase 2.6.6, and novelty is unproven. Keep the target outcome separate from the original JUnit failure.

## Evidence inspected

- Exact HBase 2.6.6 source at commit `d5f63f523c065f963992ea4e74db268d17816631`: `TestRegionMove.java:75-125`, `Admin.java:1157-1186`, `HBaseAdmin.java:1594-1621,3169-3182`, `RpcRetryingCallerImpl.java:93-116`, `MasterRpcServices.java:1755-1788`, `AssignmentManager.java:753-765,839-855,2149-2152`, and `Master.proto:102-117` under `/users/ZhenyuLi/.graphchecker-sources/hbase-2.6.6/`.
- Case-local `result.json`, `CANDIDATE.md`, and both independent exact-selector logs `replay_unassign.log` and `replay_unassign_002.log` in `node1-independent-raw.tar.zst`. The archive SHA-256 is `1be105f504bbdb5c998dc59f3e9b0aab8c922eaf232ca356397dc16ba7b9c355`, matching the case receipt. The original shared `gf_0001.log` in HBASE-10's node1 archive independently exhibits the same sequence.

The unchanged JUnit invokes the deprecated two-argument `admin.unassign(regionName, true)` at line 105. In this version the default method delegates to `unassign(regionName)`; the `force` value does not reach the master. The subsequent `move` calls deliberately expect a region-state rejection. A faulted failure at line 105 therefore prevents the test from reaching its intended assertions; it is not itself proof of a cluster-state violation.

Both clean replays show the same ordering for the same region: first `UnassignRegion` reaches `preTransitCheck` in `OPEN` with no active procedure; `RegionStateStore` records `CLOSED`, and the close and parent `UNASSIGN` procedures finish `SUCCESS`; only then does the client-side `RPC_RESPONSE|unassign#1|hbase.pb.MasterService.UnassignRegion|ordinal=1` hook replace the normal response with `SocketTimeoutException` (`originalException=none`). `HBaseAdmin` retries the same region-only request. The second request reaches `preTransitCheck` in `CLOSED` with no active procedure, raises `DoNotRetryRegionException`, and the original JUnit fails at line 105. The logs report one applied response fault each and `JUNIT found=1 succeeded=0 failed=1`.

## Contract and invariant assessment

`STATES_EXPECTED_ON_UNASSIGN_OR_MOVE` contains only `OPEN`. Rejecting the repeated unassign of a now `CLOSED` region is therefore the intended guard outcome. The observed final region state matches the first operation's requested state, and no double assignment, stale read, data loss, or failed recovery is shown. The result is a client outcome ambiguity caused by losing the successful response, followed by a genuine server-side error on a **second** request.

`Admin.unassign` explicitly permits `IOException` for remote or network exceptions. Its request carries a region and ignored `force` flag, but no nonce or operation identifier that would let the master recognize this retry as the completed first operation. `RpcRetryingCallerImpl` retries the timeout and then propagates the duplicate request's `DoNotRetryIOException` subclass. Nothing in the inspected API promises that a call whose response is lost will return success if the underlying transition completed. Calling the final `DoNotRetryRegionException` misleading is reasonable as a diagnostic/API-design observation, but this record does not establish a violated outcome guarantee.

An Apache JIRA search found earlier region-assignment timeout issues, including [HBASE-17275](https://issues.apache.org/jira/browse/HBASE-17275) (older master/region-server assignment timeout) and [HBASE-21095](https://issues.apache.org/jira/browse/HBASE-21095) (procedure retry after master restart). Neither describes this exact client `UnassignRegion` response-loss sequence in 2.6.6, and the search cannot prove novelty. A stronger bug claim would need an explicit idempotent-success contract, an invariant violated after the response loss, or a concrete client workflow that cannot safely resolve the ambiguity by reading region state. None is shown by the current unchanged JUnit and replays. The existing `candidate_unconfirmed` label is conservative; it must not be counted as a new bug.
