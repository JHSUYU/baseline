# HBASE-02: disabled-table guard during region relocation

The selected HBase 2.6.6 check is `ConnectionImplementation.relocateRegion(TableName, byte[], int)` at source lines 910–911. For a non-`hbase:meta` table, it calls `isTableDisabled`; only a true result throws `TableNotEnabledException`. The original `TestConnectionImplementation#testMetaLookupThreadPoolCreated` starts a two-region-server `MiniHBaseCluster`, creates an enabled table, calls `relocateRegion(tableName, row)` at test line 1190, and asserts that the meta lookup executor exists. The two-argument overload immediately invokes the three-argument target. The test's operation and assertion are unmodified.

`isTableDisabled` calls `getTableState`, which invokes `MetaTableAccessor.getTableState` and performs a `Get` against `hbase:meta`. The case-local Java agent probes the target method and table-state result, then observes or faults `ClientServiceCallable.doGet` **only when its call stack contains both** `MetaTableAccessor.getTableState` and `ConnectionImplementation.relocateRegion`. `doGet` normally dispatches to the region server's `ClientService` stub and declares `ServiceException`; the probe throws that declared exception with an `IOException`, `SocketTimeoutException`, `EOFException`, or `ConnectException` cause at selected hit ordinals. This call is before the selected guard returns. The HBASE-01 scan-response fault door is downstream and is not used here.

The graph-independent native JUnit launcher and ByteBuddy agent are under `work/src/`. `work/run.sh build` builds the agent; `work/run.sh run <name> <ordinal:exception,...>` starts the **original** JUnit in a fresh HBase data directory. `work/campaign.py` starts with 48 one-to-four-fault trials, then `work/extend_campaign.py` continues the same checkpoint through trial 64 with up to six faults. If fresh production coverage or I/O family appears near trial 64, the approved budget extends to trial 128 with up to eight faults. Each process atomically updates `result.json` after every trial. Each trial log contains elapsed time, exact RPC hit ordinals, selector match and application, post-fault target result, selected exception, and native JUnit result. JaCoCo records production coverage for `ConnectionImplementation`, `MetaTableAccessor`, and `RpcRetryingCallerImpl`; `work/run.sh coverage <name>` reports method, branch, and line counts. The coverage scope includes these whole classes, so branches exercised by cluster setup can also contribute; coverage increases alone do not establish a target bug.

**Instrumentation provenance:** The counted healthy run and every counted fault trial use the distribution HBase jars, JUnit Platform Launcher, this case's ByteBuddy agent, and JaCoCo. `run.sh` has no GraphChecker JAR or prewoven class directory on its runtime classpath; it neither reads `region_skeletons` nor `static_scope_map`, and it does not run static analysis, aggregation, or closure. An early exploratory `healthy2` run used GraphChecker's JUnit runner to debug classpath and is not part of the counted campaign or final evidence chain.

The healthy native run reached the target once, observed one meta table-state Get RPC, got `isTableDisabled=false`, left the target normally, and passed the original JUnit. JaCoCo covered line 910 and left the selected throw at line 911 uncovered. Faults are considered valid only when every requested ordinal is matched and applied; a target observation must follow the last injected exception. A target exception is a candidate requiring clean-fixture replay and source review before any bug claim.

The original test sets `HBASE_CLIENT_RETRIES_NUMBER=5`. `ConnectionUtils.retries2Attempts` yields six calls; a five-fault sequence can still reach the target after the sixth attempt, while six faults may exhaust retries and lose the guard. Such a sequence is recorded as `lost_target`, not as a target bug. At this observed door, seven or eight requested faults cannot all match before retry exhaustion, even though the approved extended ceiling allows them at other sites.

## Completed result

The healthy JUnit passed in 40.20 seconds. The bounded campaign then completed **65 effective fault trials** with 217/217 requested exception events applied. The original JUnit passed in all 61 trials with one to five faults; each completed the selected guard after the last fault, with `isTableDisabled=false`. Four six-fault trials applied all six exceptions but made `isTableDisabled` exit with `RetriesExhaustedException` before the guard could evaluate. Their JUnit failures are `lost_target`, not selected `TableNotEnabledException` outcomes.

Scoped production branch coverage rose from 147 to 178 outcomes across the three monitored classes, a gain of 31. The first IOException retry trial contributed 29; a `ConnectException` single-fault trial contributed one class-wide branch; the first six-fault retry-exhaustion trial contributed one branch in `RpcRetryingCallerImpl`. The later distinct five-fault order `r066` added no coverage. Line 911, the selected `TableNotEnabledException` throw, remained uncovered. Class-wide coverage can include background cluster work; the evidence supports the precise table-state retry and exhaustion paths, not a whole-system coverage claim.

The 128-trial ceiling opened because the six-fault trial near round 64 reached a new production retry branch. The observed door had then covered all four exception families at depths one through six. Its six-attempt limit makes seven- or eight-fault selectors unmatchable, and additional queued orders reused the same retry path. The campaign therefore stopped with 63 budget slots unused and **no bug claim**. One executed `r065` attempt repeated `r53`'s exact five-IOException selector sequence; it is preserved as `duplicate_attempt` in `result.json` and excluded from the 65 effective trials. Effective healthy-plus-trial time was 2,791.15 seconds; the duplicate took 42.74 seconds separately.
