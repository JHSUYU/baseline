# HBASE-35: duplicate `hbase:meta` entry check in hbck

## Exact target and original cluster test

The selected HBase `rel/2.6.6` condition is `HBaseFsck$3.visit` line 2717, `previous.getMetaEntry() == null`; its false branch throws `IOException("Two entries in hbase:meta are same ...")` at line 2720. The unchanged `TestHBaseFsckReplication#test` runs a `MiniHBaseCluster` and invokes `doFsck` three times. In the counted healthy run, the JUnit passes, a direct ByteBuddy probe observes all three visitor calls and all three null-true guard evaluations, and JaCoCo covers line 2717 but not the duplicate-entry throw. The test expects `UNDELETED_REPLICATION_QUEUE` reports after one peer is removed; those reports are separate from the selected exception.

## I/O selection and exact request identity

The independent probe observes the inbound `RSRpcServices.scan` RPC that opens the `hbase:meta` scanner within each `MetaTableAccessor.fullScanRegions` invocation. Each selector names that full-scan invocation, its retry ordinal, and one exception class. The agent records matching, application, and exact fault cause; the original client may retry the scanner-open RPC. A counted target-retaining trial requires that every planned fault be applied in order inside one full-scan invocation and that a direct visitor guard marker appear after the final fault but before that same invocation exits. An exceptional visitor exit alone does not establish guard reachability. JaCoCo checks the production target line, and the original JUnit outcome is recorded separately.

The campaign uses only the observed scanner-open RPC door. It does not model scanner continuation RPCs or mutate `hbase:meta` rows. Plans are unique ordered sequences of `IOException`, `EOFException`, `SocketTimeoutException`, and `ConnectException`, with a default budget of 80 trials and at most eight faults. Valid production method/branch coverage or a new observed I/O family promotes nearby plans into the queue. Extension to 128 trials and ten faults is conditional on new valid coverage or I/O in trials 73–80. Each completed trial atomically updates `result.json`, which the table watcher reads.

An isolated, unchanged healthy JUnit rerun used an expanded observation agent to inspect all `RSRpcServices.scan` calls, `FileSystem.open`, and `FSDataInputStream.read*` during each full-scan invocation. Each of the three target-reaching scans showed one `hasScan=true` scanner-open RPC before the visitor; it showed no scanner continuation or events on the probed file I/O APIs in that interval. This is a statement about those observed APIs, not a claim that every possible lower-level I/O operation was absent. The supplemental observations generated no additional scoped fault family.

## Result and provenance

The completed campaign ran 80 unique ordered plans: 12 one-fault, 48 two-fault, 18 three-fault, one four-fault, and one eight-fault sequence. All 174 requested fault events matched and were applied. Every trial retained a direct guard call after the final fault in the same full-scan invocation and passed the original JUnit. Selected production branch coverage remained at 514, equal to the healthy run. The duplicate-entry throw at line 2720 stayed uncovered; no trial produced the selected `IOException`, another target exception, or a new-bug mark. Trials 73–80 added no valid production method/branch or observed I/O family, so the conditional 128-trial extension did not trigger. The ledger records exact selectors, fault cause markers, elapsed time, per-trial UTC checkpoint estimates, raw evidence hashes, target calls, and JaCoCo coverage.

Source inspection supports the observed recovery: the injected `ServiceException` wraps the chosen I/O exception at the server scanner-open RPC before that attempt returns a meta row. The original scanner retries, and the direct visitor markers show the same `fullScanRegions` invocation proceeds to the guard. The selected throw requires a second meta entry for an already populated region; the original replication-queue test does not create such a row. These results cover the tested scanner-open fault door and do not establish behavior for unobserved fault locations.

The counted runtime uses the unchanged original MiniHBaseCluster JUnit, case-local ByteBuddy probes, and JaCoCo over five relevant HBase production classes. It does not use GraphChecker, prewoven classes, `region_skeletons`, `static_scope_map`, static aggregate, or closure data. Source snapshots are from HBase commit `97a51ab9e3cf9f9d21bf08c3b1e52c962579ef2b`. The evidence archive includes the healthy and fault logs, JaCoCo execution files, runner, source snapshots, and a per-file SHA-256 manifest.
