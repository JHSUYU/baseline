The final move exits at the preceding B2 check and does **not** evaluate B3, even though the JUnit catches `DoNotRetryIOException` (the B2 `DoNotRetryRegionException` is a subclass).
- `independent/mirror.py` records B3-specific outcomes from HBASE-10 original-JUnit executions without rerunning the same fault sequences. Its strict injection, target-after-fault, exact exception, stable I/O, coverage, and timing fields are separate from HBASE-10/11. These shared runs use a case-local ByteBuddy recorder and JaCoCo on original production classes; they use no GraphChecker code or static skeleton. Shared runtime is nonadditive.
- The B3 target is often lost after response-loss faults on assignment/unassignment, so a separate `independent/unique` campaign uses the **same original JUnit** with an independent ByteBuddy/JaCoCo recorder and prioritizes new request-side fault sequences. Before execution, it checks HBASE-10's completed sequence keys to skip those already run. It also observes HBASE-31's RS start-code guard in the same JVM. Its own checkpoint and target-specific budget begin with a new healthy seed; coverage unions are not mixed across recorder scopes.
- The RPC campaign covered request/response families. The target also depends on table state: `AssignmentManager.isTableDisabled` reads `TableStateManager`, whose `setTableState` writes `hbase:meta` before updating its cache. `DisableTableProcedure` writes `DISABLING`, waits for `CloseTableRegionsProcedure`, then writes `DISABLED`; `TestRegionMove` calls its final move only after synchronous `disableTable` returns. The region is then `CLOSED`, so B2 preempts B3. A meta read exception inside `isTableState` is caught and converted to `false`. These source facts limit what the sequential original JUnit can expose.
- The default budget is 80 effective B3-retaining trials with at most 8 ordered faults, extended to 128/max-10 only if the last 16 effective trials contain genuinely new production coverage or stable I/O families. Every trial records seconds, exact I/O identity, faults actually applied, whether B3 still executes afterward, the exact target exception, and production coverage.
- Stable I/O novelty for this queue uses only I/O **before the last B3 evaluation**. A two-trial setup error that had counted later RPCs as new B3 feedback was corrected in their existing checkpoints with `unique/reconcile_target_prefix.py`; the two JVM executions were retained and did not rerun. The aborted in-flight third trial was restarted from its checkpoint. The initial healthy seed that omitted `RSRpcServices` from the coverage report was archived as a setup pilot; the homogeneous campaign began only after a corrected healthy seed covered all nine production classes.
- `unique/resume_campaign.sh` restarts the tmux campaign from its saved queue and in-flight trial after a process interruption. The `HBASE-12/independent/publish_unique.py` publisher merges the separately attributed shared and unique rows while keeping their distinct JaCoCo coverage scopes explicit.

## TableState I/O supplement and its limit

The case-local ByteBuddy `HBase12MetaAgent` and ten-class JaCoCo reporter ran the same original JUnit with an independent healthy seed. An initial setup run failed during table creation because an inlined advice helper was package-private; its log and state were archived as `healthy-access-error-pilot.json` on node1 and excluded. After the visibility fix, the clean seed passed in **43.56 seconds**, observed two real B3 evaluations, **1,126 production probes**, and eight TableState writes: ENABLING, ENABLED, DISABLING, and DISABLED, each with request/response. It observed **zero** `MetaTableAccessor.getTableState` reads for the test table because `TableStateManager` served the state from its cache. No read selector was invented.

The first six precise fault plans targeted DISABLING/DISABLED writes. All six matched and applied, and all six original JUnit runs passed, but those writes happened **after both B3 evaluations**, so none had a post-fault B3 visit. Four further precise plans targeted the earlier ENABLING/ENABLED write requests or responses using the same healthy seed and coverage scope. All four matched, reached B3 after the fault, and passed the original JUnit; B3 remained false. These ten trials took **459.67 seconds** plus the 43.56-second healthy seed. The early/late continuation retained the original six checkpoints and did not rerun them. This is a workload-order limit on bug detection, not evidence that the guard cannot fail in other executions.
