# SOLR-05 POST-write extra-replica independent review

Scope: read-only source and raw-evidence review of Solr 8.11.4. This observation is separate from the selected `ZkController.register` null guard. No additional cluster JUnit was run for this review.

## Evidence and causal path

The unchanged `AddReplicaTest.testAddMultipleReplicas` sends one AddReplica request for the five-replica final batch, waits for nine active replicas, then asserts the collection has exactly nine entries (`AddReplicaTest.java:96–122`). Its own assertion failed `expected:<9> but was:<10>` in eight of nine strict POST-write campaign attempts and in the independent exact-plan replay (`actor-upstream/evidence/replay-post-001/replay-audit.json`, 17.869s, JUnit exit 1). The selected register guard did **not** fail: replay event 1071 reports `present` for the same replica after the fault. The nine PRE-write attempts lost that same-replica guard and are not effective selected-target trials.

The replay's sole selected `STATE_SET_DATA_POST` fault is event 1002: collection `testAddMultipleReplicas`, shard1, `core_node18`, core `testAddMultipleReplicas_shard1_replica_p13`, Overseer writer 880739410, intended host `127.0.0.1:45083_solr`. Generated `ZkStateWriter.java:263–267` calls real `SolrZkClient.setData` and **then** the research `upstreamWriteDone` hook; this hook raises synthetic `ConnectionLossException` after the write returned. It represents an ambiguous committed-write result to the caller; it does not mean the underlying ZK call itself failed. The exception prevents the writer's subsequent local `clusterState` update and pending-map clear. `Overseer.java:194–214, 261–285, 286–298` retains/reprocesses work after the exception. Replay event 1017 has a new pending `core_node19` on a different writer for the **same core and receiver**; event 1021 shows its state write completed.

The source permits this change of ID: `AddReplicaCmd.java:247–260` may queue `ADDREPLICA` without `coreNodeName`; `SliceMutator.java:84–89` calls `Assign.assignCoreNodeName` afresh when it is absent. This is a source-supported non-idempotent internal state-queue retry. It can produce two logical state entries for one requested core. The replay logs show one `CoreAdmin CREATE` with `coreNodeName=core_node18`; they do not prove creation of a second physical core. The assertion reads the test client's collection state, not an independent fresh ZK snapshot. A direct authoritative state read of both IDs would strengthen the persisted-state claim. Raw trace, JUnit log and manifest SHA-256 are in `replay-audit.json`; the audit checks a unique applied F0, exact writer/replica/receiver identity, subsequent same-replica guard, and the second pending entry.

## Known-issue comparison

- [SOLR-8722](https://issues.apache.org/jira/browse/SOLR-8722) is a fixed 2016 improvement about removing forced refresh on every Overseer operation and waiting for AddReplica state change. The observed ambiguity occurs after a committed `state.json` write during internal queue processing; this issue does not establish the same mechanism.
- [SOLR-9818](https://issues.apache.org/jira/browse/SOLR-9818) is an open Admin UI retry bug after the **external client** loses a response. It shares the general non-idempotent-retry concern but differs in actor and queue boundary. The original JUnit did not use Admin UI retries.
- [SOLR-7982](https://issues.apache.org/jira/browse/SOLR-7982) reports the **same ID** assigned to different cores/shards. This trace has **different IDs** assigned to the same core and receiver.
- [SOLR-13859](https://issues.apache.org/jira/browse/SOLR-13859) reports AddReplica waiting for a state entry. It does not describe this POST-write duplicate-entry chain.

The concrete mechanism is distinct from these descriptions, but this search cannot establish exhaustive upstream novelty. The injection is synthetic, and the selected guard never throws. Classification: **reproduced non-target candidate, known-issue overlap unresolved; no new-bug mark**. A report would need an authoritative post-fault ZK snapshot, a minimal failure/replay on a maintained version or a fix differential, and an upstream duplicate search before claiming novelty.
