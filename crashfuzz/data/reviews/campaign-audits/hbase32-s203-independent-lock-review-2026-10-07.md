# HBASE-32 s203 independent lock review

**Disposition:** retain `candidate_review`; no new bug classification. The exact two-fault original embedded-cluster JUnit stalled twice without a final JUnit result, but a trace-only diagnostic overlay has not captured the missing same-server lock identity edge. The directly observed B7 `DoNotRetryIOException` is the expected response to the injected exception, separate from the recovery-stall candidate. No diagnostic run enters the fuzz denominator.

## Native observation and source path

The unchanged `TestRegionReplicaFailover#testLotsOfRegionReplicas` s203 run and its fresh-fixture same-plan clean replay both applied the selected `MASTER_OPENED_RPC` and `RPC_FLUSH_REGION` faults to the same replica-7 region actor, reached B7, then stalled during the 600-region create-table workload. Both were capped at 600 seconds and exited 124 without JUnit completion. The original run has 162/600 successful child procedures before shutdown; the replay has 170/600. The original raw plan/receipt are `cases/HBASE-32/work-upstream/replay-s203-plan.json` and `evidence-s203-candidate-receipt.json`; the raw logs and repeated `Thread.print -l` dumps are under `work-upstream/logs/s203*` and `replay-s203*`. The original and replay archive manifest SHA-256 values are `5cb4fb05eb9f887780bb8dc3aa479dc6246afb9de15863387d787745096bfe68` and `f71e5c533a073c81e00fcabc461eece65846ee3108899ac00b922cf0912c6103`.

In exact HBase 2.6.6 `AssignmentManager.java`, `reportRegionStateTransition:1256–1278` retains a `ServerStateNode.readLock` through `updateRegionTransition:1298`, while `submitServerCrash:1980` needs that server node's `writeLock` before scheduling the crash procedure at `:2008`. `RegionRemoteProcedureBase.beforeExec:289` acquires a `RegionStateNode` lock and `execute:323` can persist a transition through `AssignmentManager.persistToMeta:2290` and `RegionStateStore.updateRegionLocation:238` into `HTable.put`; `afterExec:295` releases the region lock. The repeated pre-shutdown original/replay thread dumps show the tracker waiting for a server write lock, two report RPC handlers waiting for region locks, and PEWorkers owning those same region locks while retrying meta writes. In the clean replay 500-second dump, handler #1 waits on region lock `0x00000007b80c91f8` owned by PEWorker-12, and the tracker waits on server RW synchronizer `0x00000007b8471880`; the first SCP appears only after the shutdown hook (`replay-s203.log:37145,46396`). This proves the region-lock edges and an SCP scheduling delay. `Thread.print -l` cannot identify shared read-lock holders, so it does not prove that the handler's read lock is on the **same** `ServerStateNode` as the tracker's blocked write lock.

## Prior issues and next evidence threshold

[HBASE-21508](https://issues.apache.org/jira/browse/HBASE-21508) fixed a late transition report from a dead server racing with SCP and introduced the read/write fencing present in 2.6.6. The s203 evidence concerns a possible wait *within* this current fencing, so it does not itself establish a recurrence of the old double-assignment bug. [HBASE-24526](https://issues.apache.org/jira/browse/HBASE-24526) reports a meta assignment stall with PEWorkers blocked in meta updates; there the meta assignment procedure was already created, whereas s203's first SCP is delayed until shutdown. This is a meaningful source-level difference, but not sufficient to establish a distinct upstream bug without a diagnostic positive run and source comparison.

The conservative mechanism hypothesis is that, under a narrow schedule, a report handler holds the failed meta server's READ lock while waiting for a region lock owned by a PEWorker blocked on meta, and `RegionServerTracker` waits for that same server's WRITE lock before scheduling SCP. The first two edges are supported by raw stacks; the shared `ServerStateNode` identity and closed wait cycle are **not** proven. Retain s203 as an independently replayed timeout candidate. Resume supplemental fuzz after archival if desired, and if the symptom reappears, collect the same actor/lock trace plus pre-timeout dumps without counting diagnostic replays as new fuzz trials. Promote the finding only after the same-node identity and recovery causality are shown and relevant known issues are excluded.
