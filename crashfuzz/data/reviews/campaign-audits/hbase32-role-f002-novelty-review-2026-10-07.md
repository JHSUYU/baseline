HBase 2.6.6 source at `/users/ZhenyuLi/.graphchecker-sources/hbase-2.6.6` (`d5f63f523c`) corroborates each edge: `ServerStateNode.java:38-39,90-96` uses one `ReentrantReadWriteLock`; `AssignmentManager.java:1256-1278` keeps its READ over the transition handler, while `:1975-2009` requires WRITE before setting `CRASHED` and submitting SCP. `RegionRemoteProcedureBase.java:287-295,322-346` keeps the region lock across synchronous `persistToMeta`; its IOException backoff starts only after that call returns or throws. `RegionStateStore.java:231-249` synchronously calls `table.put(put)`, catches an IOException, aborts the master, and rethrows. Thus a client retry still inside `HTable.put` has not reached the procedure's error handler. The dependency is: meta-host recovery needs SCP; submitting SCP needs WRITE; the held READ waits for a region lock; its owner awaits a meta write to the crashed host. This is a concrete recovery wait cycle, but the retries may terminate and break it. A 600 s test timeout alone cannot prove permanent nonprogress or a JVM deadlock.

## Known issue and later source boundary

- [HBASE-21508](https://issues.apache.org/jira/browse/HBASE-21508) introduced/uses read–write fencing to prevent a dead server's transition reports from racing with SCP and double assignment. Its discussion also recognizes meta-related deadlock with an exclusive report lock. Our trace concerns a distinct liveness risk of the *read* lock still held when SCP tries WRITE; the prior fix does not by itself classify this run as new.
- [HBASE-24526](https://issues.apache.org/jira/browse/HBASE-24526?focusedCommentId=17149647&page=com.atlassian.jira.plugin.system.issuetabpanels%3Acomment-tabpanel) is open and describes PEWorkers stuck on meta updates while a meta assign subprocedure has already been scheduled. It strongly overlaps the meta-write dependency, but the observed role-f001/f002 ordering is earlier: the dead meta host's SCP cannot be submitted before shutdown. The issue may cover the broader symptom even if its documented lock ordering differs.
- [HBASE-29259](https://issues.apache.org/jira/browse/HBASE-29259?focusedCommentId=17943805) **comment 17943805** explicitly discusses a user-region meta update waiting until SCP assigns meta. The issue's *primary reported failure* is instead an orphaned `CloseRegionProcedure` persisted in `INITIALIZING` after SCP and TRSP race, then a master restart failure; the fix was reported in 2.6.3. Its comment describes SCP and TRSP already running concurrently, so it does not document this candidate's pre-SCP `ServerStateNode` READ/WRITE edge. It is a partial mechanism overlap, not an established duplicate.
- [HBASE-21440](https://issues.apache.org/jira/browse/HBASE-21440) concerns a crashed server's AssignProcedure incorrectly progressing after SCP already acts, leaving a region inaccessible. It has a different order and failure manifestation.

In local `origin/branch-2.6` at `03be5bee0ade1072258189bc9e28c12f193bab4b` (2026-09-30), the same `AssignmentManager` READ/WRITE fence and synchronous `RegionRemoteProcedureBase.persistToMeta`/`RegionStateStore.table.put` still exist. This shows no source-level removal of this dependency in that branch snapshot; it does **not** prove a later build reproduces the runtime symptom. Local Apache `origin/master` snapshot `db7081f6739d32bec142cab76936e4a2c16c62de` still has the server READ/WRITE fence, but `persistToMeta` now returns a `CompletableFuture` and meta put uses an async client. Its `RegionRemoteProcedureBase.afterExec` also retains the region lock while that future is pending. The scheduling and lock behavior differs, so neither fix nor reproduction can be inferred from source shape alone.

## Repetition boundary and classification

role-f001 independently retained this chain through repeated dumps and did not complete the original JUnit within 600 s; SCP was first submitted only during timeout shutdown. role-f002 now reproduces that bounded outcome on a different physical meta RS/replica with the same exact-actor V3 selector. These runs establish reproducible **600 s noncompletion under the frozen V3 semantic plan**, not an indefinitely hung production cluster. The 46-retry client path, with try 36 still in flight at the cap, is an explicit alternative to permanence; a later retry exhaustion could release the locks or abort the master. The correct classification remains `scheduling_sensitive_recovery_wait_candidate`; `new_bug=false`, with HBASE-24526 and HBASE-29259 as substantial overlap boundaries. A novelty claim needs a same-version source/issue differential for the pre-SCP lock cycle and evidence that the runtime cannot recover within relevant retry bounds (or a causal fix that restores progress under the same plan).
