# ZooKeeper terminal-case runtime identity audit

Snapshot: 2026-10-07 03:40 UTC. This is a read-only audit of the 11 ZooKeeper rows marked `quality_complete` in the 104-check graph-free checklist. No JUnit, fault campaign, case result, or checklist was changed. I read the final case-local agents and campaign acceptance code, original test bodies, and archived healthy/trial events. The earlier [Solr/ZooKeeper evidence audit](quality-complete-solr-zk-2026-10-07.md) verifies archive hashes and callsite/ordinal counts; this audit asks the stronger **logical actor** question.

## Finding and scope

Seven terminal rows, **ZOOKEEPER-01/02/03/04/11/12/13**, use `site@@globalOrdinal` to inject I/O across every peer and client in one embedded-cluster JVM. Their probes increment `ORDINALS[site]`, log only callsite/ordinal plus a thread name, and match a plan without a client object, channel, peer ID, session, or epoch-file owner. Their `strict` checks re-parse those same plan strings; `target_after_final_fault` means any later exact source guard. They prove callsite/ordinal applications and exact source-site observations, but they do **not** establish that the selected logical I/O actor is the one faulted in another fresh JUnit run. They must not be counted as actor-matched completions under the current criterion. This finding does not itself establish a new system bug or invalidate the raw observations.

## Conservative offline salvage

These are **not** estimates of how often the old tests were correct. They count what the present raw fields can prove without a new instrumented run. A thread name is not a stable client/socket identity; dynamic TCP ports alone do not identify a client handle or session across runs. Likewise, file-call sites without a `File` receiver/path cannot prove an epoch-file key. The campaign trial counts and elapsed times remain valid as callsite-level observations.

| Case(s) | Old strict/post counts | Full I/O actor + selected target actor/relation provable offline | Useful partial evidence |
| --- | ---: | ---: | --- |
| 01 | 58 / 49 | **0** | Target raw session IDs and two same-session diagnostic replays exist; faulted client handle/server connection is unbound. |
| 02 | 80 / 28 | **0** | Target raw session ID exists; client move-step and server-side connection are unbound. |
| 03 | 80 / 31 | **0** | Same as 02. |
| 04 | 80 / 74 | **0** | Client endpoint appears in SendThread name for some faults, but guard has neither server SID nor client/session ID. `trial-015` shows ordinal drift. |
| 11 | 44 / 25 | **0** | Target peer 0 is visible after faults in all 25 retained trials; the chosen I/O actor and exact epoch filename are not recoverable for every fault. |
| 12 | 55 / 45 | **0** | 17 of 45 postfault trials have every fault peer inferable from a preceding same-thread `TARGET_ENTRY`; this is **peer-only**, and does not recover epoch filename/client connection. Six of those 17 have all faults on peer 0 yet no later peer-0 guard. |
| 13 | 116 / 103 | **0** | The source audit joins 863 selected throws to the created global session, but the faulted socket/client actor is unbound. |

Thus no old trial should silently satisfy the **full** actor-aware identity gate. Keep the archives and measured ledger intact; V2 can seed its I/O callsite families and coverage priorities from them, while its actor-aware effective-trial denominator starts separately. A stronger offline join may salvage a narrower fact (for example, some peer-only file-fault contexts) and should be recorded separately, not relabelled as a full V2 run.

## Other terminal ZooKeeper cases

ZOOKEEPER-05/06/07/10 use `site@@peer/resource@@ordinal` in their final `Probe.io(site, actor, resource)`, with `sourceKey` reading `QuorumPeer.getMyId` or known `LearnerHandler` SID. No selected plan contains `peer=unknown`. ZOOKEEPER-05 excluded five pre-`FOLLOWERINFO` `LearnerHandler peer=0` selections from strict counts. These four do **not** have the same global-ordinal I/O actor defect. Their campaign code still regards any later method guard as target-retaining; the guard records peer ID, so a stricter role-aware recomputation is feasible from existing events. For ZOOKEEPER-10 healthy sampled guards are on peer 1, while 14 of its 76 postfault trials show only peer-2 sampled guards. This may be a legitimate ObserverMaster/leader role transition, not automatically an invalid run. Record the role transition and expected fault-to-target relation before making a stronger per-actor claim. Literal `fault peer == target peer` would wrongly discard legitimate cross-peer coordination, such as a follower RPC fault influencing a leader's `waitForEpochAck` check.

## Shared V2 actor contract

Use the **actual I/O receiver and resource**, not the current Java thread name or static callsite ordinal, to produce `faultActor`, `resource`, and `actorLocalOrdinal`. Record `targetActor` plus a case-declared relation (`sameSession`, `samePeer`, `clientToPeer`, `followerToCurrentLeader`, or `epochFileOwnedByTargetPeer`). A plan is strict only if every full key applies in order and is unambiguous. A postfault target counts only when its logical actor/relation matches the case target, even if the target executes on a different physical peer due to a documented leader transition. Two fresh fault-free JUnit seeds must establish stable logical tags before mutations. Any unknown/zero/ambiguous actor or file owner is excluded from candidate generation and from effective counts.

| Case | Minimum stable I/O key and target relation | Fail-closed rule |
| --- | --- | --- |
| 01 | `clientRole={creatorCloser,verifier}` + logical session token + current leader SID + socket direction; server `NIOServerCnxn` peer SID + correlated client/session + connection generation. Target `checkSession` raw ID maps to creator/verify role. | Exclude pre-handshake socket without a uniquely mapped client role/peer, async callback without owning request/client, and server connection without a client/session join. |
| 02/03 | `sharedTestSession` + client-handle move-step index + destination peer SID + socket direction; server peer SID/connection generation. Target `checkSession`/`setOwner` ID and owner map to that shared session and expected move step. | Exclude an unpaired reconnect handle, reused session with unresolved generation, or server-side connection with unknown peer/session. |
| 04 | Single client handle/session + `initialFollower` or `replacementFollower` SID + direction; target `processConnectRequest` server SID + connecting client/session. | Exclude endpoint whose dynamic port cannot be joined to a peer SID, and target connection before its client role can be resolved. |
| 11/12 | `QuorumPeer.myid` + normalized epoch filename (`currentEpoch`, `acceptedEpoch`, or `.tmp`) + operation; for nested `AtomicFileOutputStream`, use receiver `origFile` and map its parent snap directory to the owning peer SID. Target `loadDataBase` peer SID; 12's JUnit assertion specifically concerns peer 0. | Exclude `FileReader`/atomic calls whose `File` argument or `origFile`/owner cannot be read, plus network I/O lacking its socket peer/session. Do not use temporary absolute directory strings as cross-run identity. |
| 13 | First test client/global-session role + destination peer SID + direction; server peer SID + client/session-correlated connection. Target read-only server role/SID and the first created global session ID. Later test clients have separate tags. | Exclude pre-session sockets and server requests that cannot be joined to the created global session, or `TARGET_ENTRY` without a session/RO-peer binding. |

Practical hooks in the original 3.8.7 source: `ClientCnxnSocketNIO#doIO` receives a `ClientCnxn` and owns `sockKey`/`sessionId`; capture that receiver and `SocketChannel` endpoints, then tag the client by a stable constructor/test-operation role rather than absolute ports. `NIOServerCnxn` owns `zkServer`, `sock`, and `sessionId`; map `zkServer.getServerId()` (quorum subclasses override the base method) and join the two socket endpoints or session ID. `QuorumPeer.readLongFromFile(name)` and `writeLongToFile(name, value)` have the owning `this.myid` and logical filename; `AtomicFileOutputStream` owns `origFile`/`tmpFile`, and `AtomicFileWritingIdiom` receives `targetFile`. Register each peer's snapshot directory to `myid`, normalize filenames, and reject ambiguous mappings. For async work, propagate a stable request/client token at the actual scheduling boundary or derive it from the callback's request object; never infer ownership from a reused worker-thread name alone.
