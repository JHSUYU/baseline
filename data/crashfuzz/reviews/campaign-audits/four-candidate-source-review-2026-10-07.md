# Source review of four unconfirmed candidates (2026-10-07)

Scope: HBase 2.6.6 and Solr 8.11.4, with the preserved original embedded-cluster JUnit workloads and fault traces. This review distinguishes a reproduced fault-induced symptom from a confirmed new upstream bug. No candidate is promoted to `new_bug=true`.

| Case | Direct source and run evidence | Conclusion |
| --- | --- | --- |
| HBASE-11 | `Admin.java:1164-1169` permits `IOException` for network failure. `HBaseAdmin.java:1609-1620` rebuilds the unassign request on retry, while `AssignmentManager.java:2151-2152` accepts unassign only from `OPEN`. The original request completed and persisted `CLOSED`; the injected response loss caused a retry against `CLOSED`. Two exact-selector replays reproduced the exception. | Client completion is ambiguous after a lost response, but the trace does not establish a state invariant or API contract violation. Not a confirmed bug. |
| HBASE-32 | `AssignmentManager.java:1256-1278` holds the server READ lock while handling a region transition, whereas `submitServerCrash` at `:1975-2009` requires WRITE. `RegionRemoteProcedureBase.java:287-346` retains the region lock during synchronous `hbase:meta` persistence. Two actor-matched runs showed this lock chain and remained unfinished for 600 s; the second had completed only 36 of 46 meta RPC retries. A third run without the outstanding READ completed in 89.83 s. `RegionReplicaFlushHandler.java:117-136` makes the selected target rethrow the injected error. | A reproducible, scheduling-sensitive recovery wait, but no observation after retry exhaustion and no proof of permanent failure. [HBASE-24526](https://issues.apache.org/jira/browse/HBASE-24526) and [HBASE-24673](https://issues.apache.org/jira/browse/HBASE-24673) overlap the meta-unavailable procedure blockage. Newness unresolved. |
| SOLR-09 | `DeleteReplicaCmd.java:254-279` reports failure after `waitForState` cannot see replica removal. In actor-aware replay run 08, two ZooKeeper read failures left a watcher registered but its collection cache absent; the same client directly read ZooKeeper state version 9 with the replica absent, and the replica's core directories were absent, before the selected exception. See `cases/SOLR-09/actor-v2/evidence/replay-timeout/run-08/events.tsv:601-706`. `ZkStateReader.java:1374-1392,1768-1785,1877-1919` contains the watch/cache/wait paths. | A reproduced fault-induced false failure in 8.11.4. [SOLR-16257](https://issues.apache.org/jira/browse/SOLR-16257) describes a related stale-state symptom with a different recorded cache/watch ordering; its fix has not been tested against this fault sequence. Plausibly distinct, but novelty unconfirmed. |
| SOLR-40 | `ZkStateReader.java:2302-2319` updates the alias cache only after the watched read returns, and `RoutedAliasUpdateProcessor.java:129-135` throws immediately on an empty cached property map. `CreateAliasCmd.java:75-87` describes immediate usability for an initially created alias. In the original four-node JUnit, the alias was persisted in ZooKeeper but the same-reader update got HTTP 500 during the read retry window. Independent lower-layer single-read-loss controls reproduced the failure in 1/5 and 1/3 trials; a post-retry timing control failed in 0/4. | A reproduced transient alias-cache visibility failure under a synthetic lower-layer read loss. Real disconnection behavior and nonduplication against [SOLR-12256](https://issues.apache.org/jira/browse/SOLR-12256) and [SOLR-12258](https://issues.apache.org/jira/browse/SOLR-12258) remain unproven. Newness unresolved. |
