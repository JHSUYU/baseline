# SOLR-36 trial 58: exact target exception review

The unchanged Solr 8.11.4 `ShardSplitTest#test` passed in trial 58 (`JUnit ran=1, ignored=0, failures=0`). Four planned ZooKeeper `ConnectionLoss` events matched and applied on the same logical child replica, `SOLR/REPLICA/collection1/shard1_0/core_node11`. After the last applied event (trace sequence 2762), that child evaluated the SOLR-36 guard at sequence 4581 with `state=active;phase=FROMLEADER` and threw the exact line-987 `SolrException` at sequence 4582. The frozen plan, trace, JUnit log, and JaCoCo data are in `candidate-0058-evidence.tar.gz`; `candidate-0058-sha256.txt` records the archive digest.

The original source explains this response. `DistributedZkUpdateProcessor.getSubShardLeaders` (lines 868–890) forwards a parent update when its collection-state view says that the child is in `CONSTRUCTION` or `RECOVERY` and its range is a subset of the parent. `doDefensiveChecks` (lines 976–997) rejects `FROMLEADER` requests on a child whose *own* collection-state view already says `ACTIVE`, returning a protective 503. Parent `shard1/core_node4` and child `shard1_0/core_node11` are separate logical cores hosted by the same physical Jetty endpoint in this trial. This observation is a collection-state snapshot disagreement, not evidence of a message lost between physical nodes.

The trial log records the child 503, a parent `DistributedUpdatesAsyncException`, and a `BaseCloudSolrClient` retry. In original `BaseCloudSolrClient` (lines 976–999), a 503 `RouteException` marks cached collection state stale and retries. Document id 298 was accepted on the subsequent child request. The original test's `splitByUniqueKeyTest` waits for child recovery and calls `checkDocCountsAndShardStates` (lines 805–806); that method checks both children become `ACTIVE`, replica counts, subshard consistency, and their document counts (lines 969–1020). Passing JUnit therefore supports recovery for the operations checked by this test; it does not prove every possible application invariant.

Eight bounded, byte-identical replays used the same four-event plan and agent. All eight applied all four faults exactly and passed the original JUnit, but none repeated the post-fault `ACTIVE` guard or exact line-987 throw. Details and trace digests are in `candidate-0058-replay-summary.json`. The exception is a real, schedule-sensitive target observation and a protective abort candidate. It is **not a confirmed new bug**. The ZooKeeper campaign resumed from trial 59 without repeating trials 1–58; parent-to-child HTTP faults remain a separate modality to test.
