# Mallory campaign core

## Native GraphChecker trial mode

`graphchecker_campaign.py` is the new per-trial backend for an **unchanged
JUnit 4 cluster test**. It consumes a `weave_manifest.json` and
`static_scope_map.jsonl` generated by `Mallory/static_scope_port`, weaves the
selected original classes once, and starts a fresh test JVM for each fault
plan. Its causal evidence comes only from `MessageDoors`/`TrialGraphMain`
rows. The old `campaign.py` event graph and `MALLORY_PROBE` cannot satisfy its
strict fault or target oracle.

Example configuration, with real absolute build paths substituted for the
placeholders:

```json
{
  "schema_version": 1,
  "case_id": "EXAMPLE-01",
  "cwd": "/absolute/original/source/tree",
  "java": "java",
  "timeout_seconds": 600,
  "junit": {"class": "org.example.OriginalClusterTest", "method": "testOperation"},
  "target": {
    "check_site_id": "<target-branch-site-from-weave-manifest>",
    "throw_site_id": "<exact-target-throw-site-from-weave-manifest>",
    "exception_class": "java.io.IOException"
  },
  "weave_manifest": "/absolute/static-output/weave_manifest.json",
  "static_scope_map": "/absolute/static-output/static_scope_map.jsonl",
  "original_class_dirs": ["/absolute/original/module-a/classes", "/absolute/original/module-b/test-classes"],
  "tool_classpath": ["/absolute/weaver/classes", "/absolute/weaver/dependencies.jar"],
  "test_classpath": ["/absolute/original/compiled/test-classes", "/absolute/original/test-dependencies.jar"],
  "graph_jar": "/absolute/mallory-graphchecker-runtime-all.jar"
}
```

For JUnit runners that execute the test on a worker thread, the config may
pin a runner with `"runner":{"main_class":"org.example.GraphJUnit",
"args":["{class}","{method}"],"jvm_args":["-Djava.io.tmpdir=/scratch"]}`.
The resolved class bytes and exact config hash are included in the weave
receipt. The runner must open exactly one GraphChecker window and bind a named
request scope on the thread executing the unchanged test method. The default
runner is `JUnitTrialMain`; a second Java agent is rejected.

For a target that is itself a selected `THROW`, omit `check_site_id`. Both
target site IDs must resolve to unique sites in the static weave manifest;
the throw site must declare the same exception class. The current preparation
step stages selected class files from the ordered `original_class_dirs` into
an isolated weave input, then pins each source file hash. The singular
`original_classes` key is accepted for one-directory builds. Source aliases
and RPC/state carriers remain
system adapter obligations; an absent identity is recorded as a gap, never
filled by a matching name or timestamp.

Run the preparation once and then run individual plans:

```sh
python3 -m Mallory.core.graphchecker_campaign prepare \
  --config /absolute/case.json --out /absolute/campaign/prepared
printf '%s\n' '{"faults":[]}' > /absolute/campaign/healthy-plan.json
python3 -m Mallory.core.graphchecker_campaign trial \
  --config /absolute/case.json --prepared /absolute/campaign/prepared \
  --plan /absolute/campaign/healthy-plan.json --out /absolute/campaign/healthy
python3 -m Mallory.core.graphchecker_campaign trial \
  --config /absolute/case.json --prepared /absolute/campaign/prepared \
  --plan /absolute/campaign/fault-001.json \
  --prior-trace /absolute/campaign/healthy/graphchecker-trace.jsonl \
  --out /absolute/campaign/trial-001
```

The native fault plan has `{"faults":[{"siteId":"...","node":"nn-1#epoch0",
"occurrenceId":"...","ordinal":1,"exceptionClass":"java.io.IOException"}]}`.
Take the four runtime identity fields from a seed `FAULT_DOOR`; `ordinal` is
one-based for its occurrence and site. The controller injects faults in array
order. A trial is strict only if each planned fault has a same-identity
`FAULT_DOOR` followed by a matching `FAULT_APPLIED` in that order. A target
candidate additionally needs a named, exact `TARGET_THROW` at the selected
site and exception type after the last applied fault. Branch execution and
whether the throw belongs to the observed closure are reported separately;
an incomplete graph cannot hide a real target throw. A passing or failing
JUnit result is recorded separately. A candidate still needs replay and source
review before any new-bug claim. When a prior healthy trace is supplied, the
result also records its exact target throw count, so an injected trigger stays
distinct from an exception already expected by the original JUnit.

Each `result.json` keeps GraphChecker closure occurrence IDs, edge IDs,
coverage sites, gaps, and observed fault doors. The full recorder output is
`graphchecker-raw.jsonl`; the graph consumes only rows between its unique
`WINDOW_OPEN` and `WINDOW_CLOSE`, saved as `graphchecker-trace.jsonl`. This
prevents server shutdown activity after JUnit teardown from entering the
trial's causal graph. Both traces have SHA-256 receipts. Door tiers are
`observed_closure`, `static_may_observed`, and `outside_closure`. Static MAY
membership can guide a later scheduler, but does not add a causal edge or
count as closure coverage. This module executes and verifies **one trial at a
time**; it does not yet own a campaign queue, replay budget, or resume policy.
The caller must give each trial a new output directory and preserve completed
receipts. The old `campaign.py` runner below remains for archived campaigns.

To run a whole per-check campaign, add a bounded budget to the same config:

```json
"budget": {"fault_trials": 80, "seconds": 3600, "max_faults_per_trial": 3}
```

Then run:

```sh
python3 -m Mallory.core.graphchecker_fuzzer \
  --config /absolute/case.json --out /persistent/campaign/case-id
```

The campaign weaves once, runs a healthy original JUnit seed, and enqueues
fault plans only from attributed, typed `FAULT_DOOR` rows. It gives observed
target closure doors the highest priority, then observed doors in Soot's
static MAY scope, with occasional exploration outside both. It samples early,
middle and late repeated I/O occurrences, then adds one later observed fault
to a successful sequence up to the configured depth. New closure nodes,
edges and coverage increase a sequence's priority. A fault that loses the
target is not expanded. The time budget counts actual JUnit trial runtime.

`checkpoint.json` is written atomically before and after each trial. A restart
reconciles a completed active trial, refuses to duplicate a still-running JVM,
and archives an incomplete attempt before retrying its plan. Terminal cases
have `terminal: true` and `summary.json`; restarting one returns immediately.
Every trial retains its exact plan, trace, graph feedback, result and elapsed
time. An exact post-fault target throw is recorded even when the static graph
has a gap. If the healthy JUnit already throws the same exception, the trial
is `needs_differential_review`; only an excess exact throw count is called a
`candidate`. Source review and replay remain necessary for a new-bug claim.
The current runner requires all selected original classes to be present in the
declared compiled-class directories and a completed GraphChecker window to fit
within 256 MiB.

## Legacy campaign runner

Run one configured original cluster JUnit workload in a fresh process per trial:

```bash
python3 -m Mallory.core.campaign \
  --config Mallory/cases/HDFS-01.json \
  --out data/mallory/cases/HDFS-01
```

The case config is a JSON object. Required fields are `case_id`, `system`,
`cluster_test`, `cwd`, `command` (an argv array), `target` (`check_sites`,
`throw_site`, and `exception_class`), and `budget` (`trials`, `seconds`, `max_faults_per_trial`,
`trial_timeout_seconds`). The command must launch the selected cluster test
and its runtime instrumentation. Optional `agent_jar` adds the agent to
`JAVA_TOOL_OPTIONS`; this also instruments Maven's JVM, so a direct forked
JUnit command or explicit test JVM options are preferable when available.
The runner sets `MALLORY_EVENT_FILE`, `MALLORY_PLAN_FILE`, `MALLORY_RUN_ID`,
`MALLORY_SITE_CATALOG`, and optionally `MALLORY_SITE_FILE` for every process.
The catalog is saved as `trials/rNNNN/sites.jsonl` with a SHA-256 in that
trial's result. For Maven Surefire
workloads, set `agent_transport: "surefire_argline"`; the controller appends
the trial-specific `-DargLine=-javaagent:...` to the Maven command and leaves
Maven's own JVM uninjected. The default `java_tool_options` transport is for
direct Java commands and small smoke tests.
For a POM with a hardcoded Surefire `argLine`, arrange an explicit property in
that POM and set `agent_arg_property` to its name (for example,
`mallory.agent.arg`); the runner then supplies `-Dmallory.agent.arg=...`.

Each trial has a `plan.json`, an event trace, stdout/stderr logs, and a
`result.json`. The controller atomically updates `checkpoint.json` and a
case-level `result.json` after each trial. A restart resumes unfinished work;
if the previous test process group is still alive, the controller refuses to
start a duplicate. If a controller died after a process exited but before
writing its result, it retains that partial evidence under `interrupted/` and
reruns the plan.
After analyzing a trial, the controller gzip-compresses the trace and records
both raw and compressed SHA-256 digests and byte counts. It removes the raw
trace only after verifying the gzip round trip. Logs above 1 MiB are likewise
compressed. Each result records `MALLORY_ATTEMPT_ID` when dispatched remotely.

Preliminary configs can set `calibration_only: true`, or the runner can receive
`--calibration-only`, to stop after healthy trial `r0000`. A promoted config
must set `auto_promote_if_healthy: true` and pin the original loaded target
class SHA-256 as `expected_target_class_sha256`. Before fault trial 1, the
controller checks the exact guard and throw IDs in the runtime site catalog,
the loaded class hash and loader identity, named target actors and regions, a
clean healthy target outcome, and an eligible observed I/O door. The receipt
is stored as `runtime_attestation` in the checkpoint and case result. If any
check fails, it does not run a fault trial. Commands may use `{trial_dir}` for
trial-specific temporary paths.

The trace uses `type`, `id`, `seq`, `node`, `epoch`, `occurrence`, `site`.
`TARGET_CHECK` identifies an exact guard branch site. `TARGET_THROW` identifies
the separate bytecode throw site and carries `exception_class`. A legacy
single `site` target is accepted only when the two site names coincide.
If the source says `throw helper()` and `helper()` throws internally, the
caller's `ATHROW` instruction is never executed. Configure a target call rule
for that invocation and use its `@line:callthrow:N` site from the runtime
catalog; it records the exception crossing the call into the target method.
The Java agent names these sites `Class#method(desc)@line:branch:N`,
`Class#method(desc)@line:throw:N`, and `Class#method(desc)@line:callthrow:N`;
take the ordinal from its site catalog.
The target event must belong to a named region occurrence. A healthy run may
visit the target multiple times and on several named logical nodes. The seed
binds the set of named actors and retains a separate backward closure for each
target occurrence. Unnamed startup occurrences are recorded as identity gaps
and do not qualify as target evidence in fault trials.
The compact agent emits `COVERAGE_DEF` rows mapping integer `coverage_ref` to
full coverage IDs, followed by `COVERAGE_SUMMARY` with unique `coverage_refs`
for each `(node, epoch, occurrence)`. Feedback rejects undefined or conflicting
references and unions the resolved IDs globally and for summaries whose
occurrence lies in the target closure. The summary's late sequence number is a
flush time, not the execution time of its individual coverage IDs. Older
string `coverage_ids` summaries and `METHOD`/`BRANCH` rows remain readable.
`DOOR_OBSERVED` carries `door_ordinal`, a one-based counter scoped by
`node`, `epoch`, and exact `site`. Fault plans use these four fields and omit
the occurrence because RPC call IDs can change between test runs. The trace
still keeps the full occurrence for within-run causal edges. Older agents
without `door_ordinal` fall back to exact occurrence and `hit` matching.
Directed multi-fault replays can instead use optional `point.after_fault`
(zero-based earlier fault index), `point.same_node_as` (earlier fault's concrete
node and epoch), and `point.relative_hit` (one-based count of matching doors
after `after_fault` applies). These selectors let a later fault follow a
runtime role without pinning an ephemeral Jetty port. The trace validator
recounts the matching doors and rejects a receipt with the wrong ordering,
node, epoch, or relative hit. Ordinary campaign plans still use exact door
ordinals; a directed replay must be labeled separately from graph-discovered
plans.
`DOOR_OBSERVED` also carries `hit` and optionally
`fault_type`, `fault_types`, and `exception_class`. `FAULT_MATCHED` and
`FAULT_APPLIED` carry the plan's `fault_id`. SEND/RECV require matching
`transport`, `correlation`, `attempt`, `half`, `port`; task handoffs require
`correlation`; state accesses require `object`, `key`, `version`. Optional RPC
`attempt` and `half` must agree when present. The graph accepts only unique
complete message pairs. Missing or ambiguous pairs are counted as gaps.
State probes installed after field or Map calls report sampled versions and
form candidate edges, never proven read-from edges. Their object IDs restart
in each JVM, so a state pair must also match node and restart epoch. Balanced
same-thread region nesting contributes observed parent-to-child and
child-exit-to-parent-continuation edges. An asynchronous task's completion
does not imply a continuation edge on the submitting thread without an
observed join. Solr's `ShardRequestor.call()` return and
`HttpShardHandler.take()` `Future.get()` now emit `TASK_COMPLETE`/`TASK_JOIN`
for the exact returned `ShardResponse` object; the graph pairs only a unique
same-node, same-epoch result. Static candidate sites may
broaden selection but are never reported as observed causal edges.

The scheduler first tries fault doors within the observed target closure,
then doors at static frontier locations. By default it also retains lower
priority exploration doors outside those sets, because instrumentation gaps
could otherwise leave a reachable target with no testable candidate. Set
`explore_outside_closure: false` for a strict ablation. Every trial records
the selection reason.

`allow_node_timeline_guidance: true` adds a lower priority exploration class
for a door observed before an exact target check on the same node and restart
epoch, even when different threads have no matched handoff. Its selection
reason is `node_timeline_candidate`; the feedback records the two event IDs,
thread IDs and sequence numbers. This is a temporal candidate, not a graph
edge, closure member, read-from relation, or positive causal-path report.
When enabled, every fifth fault-trial pick reserves a slot for a queued
timeline candidate; `node_timeline_exploration_interval` changes that interval.
The option defaults to false and must be chosen in a new campaign config.
`actor_miss_replays: N` optionally repeats a single fault selected from the
dynamic target closure or the target node's timeline when it applied, the
target ran afterward, but the target ran on another node. Only faults on a
healthy target actor qualify.
Each plan receives at most `N` such retries, queued below fresh candidates;
the result keeps the `actor_miss_replay` selection reason. The default is 0.
`target_branch_replays: N` similarly repeats an effective single fault when
the target check executes on the faulted healthy target node without throwing.
It records `target_branch_replay` and limits each plan to `N` such retries.
This samples scheduling variation at a relevant fault site; it does not add
an unobserved causal graph edge. The default is 0.

In the archived SOLR-09 healthy trace, the UNLOAD request is submitted from
the target's region to another thread and its task claim is observed, but no
matched completion/join returns to the target thread. The low-level ZooKeeper
reads from the earlier CrashFuzz replay are not configured as fault doors in
that trace. The graph therefore cannot assert an UNLOAD-to-target path.
With the new `ShardResponse` completion/join hooks, a fresh
`DeleteReplicaTest#deleteReplicaAndVerifyDirectoryCleanup` cluster JUnit run
recorded an exact UNLOAD send/receive, task completion/join, and target-check
path. Its five-trial pilot passed offline causal audit, with one observed graph
path door in the healthy run. Of the four fault trials, three did not match the
chosen I/O occurrence and one matched but lost the target. No target exception
was observed, so this pilot validates the graph repair rather than a bug claim.
The Solr adapter now also exposes exact, typed `ConnectionLossException`
doors at collection watch `getChildren` and `getData` reads of `state.json`
by a known server actor. These target reads that can leave a watcher cache
stale when their exception is caught. A separate SOLR-09 cluster JUnit pilot
with the `getData` door observed 17 such reads in its
healthy trace, including one in the target closure and one later same-node
timeline candidate. In three fault trials, one selected read was unmatched,
one matched but lost the target, and a different timeout door matched while
the target stayed nonthrowing. The four-trial archive passed offline causal
audit; it did not reproduce the earlier CrashFuzz candidate.
In the archived SOLR-40 trace, the alias watch door and a later target check
share node3 but run on different threads. Sampled reads of the alias cache do
not prove a read-from relation or the effect of a failed watch refresh. With
the optional timeline rule, this watch door becomes an exploration candidate
while remaining outside the causal closure.

### Target-absent bootstrap for an existing cluster test

Some real cluster tests pass without executing a selected guard, while a fault
may expose it. A **new, separately pinned campaign** may opt in to bounded
target discovery with:

```json
"target_absent_bootstrap": {
  "door_sites": ["exact.Class#io()V@42:door:1"],
  "max_trials": 12,
  "max_doors_per_trial": 16,
  "max_faults_per_trial": 2
}
```

The full config must also pin `expected_target_class_sha256`, keep an exact
`check_sites`/`throw_site` target, and set `auto_promote_if_healthy: true` for
fault trials. Choose `door_sites` from I/O sites actually observed in a fresh,
successful run of the existing cluster JUnit; the list is an explicit search
policy, not an inferred causal relationship. The healthy bootstrap receipt
requires that JUnit passed, the exact check and throw sites were woven into
one loaded target class with the pinned hash, and at least one listed I/O door
has a named actor and replayable identity. An old calibration with zero
`DOOR_OBSERVED` events cannot start this campaign.
`max_trials` must equal `budget.trials` in a promoted config, so the bootstrap
phase cannot silently end a case before its declared full campaign budget.

While the target is absent, feedback records global coverage and exact I/O
doors, but `closure_occurrences` and closure coverage remain empty; the graph
summary says `analysis_skipped`. Each bootstrap mutation adds one fault after
the last applied fault, chooses only a listed observed I/O site, and obeys the
smaller of the global and bootstrap fault-depth caps. A matched fault with no
target can expose another eligible I/O door for the next mutation. If no exact
target is discovered, the campaign ends as `budget_exhausted` or
`queue_exhausted` and reports zero target hits.

The first effective fault trial with an exact target check on a named actor
records `target_discovered_trial` and binds that actor for later trials. Only
its **observed** target occurrence is used to build a backward graph; pending
bootstrap plans are discarded and subsequent mutations use the normal graph
feedback. A target exception still needs the original strict matched/applied
fault, check-before-throw, class, site, node, epoch, and occurrence oracle.
Discovery alone does not prove that the fault caused the target or establish a
new bug. `healthy_seed_valid` remains false because the target was absent;
`bootstrap_seed_valid` separately records the honest bootstrap attestation.
The offline audit rechecks each trial under its binding at that time. Its
`healthy_closure_proven` and `report_gate_passed` remain false for bootstrap
campaigns, since no healthy target closure exists.

For workloads where deeper sequences replay unreliably, optional
`single_fault_breadth_interval: 3` chooses the highest ranked one-fault plan
on two of every three fault-trial picks while one remains queued. Every third
pick uses the usual priority order, so multi-fault sequences remain eligible.
Candidate replays retain first priority. The interval is counted from
completed fault trials and is stored in the immutable case config, making
selection deterministic after checkpoint resume. Omitting the field preserves
the original scheduler behavior. When `validated_recovery_sites` are also
configured, their periodic exploration pick takes precedence over this
breadth preference.

An optional `validated_recovery_sites` list gives higher priority to exact
door sites that retained the target in independent pilot trials. Each row has
`site` and a nonempty `evidence` list of `{trial_result, sha256}` receipts.
The runner verifies each pinned trial belongs to the same case, applies only
faults at that site with exact runtime identity, and reaches the target after
the fault. The loaded target class hash must match when pinned. Such sites
receive `validated_recovery` as their selection reason. Every fifth fault
trial, when available, explores another candidate; configure
`validated_recovery_exploration_interval` to change that cadence. This
priority affects only newly started campaigns; a running checkpoint's config
must stay fixed.

`target_exception_candidate` requires that every planned fault was matched
and applied in order, then an exact guard event precedes the exact target throw
with the configured exception on the same bound node, epoch, and occurrence.
Replays are queued by default, but the result remains a *candidate* pending
source review. Other test failures, hangs, and target loss cannot satisfy the
oracle. The summary leaves `new_bug` null.

Run core contract and archive checks with
`python3 -m unittest Mallory.core.test_core Mallory.core.test_audit`.

## Offline causal audit

Audit a terminal campaign without rerunning its workload:

```bash
python3 -m Mallory.core.audit \
  --campaign data/mallory/cases/CASE-ID \
  --out data/mallory/cases/CASE-ID/offline-causal-audit.json
```

The auditor verifies raw and gzip trace hashes, recomputes the graph and
target oracle from each archived trace, and checks exact runtime identities
for applied faults. It compares eligible door closure membership, closure
occurrences and edges, and coverage/closure novelty against the live result.
The machine-readable artifact includes `report_gate_passed` and separate
integrity, identity, target-claim, and guidance gates. Door membership is
stored as a count and SHA-256 with at most ten differing entries per trial;
the full maps are compared in memory. Only the named audit artifact may be
written inside the case directory; archived campaign results and traces are
read-only.
The independent `healthy_closure_proven` gate requires at least one uniquely
observed causal edge in healthy trial `r0000`'s target backward closure and
at least one named pre-target I/O door with a nonempty path to the target made
entirely of observed edges. The artifact records this as
`healthy_observed_path_doors`. Sampled state edges remain available for
exploration but cannot prove this audit gate. A reached target with a
singleton closure or only a candidate-edge door path cannot pass
`report_gate_passed`.

For a new, separately versioned campaign, `allow_local_timeline_doors: true`
also admits a named I/O door that occurs strictly before an exact nonthrowing
target check in the same node, epoch, and region occurrence. Feedback records
the two event IDs and sequence numbers as `observed_local_timeline`; the
audit reports `healthy_local_timeline_doors` and
`healthy_closure_evidence_types`. This proves local temporal order, not data
flow or a cross-region causal link. The option defaults to false, so existing
campaigns and their audit meaning remain fixed. Create a new config and output
directory for any opt-in run; do not edit a running campaign checkpoint.

For a terminal campaign whose healthy evidence is *only* local timeline
evidence, the future audit also requires one effective fault at a door site
admitted in that healthy run, followed by an exact target check in the same
named node, epoch, and occurrence. It binds the fault, observed door, and
check event IDs and records `same_actor_target_trials`. The older
`strict_target_trials` count only says the target was reached somewhere after
an effective fault; another actor or occurrence can satisfy that count.
Healthy-only calibration needs no post-fault proof. Frozen 5820 campaign
results and releases remain unchanged; a separately versioned re-audit may
change the quality gate for local-timeline-only cases.

## Scoped root contexts for future campaigns

Older agents emit the same `unscoped:<node>:<epoch>:root` occurrence for all
threads and operations on one actor. Reused non-root context tokens can also
merge unrelated threads. Two separately matched handoff edges can therefore
join at an unscoped occurrence without an event-level link between them. For a
new campaign, build the agent from the current instrumentation source and set
`reject_coarse_roots: true` in a **new** case config and output directory.
The new agent adds the JVM thread ID and a bounded segment number to every
unscoped occurrence. It rotates the segment when a region ends or the actor/causal
context changes. `REGION_ENTER` records the exact preceding scoped root as
its parent; the graph accepts that parent only when a prior event belongs to
the same named actor, epoch, JVM thread, and segment. The resulting edge
records local program order, not data flow. Exact RPC/task/state matches
remain separate graph edges. The strict graph rejects edges incident to the
old actor-wide root or an unscoped token without thread/segment evidence,
counting `coarse_root_edge_rejected` or `unscoped_token_edge_rejected` gaps.
This option defaults to false for frozen campaigns; do not change a running
campaign's config or reinterpret its saved feedback under another core.

Migration is per case: pin a new core release and agent JAR by SHA, make a new
config/output directory with `reject_coarse_roots: true`, run a healthy
calibration to verify the exact target and eligible doors, then run bounded
fault trials and audit them with that same core release. Preserve old trial
archives and checklist rows as historical evidence; promote a new result only
after the new audit passes. If the strict healthy graph loses all paths, add
an explicit handoff hook or a separately justified local-timeline calibration.
The current occurrence-level path gate does not establish that every handoff
event precedes a target check within a shared region occurrence; response
handoffs after the target still require a separate event-time path audit.

For a further new campaign, `require_event_time_paths: true` enables that
event-time audit and implies rejection of legacy unscoped aliases. It proves
a door-to-check path only when each cross-occurrence edge has unique producer
and consumer events in increasing trace sequence, and each step within an
occurrence has an increasing sequence on the same JVM thread. The audit
records up to ten exact door/check IDs and edge-event witnesses in
`healthy_event_time_path_sample`. A direct same-occurrence door/check order
has an empty-edge local witness and only qualifies through the separate
`allow_local_timeline_doors` policy. New agents must emit numeric `thread_id`
for this gate; older traces without it cannot pass. Compact coverage summaries
emitted after a run have no per-hit event time, so this strict mode uses them
for global coverage feedback but not proven pre-target closure coverage.
