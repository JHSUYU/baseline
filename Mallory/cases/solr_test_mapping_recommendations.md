# Solr cluster test mapping audit

This is a source-only recommendation for the 21 original Solr cases in `inventory.json`. It does not claim a JVM run, successful calibration, or observed target coverage. The JSON companion lists each recorded selector, a practical alternate when source evidence supports one, and the exact source anchors used here. All paths below are relative to `/users/ZhenyuLi/.graphchecker-sources/solr-8.11.4`.

## Calibration priorities

- **SOLR-01:** Keep `CloudHttp2SolrClientTest#testAliasHandling`. Its `@Before` builds an HTTP-backed `CloudHttp2SolrClient` from a running Jetty URL, and the method issues queries through that client after creating aliases (`solr/solrj/src/test/org/apache/solr/client/solrj/impl/CloudHttp2SolrClientTest.java:112-126,197-249`). The HTTP provider is `Http2ClusterStateProvider`, a subclass of `BaseHttpClusterStateProvider` (`solr/solrj/src/java/org/apache/solr/client/solrj/impl/CloudHttp2SolrClient.java:79`; `BaseHttpClusterStateProvider.java:232-267`). A successful `LISTALIASES` returns at line 251, leaving the line-267 exhaustion throw untaken. Observe the **client actor**; server-only coverage cannot establish this target's reach. `testRouting` is a weaker alternate because its update requests also resolve collection aliases through the HTTP client.
- **SOLR-06:** Keep `TestPullReplica#testCreateDelete`. It creates two shards with three PULL replicas each, checks that PULL replicas do not lead, and reloads the collection (`solr/core/src/test/org/apache/solr/cloud/TestPullReplica.java:129-193`). Every successful PULL core registration evaluates `assert !(isLeader && replica.getType() == Type.PULL)` (`ZkController.java:1310-1315`). The method has `@Repeat(iterations=2)` rather than a single-run annotation; two successful JUnit runs are intended test behavior. `testAddDocs` is an alternate with PULL creation and reload.
- **SOLR-07:** Keep `AddReplicaTest#testAddMultipleReplicas`. It creates an initial NRT core and adds NRT, TLOG, and PULL replicas (`solr/core/src/test/org/apache/solr/cloud/AddReplicaTest.java:59-84`). Their registrations evaluate `cc.getCore(desc.getName())` and the null check (`ZkController.java:1317-1326`). If this selector fails for harness reasons, `AddReplicaTest#test` is a simpler alternate that creates a collection and adds replicas asynchronously (`AddReplicaTest.java:123-169`); `TestPullReplica#testCreateDelete` is a second alternate. Registration executes on embedded node actors.

## Exact guard reachability

`SplitShardTest#doTest` creates a collection and successfully splits shard1 (`solr/core/src/test/org/apache/solr/cloud/SplitShardTest.java:77-92`). It is appropriate for **SOLR-14**: the initial live-node check at `SplitShardCmd.java:163-167` is evaluated with a nonnull znode in a healthy split. `SplitShardTest#testSplitFuzz` is a practical alternate.

**SOLR-15 and SOLR-16 have a source-level healthy-check reachability problem, not a missing cluster test.** At `SplitShardCmd.java:523-524`, the outer condition is true only when the leader znode is null or its ephemeral owner changed. The nested null check at line 536 throws at line 538 if null. Otherwise the changed-owner condition at line 539 is necessarily true and throws at lines 541-543. A healthy, nonthrowing split evaluates the *outer* condition as false and cannot evaluate either mapped inner guard (`#B40`, `#B41`). These two cases need a different seed criterion or a different target predicate before they can be called healthy-guard-reached; a replacement JUnit selector cannot solve this control-flow constraint.

There is also a mapping inconsistency for SOLR-16: `inventory.json` names `#B41` as its target guard, but `SOLR-16.json` lists only `@536:branch:40` in `check_sites`, the same null check used for SOLR-15. The line-543 throw is the changed-owner alternative. Both checks have the source-level reachability problem above; reconcile the guard identity before interpreting a trace.

**SOLR-34 has the same kind of source-level limit.** `TestCoordinatorRole#testSimple` does reach synthetic collection creation, but the mapped `CoordinatorHttpSolrCall.getCore` check is `@139:branch:6`. It is inside `if (syntheticColl == null)` after the creation attempt (`CoordinatorHttpSolrCall.java:113-139`). If the synthetic collection remains null, the nested `createException` check throws on both outcomes (`CoordinatorHttpSolrCall.java:139-147`). A nonthrowing coordinator query cannot evaluate the mapped check. This is distinct from an undiscovered JUnit method.
