# Mallory precision reruns for nine existing terminal checks (v1)

This is a read-only source and trace review, dated 2026-10-09. Event numbers below identify archived example runs; they are **not** stable injection ordinals for a new run. The eight original cases are HDFS-01, HBASE-07/13/14/15, and ZOOKEEPER-01/02/03. HBASE-21 was added after its terminal audit. The canonical results and check locations remain intact. No conclusion here establishes a new bug.

## Common admission and replay rules

1. Create a separately versioned case config, runtime artifact receipt, output directory, and healthy seed. Do not edit a frozen campaign or reinterpret its saved feedback under a different agent/core. Set `reject_coarse_roots: true` and use an agent built from the current instrumentation source, which emits `thread_id` and bounded `root:thread:<id>:segment:<n>` occurrences. See `Mallory/core/README.md`, “Scoped root contexts for future campaigns,” and `Mallory/instrumentation/src/main/java/edu/uva/liftlab/mallory/instrumentation/Probe.java` around `occurrence(Context)`.
2. Admit a fault only when its exact site, runtime actor, epoch, and observed request/call token have a directed observed path to the exact target check. Enforce **time-respecting event paths**: every edge producer precedes its consumer; consecutive edges represent a nondecreasing event sequence; the path reaches a target event after the applied fault. An occurrence-level graph edge alone is insufficient. For example, old HBASE-07 healthy graph could join door event 1780 through a root to response event 31747, even though its selected target check was event 22436.
3. Begin with one exact I/O exception pilot per distinct door. Require a named `FAULT_APPLIED`, effective exception, matching healthy door identity, target check after the fault on the intended actor/occurrence or an explicitly matched retry path, JUnit receipt, and an offline causal audit. If the fault prevents the target, record the lost-target outcome; do not promote it as a retained check. Expand the budget only after a qualifying pilot. Report target exception as a candidate until source and replay confirm the behavior.

## 1. HDFS-01 — root-free healthy path was not exercised

- **Existing JUnit:** `org.apache.hadoop.hdfs.TestPread#testPreadDFS`, source `hadoop-hdfs-project/hadoop-hdfs/src/test/java/org/apache/hadoop/hdfs/TestPread.java:271`. Its normal and non-transferTo positional reads execute the target.
- **Target:** `DFSInputStream.fetchBlockAt(long,long,boolean)` null/empty `LocatedBlocks` guard and `EOFException`, source `hadoop-hdfs-project/hadoop-hdfs-client/src/main/java/org/apache/hadoop/hdfs/DFSInputStream.java:517-518`.
- **Old evidence:** `data/mallory/cases/HDFS-01/trials/r0000/events.jsonl.gz` and `.../result.json`. A `NameNodeRpcServer#getBlockLocations` IOException door at source `hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/NameNodeRpcServer.java:795` was observed on **`hdfs-cluster-1/nn0`, epoch 0, ordinal 3**, event 4553. Its response SEND 4563 paired with client RECV 4566, then the exact `fetchBlockAt` TARGET_CHECK 4568 in the client's named target region. This is a time-respecting root-free healthy path.
- **Why old fault trials do not qualify:** 196 effective fault events hit `DFSInputStream.readBuffer@789` under `unscoped:hdfs-client:0:root`. Six NameNode faults targeted a later `hdfs-cluster-2/nn0`; example r0005 applied there at event 15211 after the final target check, so no target followed. Direct `fetchBlockAt@516` exceptions are inside the target region but likely exit that occurrence before the guard; they are lower priority.
- **Narrow rerun:** After a fresh healthy seed confirms the corresponding `hdfs-cluster-1/nn0` `getBlockLocations` request/response and pretarget door, pilot one server-side `IOException` at the exact matched door. Bind to the actual runtime NameNode actor and RPC correlation, not the literal old event ID or ordinal. Check whether the client retries within the same `fetchBlockAt` occurrence and reaches the guard. The existing HDFS RPC SEND/RECV hooks should suffice if this exact path is retained.

## 2. HBASE-07 — response continuation loses its exact Call context

- **Existing JUnit:** `org.apache.hadoop.hbase.snapshot.TestRestoreFlushSnapshotFromClient#testRestoreSnapshot`, source `hbase-server/src/test/java/org/apache/hadoop/hbase/snapshot/TestRestoreFlushSnapshotFromClient.java:154`.
- **Target:** `HBaseAdmin.restoreSnapshot(String,boolean,boolean)` checks `isTableDisabled` and may throw `TableNotDisabledException`, source `hbase-client/src/main/java/org/apache/hadoop/hbase/client/HBaseAdmin.java:2787-2788`.
- **Old evidence:** In `data/mallory/cases/HBASE-07/trials/r0000/events.jsonl.gz`, the relevant `rs0` `hbase.pb.ClientService.Get` request RECV 22385 precedes `RpcServer.call@447` door 22387 under exact request token 897; response SEND 22430 reaches client RECV 22432, response-ready TASK_SUBMIT 22433, exact TASK_CLAIM 22434 inside the `HBaseAdmin.restoreSnapshot` occurrence, then TARGET_CHECK 22436. The RECV and TASK_SUBMIT are currently emitted at `unscoped:client:0:root`.
- **Narrow rerun:** Keep this JUnit and the existing server I/O door, but select the `ClientService.Get` call whose exact response completion enters the `isTableDisabled` check. The shared future-only HBase hook below must put the parsed response RECV and its completion TASK_SUBMIT into that Call's token context. Pilot a single `IOException`; a different retry/occurrence requires a separately witnessed path.

## 3–5. HBASE-13, HBASE-14, HBASE-15 — one merge workload, three guards

- **Existing JUnit for all three:** `org.apache.hadoop.hbase.master.assignment.TestMergeTableRegionsProcedure#testMergeTwoRegions`, source `hbase-server/src/test/java/org/apache/hadoop/hbase/master/assignment/TestMergeTableRegionsProcedure.java:167`. It submits a real `MergeTableRegionsProcedure` to the MiniCluster executor and waits for completion.
- **Targets:** `MergeTableRegionsProcedure.prepareMergeRegion(MasterProcedureEnv)`, source `hbase-server/src/main/java/org/apache/hadoop/hbase/master/assignment/MergeTableRegionsProcedure.java`. HBASE-13 is the `MetaTableAccessor.hasMergeRegions` guard at about line 495; HBASE-14 is the `RegionState == null` guard at about line 500; HBASE-15 is the `!state.isOpened()` guard at about line 503. Use each case's exact compiled `check_sites` from its immutable config, not source-line approximation.
- **Old HBASE-13 witness:** r0000 `master0` target occurrence on `PEWorker-1` has `ClientService.Get` request SEND 4792 → `rs0` RECV 4797 → `RpcServer.call@447` door 4799 → response SEND 4842 → `master0` RECV 4844 at coarse root → response-ready TASK_SUBMIT 4845 at coarse root → TASK_CLAIM 4846 inside target occurrence → TARGET_CHECK 4848.
- **Old HBASE-14/15 witness:** The corresponding `rs0` `ClientService.Get` door is 4747, response SEND 4790, `master0` coarse-root RECV 4792 and TASK_SUBMIT 4793, exact target-occurrence CLAIM 4794, followed by TARGET_CHECK 4797 (HBASE-14) or 4798 (HBASE-15). Evidence is in each case's `trials/r0000/events.jsonl.gz`.
- **Shared future-only hook:** In `Mallory/adapters/hbase/src/main/java/edu/uva/liftlab/mallory/hbase/HBaseHooks.java:179-187`, `clientResponse(Object call)` already retrieves the exact `CALL_TOKENS[call]` marker and binds the node. Wrap **both** `Probe.receive("hbase-rpc-response", marker.token, ...)` and `Probe.taskSubmit(marker.completionToken, ...)` in `Probe.withCausalContext(marker.token)` inside the existing registered-node scope. The context must be restored on close; never synthesize a response when the parsed Call marker is missing. This removes the actor-wide response root without weakening the physical Call pairing.
- **Narrow rerun:** For each guard, admit only the `rs0` (or freshly observed named region server) `ClientService.Get` door paired to the `MetaTableAccessor.hasMergeRegions` result that precedes the target on the same procedure attempt. One fault may abort the procedure before the later guards; verify each guard independently. Do not use a generic earlier/later `RpcServer.call` merely because it shares an occurrence graph root.

## 6. ZOOKEEPER-01 — old fault and reached target belong to different epochs

- **Existing JUnit:** `org.apache.zookeeper.server.quorum.SessionUpgradeQuorumTest#testCloseSessionWhileUpgradeOnLeader`, source `zookeeper-server/src/test/java/org/apache/zookeeper/server/quorum/SessionUpgradeQuorumTest.java:199`. The helper `makeSureEphemeralIsGone` submits and closes the session through the MiniCluster client.
- **Target:** `SessionTrackerImpl.checkSession(long,Object)` `session.isClosing()` guard / `SessionExpiredException`, source `zookeeper-server/src/main/java/org/apache/zookeeper/server/SessionTrackerImpl.java:319-320` in the patched build. The original source differs by a few lines; the compiled catalog is authoritative.
- **Old evidence:** r0000 target on `zk2`, epoch 0, request `zk-request:2:3`, TARGET_CHECK 165; preceding queue handoff `PrepRequestProcessor#add` event 134 → `#take` 151 → target REGION_ENTER 158. Old quorum archive doors are `unscoped:zk*:0:root`, with no root-free path. In r0001 a quorum `writeRecord` fault on `zk2`, epoch 0, event 187 is followed by a reached target on `zk2`, **epoch 1**, event 367. That later target cannot establish same-epoch or same-request causality for the earlier fault.
- **Narrow rerun:** Apply the existing epoch-fixed `zookeeper.client.request.read` hook design from `Mallory/adapters/zookeeper/install_epoch_fix.py` to an isolated source overlay for this same JUnit. First demonstrate an exact client request door and its `RequestThrottler`/`PrepRequestProcessor` request-object handoffs into the named target occurrence in one epoch. Only then pilot one IOException on that precise client request (or its exact request-correlated quorum packet); reject old-epoch quorum traffic and postfault target on a different request/epoch without a replayed causal chain.

## 7–8. ZOOKEEPER-02 and ZOOKEEPER-03 — exact quorum receive is still emitted at leader root

- **Existing JUnit:** `org.apache.zookeeper.test.QuorumTest#testMultiToFollower`, source `zookeeper-server/src/test/java/org/apache/zookeeper/test/QuorumTest.java:380`. It connects to a follower, issues a multi-create, then reads each znode.
- **Targets:** ZOOKEEPER-02 is `SessionTrackerImpl.checkSession` owner mismatch / `SessionMovedException` around source line 326. ZOOKEEPER-03 is `SessionTrackerImpl.setOwner` absent/closing session / `SessionExpiredException` around line 334. See each case's compiled target catalog.
- **Old ZOOKEEPER-02 witness:** In `data/mallory/cases/ZOOKEEPER-02/full-campaign.tar.gz`, healthy `r0000/events.jsonl.gz`: `zk1` epoch 1 `zookeeper.client.request.read` door 234 → `RequestThrottler` submit/claim 235/236 → follower queue submit/claim 237/238 → quorum REQUEST SEND 240 → `zk2` leader RECV 241 at **`unscoped:zk2:1:root`** → exact `zookeeper.leader.request` REGION_ENTER 242 → leader queue submit/claim 243/246 → target REGION_ENTER 247 → TARGET_CHECK 254. Use the request door before the target. The later request-read door 305 can appear connected in an occurrence-only graph but occurs after this target.
- **Old ZOOKEEPER-03 witness:** Same archive for ZOOKEEPER-03: `zk1` epoch 1 `zookeeper.client.connect.read` door 196 → request queue submit/claim 197/198 → follower queue 199/200 → quorum SEND 202 → `zk2` leader RECV 203 at coarse root → exact leader request REGION_ENTER 204 → leader queue submit/claim 205/208 → target `setOwner` REGION_ENTER 217 → TARGET_CHECK 221. The first `zookeeper.client.request.read` is event 240, **after** this target; choose the connect door for the initial session check.
- **Shared future-only hook:** `Mallory/adapters/zookeeper/src/org/apache/zookeeper/server/quorum/MalloryZkHooks.java:123` currently emits the physical packet RECV while context is root; `Mallory/adapters/zookeeper/install_request_path.py` later scopes the leader request region with that exact packet correlation. Emit the RECV under the packet's correlation context, restoring the previous context afterward, so the unique socket direction/packet ordinal/type/zxid/request-digest match lands on a token-specific occurrence. Preserve the actual `QuorumPacket` identity check in `quorumRequestScope`; do not infer a connection from proximity alone. Then run healthy only with root rejection and chronological graph audit before fault pilots. Use `zookeeper.client.request.read` for ZOOKEEPER-02 and `zookeeper.client.connect.read` from `install_connect_path.py` for ZOOKEEPER-03.

## 9. HBASE-21 — active master flips between healthy seed and trial

- **Actual terminal JUnit selector:** `org.apache.hadoop.hbase.namespace.TestNamespaceAuditor#testRestoreSnapshot`, source `hbase-server/src/test/java/org/apache/hadoop/hbase/namespace/TestNamespaceAuditor.java:666`, as pinned in `data/mallory/cases/HBASE-21/config.json`. The preliminary `Mallory/cases/HBASE-21.json` lists `#testRestoreSnapshotQuotaExceed`, but that test at source line 701 intentionally expects `QuotaExceededException`; it is not the full-run selector.
- **Target:** `NamespaceStateManager.checkAndUpdateNamespaceRegionCount(TableName,int)` region quota comparison and `QuotaExceededException`, source `hbase-server/src/main/java/org/apache/hadoop/hbase/namespace/NamespaceStateManager.java:116-133`. Restore snapshot invokes it through the master procedure.
- **Old healthy path:** `data/mallory/cases/HBASE-21/trials/r0000/events.jsonl.gz` records the sole root-free admitted door: `hbase.pb.MasterService.RestoreSnapshot` RECV 8980 on **`master1`, epoch 0**, exact `RpcServer.call@447` door 8982 (global ordinal 83), procedure scheduler TASK_SUBMIT 8994, worker TASK_CLAIM 8998, and target check 9059 on `master1` in that procedure attempt.
- **Why the old fault missed:** r0001 planned `master1/epoch0/ordinal83`, but the actual active actor was **`master0`**. No FAULT_APPLIED occurred. The matching semantic RestoreSnapshot RECV was 9032, door 9034 on master0, then target 9135 on master0. Thirty-seven other postfault-retained trials do not substitute for an applied fault at the sole healthy root-free door.
- **Narrow rerun:** Keep `#testRestoreSnapshot`. Select the `RpcServer.call` entry associated with a parsed `hbase.pb.MasterService.RestoreSnapshot` request, its exact Call token, and the **runtime observed named master**. A future method-specific IOException door immediately after `HBaseHooks.enterServerCall` reads the request header is preferable if the generic `@447` door cannot carry the parsed method and token. Resolve actor/epoch from the actual MiniCluster RPC receiver; never pre-bind to `master1` or assume the global ordinal remains 83. Pilot one fault, then require an exact scheduler handoff to the target procedure attempt and a postfault target check. Failure to execute the procedure is a lost-target trial.
