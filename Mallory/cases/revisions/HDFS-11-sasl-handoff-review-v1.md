## Required wire order

1. The client obtains its `DataEncryptionKey` in `SaslDataTransferClient.newSocketSend` or `checkTrustAndSend`, then `doSaslHandshake` writes and flushes `SASL_TRANSFER_MAGIC_NUMBER`. Its initial SASL protobuf is sent through exactly one of `sendSaslMessage` or `sendSaslMessageHandshakeSecret`; all branches join before `readSaslMessage(in)` (`SaslDataTransferClient.java:501-545`).
2. `DataXceiver.run` passes the concrete accepted `Peer` to `SaslDataTransferServer.receive` **before** it reads any data-transfer op (`DataXceiver.java:232-238`, `:273`). In the encrypted branch, `doSaslHandshake` validates the magic, parses the initial protobuf with `readSaslMessageWithHandshakeSecret(in)`, and invokes `sasl.evaluateChallengeOrResponse(remoteResponse)` (`SaslDataTransferServer.java:372-395`). The callback can reach `BlockTokenSecretManager.retrieveDataEncryptionKey`: `allKeys.get(keyId)` at line 551 and the selected null check at line 552.
3. Therefore, a delivered-message edge for this check is: **client initial SASL protobuf successfully flushed → server initial SASL protobuf parsed → target check**. Capture `SEND` after the client initial protobuf send returns at the common join before line 544. Capture `RECV` immediately after server line 379 returns and enter a context scope there, closing it in `finally` on every exit of the rest of `doSaslHandshake`. A send-at-`send(...)`-entry or receive-at-`receive(...)`-entry is only connection intent/acceptance, not proof that the SASL message arrived. The server `receive` method can also return without a handshake, so it must not emit a SASL `RECV` for skip branches.

## Correlation and identity

For the existing MiniCluster TCP workload, capture the actual endpoint tuple **before** client encryption wrappers are made: `(client local numeric IP, client ephemeral port, DataNode remote numeric IP, DataNode transfer port)` from the `Socket` in `newSocketSend` and six-argument `socketSend`, or from `Peer.getLocalAddressString()` and `.getRemoteAddressString()` in `peerSend`. Carry the tuple through nested calls in a thread-local stack with `finally` cleanup. On the server use the accepted `Peer`: its **remote** address is the client endpoint and its **local** address is the DataNode endpoint. Set the `Probe` transport and port to a fixed `hdfs-sasl` / `initial-request` pair; both sides must use the same canonical correlation. The `InetAddress addr` passed to private `doSaslHandshake` is insufficient because it omits the client source port. The five-argument `socketSend` delegates to the six-argument method; avoid emitting two sends for that call.

Normalize `SocketAddress.toString()` forms (`hostname/ip:port`, `/ip:port`, bracketed IPv6) to numeric IP plus numeric port, without naïve `split(":")`; reject unresolved, malformed, and missing-port endpoints. Never use a remote DN ID, thread ID, timestamp, or bare destination address as a cross-process join. Include the campaign run ID in the event namespace. A TCP four-tuple distinguishes simultaneous connections, but ports can be recycled after close. Require a unique unmatched sender and receiver connection lifetime/generation; if that cannot be shown, mark the join ambiguous and exclude it from the observed causal closure. A nonce carried in an optional first SASL protobuf field is the stronger general solution: GraphChecker's Hadoop shim uses a UUID correlation and the GraphChecker tree carries SASL context in `datatransfer.proto`. A wire nonce is necessary for Unix-domain peers or any case where the endpoint tuple is not unique.

`BasicInetPeer` and `NioInetPeer` obtain both address strings from their backing TCP `Socket`. `EncryptedPeer` delegates both getters to its enclosed peer, so encryption does not erase endpoint identity; nevertheless, the hook should capture the unwrapped peer before handshake. `DomainPeer` returns `unix:<path>` and `<local>`, which do not uniquely identify a connection, and should be ineligible for tuple-only joining. SASL's resulting `IOStreamPair` wraps streams, not the original TCP endpoint; do not attempt to reconstruct endpoints from the encrypted streams.

The current HDFS adapter's `DataXceiver.run` node scope is still needed to name the exact DN actor/epoch before the handshake. The cross-process message edge carries the *request's* causal context; it does not imply a shared-field dataflow edge from the NameNode key update to the DataNode key map. The `allKeys` check's data provenance remains a separate question.

## Minimal verification gate

Use the existing `TestEncryptedTransfer#testEncryptedReadDefaultAlgorithmCipherSuite*` JUnit method with the established isolated Surefire wildcard selector. It creates/restarts a `MiniDFSCluster` with encrypted transfer and block tokens, then reads the file and checksum. The class is parameterized with a normal resolver and a trusted resolver; the trusted variant may skip SASL. Require nonzero JUnit executions, an exact nonthrowing selected target on a **named DataNode**, a client initial-message `SEND` and server initial-message `RECV` with the same canonical correlation, a graph edge from that concrete send to the target's region, and zero healthy selected throws. Inspect event IDs, transport, endpoint tuple, node epochs, and matched connection generation; do not infer an edge from temporal proximity alone. Then run a bounded fault pilot that preserves the target after an injected exception before any full 80-trial campaign. Keep the historical zero-test HDFS-11 calibration as negative runner evidence.
