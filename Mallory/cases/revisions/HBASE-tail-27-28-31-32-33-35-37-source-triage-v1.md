## Source evidence and scope

### HBASE-27

`TestClusterBootOrder.java:103-108` starts an RS before starting the master. `HRegionServer.java:725-729` starts the master address and cluster status trackers, and `:1005,1009` waits for them in `blockAndCheckIfStopped`; `:1049-1056` checks `this.stopped` after a timed wait returns null. `ZKNodeTracker.java:78-94` performs `ZKUtil.watchAndCheckExists` and possibly `getDataAndWatch` on tracker start, while `:125-165` waits and may recheck existence. Thus the mapped JUnit reaches the exact startup role, and the missing eligible door is an instrumentation/observed-path issue rather than a workload mismatch. Do not infer that an exception on a ZooKeeper read will retain the selected guard: the tracker can abort or continue, which needs a bounded pilot.

Prior `data/mallory/calibration_v2/HBASE-27/result.json`: 37.793 s, JUnit 1/1 pass, target bound to `rs0`, 25 observed door events, **0 eligible pretarget doors**, `healthy_no_injectable_door`. Next: instrument the specific tracker/ZK call path in an isolated runtime, require fixed-core observed-path audit and a postfault target-retained pilot before any full campaign. The current JUnit is more specific than boot-master-first for this wait.

### HBASE-28

`TestInfoServers.java:49-63,84-95` enables master and RS info servers at ephemeral ports, starts MiniCluster, then fetches their pages. Startup executes `HRegionServer.putUpWebUI` on the RS and HMaster. `HRegionServer.java:2467-2497` obtains `addr` from `hbase.regionserver.info.bindAddress` or `hbase.master.info.bindAddress`, checks local address at @2482, then starts `InfoServer`. A network or file exception after this branch cannot change the value already read from local configuration. An exception from `InetAddress.getByName(addr)` exits before the selected false predicate. The old healthy calibration reached @2482 twice with unknown actors and 25 eligible doors, but was rejected for missing runtime identity. That identity repair would not make this check a remote coordination check. No better existing cluster JUnit that varies the bind address was found in the source search; keep it as a likely static-screen false positive, with no fault campaign admission based only on reach.

### HBASE-31

`TestRegionMove.java:76-127` runs on a two-RS MiniCluster, assigns and moves regions, and deliberately rejects moves of offline/disabled regions. `RSRpcServices.java:2008-2014` compares the RPC request start code with this RS's `serverName` before open/close procedure handling. The JUnit's expected `DoNotRetryRegionException` and `DoNotRetryIOException` are not themselves the selected wrong-start-code exception. Independent fixed-core `data/mallory/calibration_v2/HBASE-31/result.json` reports 37.434 s, JUnit 1/1 pass, named `rs0`,`rs1`, 149 eligible doors, valid runtime attestation and no selected throw. This mapping is already sufficient; retain current ownership/configuration and classify any later exact throw against the stale-endpoint request semantics before calling it a bug.

### HBASE-32

`TestRegionReplicaFailover.java:76-86` enables replication and wait-for-primary-flush on a three-RS MiniCluster with three replicas. The original `#testLotsOfRegionReplicas` at `:315-345` creates 60 regions with 10 replicas each; its old calibration was `healthy_seed_invalid` after 63.213 s, despite 3,369 doors. `#testSecondaryRegionKill` at `:202-241` instead writes 1,000 rows, aborts the RS hosting replica 1, waits for that replica to reopen and become readable, then restarts an RS. The test comment explicitly states that reopening asks the primary to flush. Source chain: `HRegionServer.java:2654` calls `triggerFlushInPrimaryRegion` after open; `:2779-2805` submits `RegionReplicaFlushHandler` for a secondary; `RegionReplicaFlushHandler.java:115-137` makes `FlushRegionCallable` RPC, and only its `IOException` catch evaluates the selected guard. Probe this existing test for named handler/method execution and observed primary RPC. **A normal passing run may never execute exact @130**, so the current healthy exact-check gate may still reject it. An injected RPC exception could make @130 reachable, but this is a separate fault-induced-target policy decision, not evidence from a healthy seed. `#testPrimaryRegionKill` is less direct for reopening a secondary.

### HBASE-33

`TestTokenAuthentication.java:418-426` generates a token and immediately retrieves its password through the same `secretManager`; `AuthenticationTokenSecretManager.java:133-141` reaches the selected watcher-aborted check only after `allKeys.get(identifier.getKeyId())` returns null. The test does not remove that key. `TestZKSecretWatcher.java:133-167` does exercise key roll/expiry/removal across MiniZK watchers, but does not call `retrievePassword`; the explicit `retrievePassword` call search in `hbase-server/src/test` found only `TestTokenAuthentication.java:424`. The exact required sequence would be: issue token under key K, remove or expire K from the verifier's `allKeys`, retain the token, abort the verifier watcher, then verify it before token expiry. No existing MiniCluster test located composes this sequence. Treat the old 7.148 s `healthy_seed_invalid` as no target evidence and hold under the existing-test-only workload rule, rather than spending fuzz budget on a same-key success path.

### HBASE-35

`TestHBaseFsckReplication.java:74,82,90` invokes `doFsck` three times for replication queue checks; old calibration saw the selected branch three times, but timed out after 187.605 s and had unknown actor. `TestHBaseFsckMOB.java:102-125` starts a one-RS MiniCluster, corrupts a MOB HFile, and invokes `HbckTestingUtil.doHFileQuarantine` once at :122. `HbckTestingUtil.java:85-90` calls `HBaseFsck.exec`; `HBaseFsck.java:3748` calls `onlineHbck`; `:799` calls `onlineConsistencyRepair`; `:675` calls `loadMetaEntries`; `:2660-2720` scans meta and checks for duplicate encoded-region entries. This is a source-supported shorter route to the exact visitor, conditional on HBCK reaching online consistency repair. Try one isolated healthy calibration with a pinned timeout, named HBCK/client actor, and fixed-core observed-path audit. The duplicate-entry throw requires duplicate meta state; a generic I/O exception does not prove it is a coordination bug.

### HBASE-37

`TestRSStatusPage.java:94-97` calls `HMaster.getActiveMasterInfoPort` after starting a one-RS LocalHBaseCluster. `HMaster.java:3126` delegates to `ActiveMasterManager.java:164-170`, which calls the selected static `MasterAddressTracker.getMasterInfoPort(watcher)`. `MasterAddressTracker.java:197-207` reads the master-address znode via `ZKUtil.getData` at @200 and checks null at @205. The old calibration reached @205 with unknown actor and 39 doors; v5b has a staged master-watcher binding, but no fresh exact named healthy evidence yet. The immediate @200 `ConnectionLossException` would leave via the method's `KeeperException` path before @205; a target-retained pilot needs an earlier observed path fault that leaves `getData` returning null, not merely an exact injection at @200. `ActiveMasterManager` catches this IOException and returns port 0, so an exact throw alone is not a user-visible bug. `TestGetInfoPort` calls an instance tracker method and is a weaker match than the current selector. HBASE adapter owner is handling watcher binding; no parallel JVM/config work here.
