# HDFS-48 v5: bounded rename pre-send fault

The pinned v4 healthy receipt (`0fe0af3ad2ac745fc12cadcd0c20237012ddf232db5b0a8f9e94edc55e2c3067`) records JUnit 1/0/0 and one exact `hdfs-client` rename pre-send door followed by a same-token `hadoop-ipc` SEND, nn0 RECV, and the exact nonthrowing `INodeDirectory.replaceChild` check. The v4 archive SHA is `b6a6e56ccef4992b18b960f8d5731f656da8cbb268232fd88d2b066277524974`. This package leaves the v4 source, class, adapter, and healthy evidence unchanged.

The v5 controller reruns a fresh healthy seed, then admits **at most one trial with one typed `java.io.IOException`** at `hdfs:client-send-rpc-request:rename`, ordinal 1, on `hdfs-client` epoch 0. Generic auto I/O doors and outside-closure exploration are disabled. The controller has a 420-second budget, a 180-second per-trial timeout, and a 480-second outer watchdog. It uses the same isolated Hadoop source and the same node2 HDFS lane lock. The runner requires a separate dispatch `MALLORY_DISPATCH_ADMITTED=1`; staging it is not a GO.

`audit_full.py` demands exact DOOR_OBSERVED → FAULT_MATCHED → FAULT_APPLIED identity, actor, epoch, thread, occurrence, and order. It rejects a request SEND between the failed pre-send attempt and the retry door. A retry must produce one request SEND with a known token, unique nn0 request RECV and response SEND, and one client response RECV. The exact nn0 target check must carry that token and be reached from the retry door through the matching observed RPC edge. A target throw on that token is only an exception candidate for source review; it is never a new-bug claim.

The test first calls `root.replaceChild(dir2, mockDir2, ...)` in the client thread, then calls `hdfs.rename(foo, newfoo)` at line 1363. Only the latter's nn0 check counts. At `INodeDirectory.java:356`, the selected `checkState` compares `oldChild` with `children.get(i)` or the doubly dereferenced reference node. The failed pre-send request cannot directly mutate that NameNode operand because it is never queued. A later exact target exception would require review of the nn0 `oldChild`, child array entry, and reference chain for the retry token and of the test's mock `addChild` behavior. Temporal co-occurrence alone cannot establish that the one fault changed those operands.

The source-defined risk is `Client.getConnection` adding the first `Call` to `Connection.calls` before `sendRpcRequest`; the method-entry fault runs before serialization and queueing. `Client.call` rethrows a send `IOException` without removing that call. The retry policy in `RetryUtils` handles local `IOException`; the patched test enabled `dfs.client.retry.policy.enabled` and `20,1` before cluster creation. `Client.stop` waits for connections to close, and `Connection.close` can clean outstanding calls. The audit therefore records clean fault-trial process exit, timeout, JUnit result, and the pending-call cleanup warning separately. It does **not** assert that a live pending-map count was observed. A warning or exact target throw requires source review before interpretation.

No HDFS JVM has been started for v5. `preflight.py` and `test_offline.py` are read-only static checks. Dispatch must copy the SHA-sealed package and issue a separate GO for node2 before `run_one_fault_full.sh` is used. A terminal audit must be archived before any checklist change.
