## HDFS-26 typed I/O path

`BPServiceActor.connectToNNAndHandshake` obtains `NamespaceInfo` through `retrieveNamespaceInfo`. Its `versionRequest` call at line 260 is typed as `IOException`; both `SocketTimeoutException` and `IOException` are caught and the request retries after a five-second wait while the actor runs. That handshake precedes block-pool storage recovery and `BlockPoolSliceStorage.doRollback`. The site file includes this explicit typed RPC door. A completed retry, a matched reply, a named DataNode, and an event-time path into the exact target are **runtime gates**, not claims from source alone.

`BlockPoolSliceStorage.doRollback` reads `previous/VERSION` through `StorageInfo.readPreviousVersionProperties` before the guard. The site file also includes `Properties.load(InputStream)` at line 272 for diagnostic file-read ancestry. A thrown file-read `IOException` can abort startup, so this door is not a retained fault candidate without separate evidence.

The staged selector extends the already built HDFS-26 identity-overlay healthy config with those two explicit doors and `StorageInfo` instrumentation. It requests exactly one fault-free `TestDFSRollback#testRollback` run and pins the exact target, agent, adapter, core, and site file. The result gate requires Surefire 1/0/0/0, exact nonthrowing target events only on a named `hdfs-cluster-*/dn*` actor, bytecode attestation, a complete trace, a frozen-core offline causal audit, and a version-request door in the observed target closure. The generic presence of an unrelated I/O door does not admit the run.

Dispatch must grant an isolated HDFS source/build lane before a live healthy run. This revision grants no fault or full campaign. HDFS-31 and HDFS-32 remain source/identity/fault-model gaps pending their own healthy evidence.
