# HDFS-33 target-retention review

Case: `DataStorage.VolumeBuilder.build()` line 259, `assert bpStorage != null`
in Hadoop 3.4.3 (`9d50c6884666e794e45102260a4017bb31802e1b`). The existing
cluster test `TestDataNodeHotSwapVolumes#testAddOneNewVolume` starts one
NameNode and one DataNode, then adds one new volume. Its archived fault-free
run passed JUnit 1/0/0 and reached the selected check, but reported the target
actor as `unknown`. The pinned healthy-only v2 package in
`../hdfs33-34-fresh-healthy-v2/` still needs a fresh node2 JUnit to establish
the named DataNode. Its static and node2 preflight receipts passed.

## Data and fault order

1. `DataStorage.prepareVolume` lines 340–353 creates a `VolumeBuilder`, calls
   `StorageLocation.makeBlockPoolDir`, then `getBlockPoolSliceStorage`, whose
   synchronized implementation inserts the block-pool ID into
   `bpStorageMap` at lines 1409–1417. It next loads the block-pool directory
   and records it in the builder. Any thrown `IOException` prevents the
   builder from being returned.
2. `FsDatasetImpl.addVolume` lines 507–562 catches a failed `prepareVolume`
   and rethrows. Later file-I/O failures while building the temporary volume
   map are collected and thrown before `builder.build()`.
3. The configured diagnostic door is `DiskChecker.checkDir` from
   `StorageLocation.makeBlockPoolDir` line 276. That method catches its
   `IOException`, but an injected exception skips directory creation. The
   later `BlockPoolSliceStorage.loadStorageDirectory` lines 162–172 rejects a
   nonexistent block-pool directory; then the selected check is not reached.
   The healthy-only run can measure this door and its actor; the door is not
   yet an admitted target-retaining fault point.
4. `DataNode.shutdownBlockPool` lines 2147–2165 calls
   `DataStorage.removeBlockPoolStorage` line 1422, the source path that could
   remove the map entry after `prepareVolume` inserted it. This requires a
   concurrent block-pool actor shutdown between preparation and
   `VolumeBuilder.build`, with the same DataNode, `DataStorage`, and block-pool
   ID. The selected test does not explicitly request such a shutdown.
5. A generic heartbeat `IOException` in `BPServiceActor.offerService` is
   caught and retried at lines 786–789, so it does not establish the removal
   path. A `RemoteException` whose `className` is `UnregisteredNodeException`,
   `DisallowedDatanodeException`, or `IncorrectVersionException` instead sets
   `shouldServiceRun=false` at lines 772–780; actor cleanup can then call
   `BPOfferService.shutdownActor` lines 466–481 and remove the block pool.
   Mallory's current `Probe.exceptionFor` only constructs exception classes
   with a one-string or no-argument constructor. Hadoop's `RemoteException`
   requires the `(className, message)` constructor, so this specialized RPC
   response cannot currently be generated by the pinned exception injector.

## Admission decision

Run the existing healthy-only v2 calibration when dispatch grants the node2
HDFS lane. Require JUnit 1/0/0, the exact nonthrowing check on a named
DataNode, and a typed pretarget door. Do not promote the current
`DiskChecker.checkDir` door to a full fault campaign on the strength of
healthy reachability. A future specialized remote-response fault requires a
separately pinned injector revision and an observed same-actor event-time
window that retains the target. No new bug is identified by this source
review.
