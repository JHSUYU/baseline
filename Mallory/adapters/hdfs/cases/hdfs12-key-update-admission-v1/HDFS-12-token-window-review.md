# HDFS-12 token-key timing review

The source supports a **conditional timing window**, not an observed missing-key failure. The selected check reads `allKeys[identifier.keyId]` at `BlockTokenSecretManager.retrievePassword:509-511` and throws at line 514 if null. It rejects an expired token first, so any missing-key pilot must use a token still valid at that lookup.

## Test sequence

`TestEncryptedTransfer#testLongLivedClient[0]` uses the parameter with no trusted-channel resolver. `writeUnencryptedAndThenRestartEncryptedCluster` first writes and checks a file in an unencrypted MiniDFSCluster, shuts it down, enables data-transfer encryption and block tokens, and restarts the cluster over the same storage directories. Registration imports the NameNode's exported current and next block keys into the DataNode. The test then sets the NameNode key-update interval and token lifetime to two seconds, clears the NameNode's `allKeys` map for testing, reads the file and checksum, sleeps 15 seconds, and reads both again. Clearing the NameNode map does not directly clear the DataNode map. The server-side SASL handshake uses `BlockPoolTokenSecretManager.retrievePassword`, which delegates to the selected method. This source path has not yet been observed with the new indexed selector.

The NameNode's `HeartbeatManager.Monitor` wakes every five seconds. If the configured two-second interval has elapsed, `BlockTokenSecretManager.updateKeys` promotes its previous `nextKey` and creates a new next key; the monitor marks each DataNode as needing an update. `DatanodeManager` puts `DNA_ACCESSKEYUPDATE` in a heartbeat response and `BlockManager.addKeyUpdateCommand` clears that need flag. The DataNode command processor applies the exported keys with `BPOfferService.processCommandFromActive -> BlockPoolTokenSecretManager.addKeys`. The initial DataNode key set already contains one future key. Therefore a missing key after the **first** promotion requires that the DataNode miss the update carrying the *new* future key and the NameNode then promote that key on a later monitor pass.

## One and two pre-call faults

The explicit Mallory door runs immediately before `DatanodeProtocolClientSideTranslatorPB.sendHeartbeat`. `BPServiceActor.sendHeartBeat` has already scheduled the next heartbeat at that point. Its `IOException` catch sleeps at most one second and continues; the next RPC is sent when the scheduler's next heartbeat time arrives. The default heartbeat interval is three seconds. Because the injected exception occurs before the RPC, the NameNode does not clear `needKeyUpdate`; a later successful heartbeat can deliver the command. This is a **delay**, not permanent command loss.

One fault can create a candidate window if it skips the only scheduled heartbeat between two five-second NameNode monitor passes: the first pass creates a new next key, the second promotes it, and a token using that key reaches the DataNode before the next successful heartbeat. For illustration, if the first pass is at 5.0 s, a heartbeat at 7.9 s is faulted, the next is due at 10.9 s, and promotion occurs at 10.0 s, a token checked between 10.0 and 10.9 s can find the DataNode stale. These are illustrative phase values, not measured test times. A two-fault sequence on the same actor can skip two consecutive due heartbeats and widen the interval. A successful update between faults or before the target closes the hypothesized missing-key path. The existing test's 15-second sleep spans roughly three monitor sleeps, but scheduling, token mint, and DataNode lookup phases remain unknown.

Writing `R1` for the first key update that exports new next key `k`, `R2` for the later promotion of `k`, and `H1,H2,H3` for successive scheduled DataNode heartbeats, a one-fault candidate needs `R1 < H1 < R2 < H2` with `H1` faulted and no intervening successful update. With nominal three-second heartbeat spacing and five-second monitor spacing, that requires `H1` to fall more than about two seconds after `R1`. Two faults at `H1` and `H2` can leave the first success at `H3` after `R2`; the observed timestamps, not these nominal intervals, decide eligibility. The target must execute after a NameNode token with key ID `k` is minted and before a successful DataNode update carries `k`.

## Proof and pilot gates

The healthy config now targets the historical nontrusted `[0]` parameter exactly and enables map-state observations. Its indexed Surefire selector is itself unverified: **zero tests or a different executed method fail admission**. A valid healthy seed needs one passing JUnit, the exact nonthrowing target on a named DataNode/epoch, its integer token key ID and map object, a nonexpired token, and a strict root-free path from a successful heartbeat's key command through `addKeys` to the target lookup. The pinned map probe records keys and sampled versions, but not the `Map.get` result or removals by iterator; the branch supplies the result. The bridge also lacks a typed block-pool-ID and token-expiry binding at this SASL lookup. If those identities cannot be established from structured evidence, the healthy proof stays open and no pilot begins.

After that gate and dispatch lane admission, the proposed pilot is capped at **two one-fault trials, then at most two two-fault trials**, all on the same named DataNode epoch with only the explicit heartbeat door. A pilot must show the NN's R1 new-next key, R2 promotion, token key ID, no intervening DN `addKeys` for that ID, valid token, matched fault, selected check/throw, and exact event-time joins. A passing or recovered JUnit with a selected throw is a research observation; this plan makes no product-defect or full-campaign claim. The machine-readable contract is in `HDFS-12-token-window-proof.json`.

## Source-only observation overlay

The isolated `overlay/` adds `HDFS12_KEY` events without logging key bytes. The NN monitor is scoped through its registered namesystem. A true `updateKeys()` return emits current and next IDs; the monitor's `setNeedKeyUpdate(true)` emits the new next ID with the descriptor's DataNode UUID. Command construction reads the actual queued `KeyUpdateCommand` and emits its exported key IDs with that UUID before the NN clears the flag. The DN's normal `addKeys` return emits each imported ID under its named DataNode epoch. The selected `allKeys.get` receives a pre-call event after expiry rejection; NN token creation and the DN lookup emit a SHA-256 digest of the token *identifier* bytes, key ID, block-pool ID, and expiry. The digest joins one minted identifier to one lookup without serializing password or key bytes. `BPServiceActor.sendHeartBeat` emits block pool, DataNode UUID, and actor object reference at method entry; the exact call-site `DOOR_OBSERVED` proves the attempt reached the selected RPC. All rows inherit Probe's request context, named actor/epoch, thread, and monotonic timestamp. Reflection or identity failures emit a gap event and reject admission.

`audit_timeline.py` requires the indexed JUnit XML to contain exactly one `testLongLivedClient[0]` case. Its healthy gate requires a named nonthrowing selected branch, one valid token digest minted on the NN, matching command and DN `addKeys` for that key, and strict event-time graph paths command→addKeys→target. Its bounded pilot gate requires a prior SHA-bound healthy receipt, then checks the same block pool, token digest, key ID, DN epoch, descriptor UUID, and BPServiceActor reference across R1<H1<R2<H2. It rejects a prior DN `addKeys(k)` and records a timing-only result when the matched fault lacks a strict graph path to the selected target. These are future gates: no `[0]` JUnit resolution or healthy path has yet been observed, and the overlay has not been compiled or run.
