# HDFS-48 v6 sealed-pilot continuation

This package derives a fresh v6 checkpoint from the sealed v5 campaign without rerunning v5 JUnit trials. The v5 archive SHA is `78e935277aa479bb0f85879b4f35c3764b7318b8bf9584f523860321e839abab`; receipt SHA is `9c1316fbd336fb053bb91ab12a81bc56dc966e497ede43ef8b1680efe0c57828`. Its one-fault result passed strict actor/epoch/ordinal, retry token → nn0 RPC → exact nonthrowing target checks, and JUnit 1/0/0. The v5 `budget_exhausted` checkpoint has an empty queue because its budget allowed only one fault per trial. Its r0001 trace has an exact second in-closure rename door at ordinal 2 after the applied fault. With a max-three-fault budget, the scheduler produces the two-fault signature `0110700bcebade910fc2` from that door.

`seed_continuation.py` verifies every SHA-bound member in the v5 archive and independently checks the terminal summary, strict audit, and core audit. It extracts the original two trial artifacts into a new output directory, saves original result JSON under `provenance/v5`, and applies the pinned core release's `_apply_result` to reconstruct the v6 checkpoint. It requires completed trials `[0,1]`, next trial 2, and exactly one queued plan with ordinals `[1,2]`. The recorded v6 config has an 80-trial, 3600-second, max-three-fault budget and a 180-second trial timeout. The validated recovery site is the same method-specific client rename pre-send door, backed by the SHA-pinned v5 fault result. No generic or outside-closure door is admitted.

`strict_policy.py` verifies each planned `java.io.IOException` has a unique observed/matched/applied receipt on the same client actor, epoch, thread, and occurrence, in ordinal order. It rejects a request SEND from any failed pre-send attempt. It requires a final retry door, a known request token, unique request/response handoff, and the exact nn0 target check reached through that token's observed RPC edge. Only a clean JUnit 1/0/0 trial with this strict path earns coverage, closure, or edge novelty and may grow the queue. A trial with an invalid path is recorded with zero novelty and cannot produce descendant plans or automatic candidate replays. An exact target throw is a source-review candidate, never a new-bug claim.

The patched test retains `dfs.client.retry.policy.spec=20,1`. In the pinned Hadoop `MultipleLinearRandomRetry.searchPair`, `curRetry > numRetries` advances past a pair; the source therefore permits retries for `curRetry` 0 and 1 and fails at 2. Two local pre-send faults may leave a third request attempt to reach the check; three faults likely exhaust this policy. This is a source prediction to check against the v6 trace, not an observed v6 outcome. The first failed `Client.Call` may remain in `Connection.calls` until close; terminal audits must still check timeouts, test exit, and any cleanup warning. The pre-send fault itself never queues a NameNode request or changes the target operands directly.

`run_full_node2.sh` requires a separate dispatch GO, node2 host, and the exclusive HDFS lane lock. It verifies the SHA seal and prepared source, seeds the checkpoint only if the v6 output does not exist, then resumes the pinned campaign under a 3900-second outer watchdog. `audit_terminal.py` reports strict valid trials, invalid zero-novelty trials, exact target throws, and provenance. This staged package is GO=false; no v6 JVM has run.
