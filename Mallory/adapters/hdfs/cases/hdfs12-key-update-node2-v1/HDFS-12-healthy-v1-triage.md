# HDFS-12 indexed healthy seed: causal gaps

The isolated node2 run executed exactly one `TestEncryptedTransfer#testLongLivedClient[0]` JUnit case, which passed. `BlockTokenSecretManager.retrievePassword(BlockTokenIdentifier)` reached its selected `allKeys.get(keyId)` check four times on `hdfs-cluster-2/dn0`, with no selected throw. This proves target reach only. Frozen core `fa5f3bde` reports zero observed-path doors and rejects healthy promotion. No fault trial was run.

## Three distinct issues

1. **JUnit parser:** The XML classname is `org.apache.hadoop.hdfs.TestEncryptedTransfer(mallory_0000_2c6dd471a09f4d12bffe172ba96c3cf1)`, with method `testLongLivedClient[0]`. `audit_timeline.py:junit_method` compares the classname to the unsuffixed Java class, so it rejects a correctly selected JUnit case. A case-local auditor revision should accept the exact expected class followed only by the pinned Surefire `mallory_<hex>` suffix and still require one case and the exact indexed method. The raw XML SHA is in the receipt.

2. **Repeated token mint events:** Trace IDs `HDFS-12-r0000:271` and `:272` have the same identifier digest, key ID, expiry, NN actor, request token, and thread. The same pattern appears at `:295` and `:296`. The `createPassword(BlockTokenIdentifier)` bytecode has one return hook, so these are two real calls with the same identifier bytes, not duplicate instrumentation from one return. `audit_timeline.py:minted` currently requires one matching row and rejects both later lookups (`:288`, `:306`). An auditor revision may group only fully equal token identity, expiry, actor, request, and key ID as an equivalence class; it must retain the individual event IDs and establish a causal delivery witness for the selected lookup. It must not silently delete a call or pair by key ID alone.

3. **Handoff and state edges:** The source hook `Hdfs12KeyHooks.heartbeatAttempt` invokes `BPOfferService.getBlockPoolId()` through `Class.getMethod`; that method is package-private (`BPOfferService.java:227`). Reflection fails, producing seven `identity_gap_dn_heartbeat_attempt` rows and unknown-actor heartbeat doors, including door `:196` before named DN request SEND `:197`. Read the method through a declared-method walk with `setAccessible(true)`, then bind the already registered `BPServiceActor.dn` before the door. On the completed reply, NN command rows `:199`–`:201` and response SEND `:202` use request token `...:27:0`, but DN response RECV `:203` is `node=unknown`. `HdfsHooks.responseConsumerEnter` receives the translator, whose `dn` field is absent; unlike `rpcSend`, `rpcResponseConsumed` does not fall back to the enclosing `ACTOR_DATANODE`. Use that exact thread-local actor only when the translator has no registered owner, and verify one request/response token and named DN. TASK_SUBMIT `:204` and TASK_CLAIM `:205` match, but `dn_add_keys` `:210`–`:212` is in a different occurrence under the reply token with no observed parent edge from `:205`. A balanced command-processing region or equivalent explicit task-parent handoff is needed. Finally, `addKeys` writes `BlockTokenSecretManager.allKeys` under the manager monitor (`BlockTokenSecretManager.java:224–235`), and `retrievePassword` reads the selected key under the same monitor (`:501–510`). The current graph treats the generic map write/read as a *candidate* state edge. A strict path to target requires an exact observed read-from relation for the same manager instance and integer key ID, including intervening writes/removes, or another actual observed path. Equal key IDs and timestamps alone are insufficient.

The first two repairs make the healthy evidence parseable but do not satisfy the graph gate. A new isolated adapter/auditor version should be tested with a fresh healthy run, then show event-time paths `NN command → response SEND → named DN RECV → task submit → task claim → addKeys → exact selected lookup/target`, with no coarse-root join. Keep this v1 raw trace and negative audit unchanged. There is no bug claim.
