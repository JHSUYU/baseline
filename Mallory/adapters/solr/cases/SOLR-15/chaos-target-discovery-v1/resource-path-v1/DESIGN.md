# Future Solr ZooKeeper resource-path observation

This is a source-only proposal. `resource-observation.patch` applies to the current Mallory instrumentation source, but it has **not** been applied to that source, built, or used by a JVM campaign. The active agent release, v38 adapter JAR, frozen target-absent core, and SOLR-15 configs remain unchanged.

## Why the current trace lacks the path

`MalloryTransformer` currently inserts `Probe.beforeDoor(site, exceptionClass)` before selected I/O calls. `Probe.beforeDoor` records site, node, epoch, occurrence, hit and door ordinal. Neither that event nor `FaultPlan.Point` includes a resource path. The frozen core's feedback retains the door's site and actor, but no path. Therefore the existing SOLR-15 chaos healthy gate can attest an observed native `exists` call on a named node, but cannot tell whether it read the parent leader's `/live_nodes/<node>` znode.

Solr 8.11.4 `SolrZkClient.exists(String,Watcher,boolean)` calls `keeper.exists(path,wrapWatcher(watcher))` inside `ZkCmdExecutor.retryOperation` at source line 301. `getData(String,Watcher,Stat,boolean)` similarly calls `keeper.getData(path,wrapWatcher(watcher),stat)` at line 349. The pinned classfile has one instance `lambda$exists$2(String,Watcher):Stat` and one instance `lambda$getData$6(String,Watcher,Stat):byte[]`; the first argument, `path`, is local slot 1 in both. `bytecode_preflight.py` verifies those descriptors, access flags, class SHA, source SHA and source lines without a JVM.

## Minimal event change

The patch changes only future instrumentation source. For those two exact SolrZkClient lambda descriptors and matching `SolrZooKeeper.exists/getData` calls, it loads the path local and calls a new `Probe.beforeDoor(site, exceptionClass, resource)` overload. The overload adds raw `resource` to `DOOR_OBSERVED`, `FAULT_MATCHED` and `FAULT_APPLIED`; the existing two-argument method delegates with a null resource, preserving other systems' behavior. The site name and door ordinal remain unchanged. The catalog marks these doors with `resource_argument=first_string_parameter`. Restricting by owner, method descriptor and callee keeps the source pin explicit. `ClassWriter.COMPUTE_FRAMES | COMPUTE_MAXS` recomputes stack frames after the extra `ALOAD`.

The raw path must remain attached to the same event as the typed exception site and named physical actor. `verify_resource_binding.py` is a pure-Python **post-trial feedback gate** for the SOLR-15 native `exists` candidate. It requires one typed `ConnectionLossException` plan on a named physical actor with an explicit split occurrence and door ordinal, an untruncated trace, the ordered line-164 and line-523 caller doors in that same actor/occurrence/thread, native attempts on one exact `/live_nodes/<node>` path on both sides of that handoff, and a matching `FAULT_APPLIED` event for the chosen native door. It rejects an alternate znode, a different split occurrence or actor, a missing caller handoff, an unapplied fault, and trace truncation. The script compares an optional `point.resource` with the observation, but the current Java `FaultPlan` ignores that field; this comparison is only a feedback check. `test_verify_resource_binding.py` exercises the gate with synthetic events and no JVM.

A future runtime test should assert that both `@301` and `@349` catalog rows exist; the observed event has the actual `resource` string; a fault at a different path does not acquire the expected resource identity; and a `ConnectionLossException` at the native retry attempt is still caught by `ZkCmdExecutor.retryOperation`. The bytecode test must exercise both lambdas, verify the original return values without a fault, and check the transformed class loads with valid frames. No such JVM test has run during the live node campaigns.

## Full-campaign boundary

This patch **records** paths; it does not make fault plans path-qualified. `FaultPlan.Point` still matches site, node, epoch, occurrence, hit and door ordinal. The offline feedback gate can reject a completed trial, but it cannot ensure that a proposed plan will fault the correct path before execution. A future full release must propagate `resource` into feedback and add a resource-aware fault selector or equivalent proof that the native event belongs to the line-523 second parent-leader lookup in the same split actor. Because Jetty ports change between trials, blindly copying the raw healthy path into a later plan is not a stable replay strategy. Match the `/live_nodes` family and bind the parent identity from the same split occurrence, or use an explicit source-call handoff; then require the exact line-536 check and line-538 throw after the effective fault. Until that is verified, healthy path observation can guide design but cannot authorize a full SOLR-15 causal-graph campaign.
