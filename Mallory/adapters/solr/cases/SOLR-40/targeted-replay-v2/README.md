# SOLR-40 exact alias watch replay

This case-local run uses the unchanged Solr 8.11.4
`TimeRoutedAliasUpdateProcessorTest#test` and the previously built SOLR-40
watcher agent. `sites.json` configures one fault door: the
`AliasesManager.process` call to `SolrZkClient.getData` at source line 2312,
throwing `KeeperException.ConnectionLossException` before that method call.
The current Mallory core supplies graph and node timeline guidance. The run
does not edit or rebuild shared Solr source, Mallory core, or the adapter JAR.

Run output:
`data/mallory/solr40_targeted_replay_v2_node0/SOLR-40/`. The campaign
ended `queue_exhausted` after a passing healthy JUnit and nine fault trials.
All nine faults applied at their selected exact site, physical node, and
ordinal. Seven trials reached the target after the fault, but only two had a
later target check on the faulted physical node: r0008 (node2, five checks)
and r0009 (node1, eight checks). Neither emitted the SOLR-40 target
exception. r0008 failed at a different 400 error, `Could not find collection :
myalias__TRA__2017-10-25`; r0009 passed. The other seven trials had either
no later target or later targets on other nodes. See
`targeted-replay-audit.json` for each fault receipt, target node, JUnit
outcome, and SHA-256 of the raw trace, JUnit log, and result.

This bounded run did not reproduce the earlier transient alias cache miss.
The method entry fault represents a final visible `getData` exception and
does not exercise a complete ZooKeeper disconnect/reconnect. Physical node
identity is recorded, but this agent does not record a shared concrete
`SolrZkClient` identity at fault and target. A same-node target therefore
does not alone establish same-reader causation.

The earlier `targeted-replay-v1` calibration used automatic I/O doors and
included unrelated HTTP operations. Its eight fault results are preserved
separately and are not counted in this exact-door denominator.
