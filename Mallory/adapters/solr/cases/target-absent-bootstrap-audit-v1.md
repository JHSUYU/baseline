### SOLR-15 alternate cluster workload

`org.apache.solr.cloud.api.collections.ShardSplitTest#testSplitWithChaosMonkey` is an unchanged `@Test @Nightly` method in `ShardSplitTest.java` (SHA-256 `877be1fdba4d626214d647a8ca6b25957b0a87cc381821a125fff71dfe0dc352`) extending `BasicDistributedZkTest`. Its source lines 449–460 stop the parent leader Jetty during the split once a child shard has more than one replica; lines 491–506 restart it after the split request returns. Its oracle explicitly tolerates a failed split and checks document/shard consistency afterward. This supplies a real leader-loss interval absent from `SplitShardTest#doTest`.

The prior native-probe `native-chaos-02` and `native-chaos-03` healthy runs each passed one JUnit in 61.497 and 76.613 seconds. Their stable source/actor selector was `SplitShardCmd.split` line 523 → `SolrZkClient.lambda$exists$2` native `keeper.exists`, resource `/live_nodes/NODE`, source key `SOLR/SPLIT/collection1/shard1/PARENT_LEADER`, hit ordinal 1; the physical Jetty port varied as expected. A one-fault run passed and revisited outer line 524 without the selected inner check. Two ordered retry-internal `ConnectionLossException` faults at that same read then produced a non-null first stat, null second stat, exact line-536/538 target reach, and a passing original JUnit; replay reproduced it. The old no-fault seeds did not reach the selected inner check.

**Recommendation:** stage a *separate, isolated* SOLR-15 workload variant using this exact selector and source hash, with a retry-internal `SolrZkClient.lambda$exists$2` typed door and a fresh Mallory healthy gate. Keep the present `SplitShardTest#doTest` package and its calibration claim distinct. Merely changing `cluster_test` in the current config cannot switch workloads: pinned `solr_junit_runner_v14.py:selected_test` resolves SOLR-15 through the v20 inventory, which still selects `SplitShardTest#doTest`; its Java command also enables `-Dtests.nightly=true` only when `MALLORY_SOLR_NIGHTLY=1`. An isolated runner/inventory overlay and new SHA manifest must pin the alternate selector and nightly setting without changing global case selection. The alternate JVM workload remains unverified under Mallory's v38 adapter and target-absent core, so this is a static staging recommendation, not current healthy/full admission.

## Admission decision

**No-JVM static preflight: GO.** All six scoped preflights passed. They verify package hashes, the frozen core, source lines, compiled target classes, configured typed I/O site catalog, and exact check/throw pins.

**Fresh healthy JVM: NO-GO while the node0/node1/node2 campaigns are live.** When the node is available, dispatch can issue a case-and-mode-specific GO receipt for one unchanged JUnit. Admission to full requires one passing test with no failures/errors, valid target class and site-catalog attestation, a configured `DOOR_OBSERVED` event with named replayable actor, and the expected target-absent feedback. The archived healthy runs do not satisfy this gate. For SOLR-34, confirm the retry-internal `@349:door:1` catalog entry and the actual coordinator/client actor; for SOLR-15/16, confirm the `@523:door:3` second `exists` call and owning split actor. If the runtime catalog or actor differs, repin before full.

**Full JVM: NO-GO now.** The runner requires a matching dispatch GO receipt and a fresh admitted healthy result. The planned bound is 80 fault trials or 3600 trial seconds, at most three typed exception faults per trial. Treat exact check/throw reach, target retention, graph path quality, JUnit behavior, and bug status as measured outcomes. A typed injected exception, an unrelated `SolrException`, or a failing JUnit alone is not a selected-check result.
