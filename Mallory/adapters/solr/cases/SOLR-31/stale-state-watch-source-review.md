# SOLR-31: source-admitted watcher fault diagnostic

This review selects SOLR-31 from the older SOLR-05/19/31/36 campaigns for one bounded diagnostic. It does not classify the terminal SOLR-31 campaign as a bug or as a proven fault-to-target path.

`ForceLeaderTest#testReplicasInLowerTerms` stops the original leader at lines 203–207, waits for all replicas to become DOWN, explicitly refreshes **the client's** `ZkStateReader` at line 101, and checks that the client sees no leader at line 118. `doForceLeader` then sends a separate FORCELEADER request. The server handler takes **its own** `ClusterState` snapshot at `CollectionsHandler.java:1462`, then tests `slice.getLeader() != null && leader.getState() == ACTIVE` at line 1476. The client's refresh does not refresh that server snapshot.

The server's `ZkStateReader.StateWatcher.refreshAndWatch` calls `fetchCollectionState` and then `updateWatchedCollection`/`constructState` at lines 1384–1387. `fetchCollectionState` reads `/collections/<collection>/state.json` through `SolrZkClient.getData` at line 1641. A `KeeperException.ConnectionLossException` at that read is caught at line 1390; the state update is skipped, leaving the prior server cache in place. Thus, if this watcher fault occurs as the leader becomes DOWN, the handler can read a stale ACTIVE leader and take the selected guard. This is a source-supported possible state effect, conditional on the relevant watcher event, the cache contents, and the handler landing on the same server.

The old v18b full run completed 36 fault trials: 33 strict applied and 2 target-retained. The SHA-bound posthoc review found zero numeric-thread same-occurrence paths; its two retained faults were `ZkController#register@1376:door:2` on `shard-2` and a client HTTP door. Neither proves this watcher mechanism. The v19a one-fault watcher pilot did not apply its planned fault: the healthy watcher was on `shard-1` but the replay target ran on `shard-3`. The old healthy trace did not instrument `ZkStateReader.StateWatcher` or `fetchCollectionState`, so it cannot determine the relevant path or door ordinal. These are negative/limited old-budget results, not repeatable new evidence.

Bounded follow-up, with the existing JUnit workload and no full campaign:

1. Pin a separate Solr adapter and site file. Scope `StateWatcher.refreshAndWatch` to the uniquely registered `ZkStateReader` server node/epoch, record its collection and occurrence, and expose a typed `ConnectionLossException` door only at its `fetchCollectionState` `getData` call for `forceleader_lower_terms_collection/state.json`. Record the server cache collection version and leader name/state before and after the callback. At the selected `forceLeaderElection@1476` check, record the handler's physical node/epoch, collection, shard, numeric thread, method occurrence, snapshot version and actual leader operand. Fail closed on unknown/shared reader ownership or an unqualified ZK path.
2. Run one fresh healthy `ForceLeaderTest#testReplicasInLowerTerms` in an isolated node2 lane after source, compiled-class, adapter, agent, core, site, output, and host gates. It must pass JUnit, reach the exact named check, observe the qualified watcher read on the same physical node/epoch/collection, and yield unambiguous cache/operand records. Watcher and handler are on different threads; their ordering is **state evidence**, not a Mallory graph edge. Do not add a shared-field read-from edge to the graph.
3. Only if the healthy gate passes, run at most 4–6 max-one-fault trials at low, observed ordinals. For each trial require the exact typed door `DOOR_OBSERVED` → `FAULT_MATCHED` → `FAULT_APPLIED` on one server node/epoch, path and watcher occurrence. Then require a later exact `@1476` check on the same physical server/collection, with the recorded cache version and leader operand. Compare the injected trial to a fresh fault-free read of the ZK state version; a stale ACTIVE operand despite ZK reporting DOWN is the proposed effect. Report target exception and JUnit separately. A target check on another server or an unmatched fault is not a causal success.
4. Reuse old raw traces for the 36-trial budget, baseline target/site attestation and exclusion of ineffective old doors. They cannot be counted as new numeric-thread or watcher-state trials. Stop after the small diagnostic if the exact watcher-path/operand relation cannot be observed; retain `causal_precision_unverified` and write a source/evidence gap. No 80-trial campaign is authorized by this review.
