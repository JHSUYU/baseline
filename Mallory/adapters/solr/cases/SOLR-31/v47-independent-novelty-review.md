# SOLR-31 v47: independent source and issue review

**Assessment (2026-10-09): credible fault-induced stale-reader failure in Solr 8.11.4; novelty unverified.** The selected `SolrException` is the intended response to an *actually* ACTIVE leader. In the reproduced execution, the serving reader's ACTIVE leader is stale while the test's independently refreshed client reader has no leader. This distinction makes the failed `FORCELEADER` operation a correctness candidate, but neither the selected throw nor the failed JUnit test alone establishes a new bug.

**Fault-model boundary.** The v46/v47 adapter's `beforeQualifiedStateRead` hook invokes `Probe.beforeDoor` immediately **before** the `SolrZkClient.getData` invocation (`SolrHooks.java:165-175`, `SolrTransformer.java:267-282`). The thrown exception therefore bypasses `SolrZkClient`'s internal retry loop. It models a ConnectionLoss already propagated to the caller after unsuccessful retries, or a stronger read failure, **not one transient failed ZooKeeper attempt**. A real disconnection may also trigger a separate reconnect refresh, which this call-site injection does not simulate. This limits claims about frequency and production reproduction. It does not contradict the source-level possibility of a propagated ConnectionLoss: `ZkCmdExecutor.retryOperation` explicitly throws after retry exhaustion.

## Official issue comparison and conclusion

Apache's [FORCELEADER guide](https://github.com/apache/solr/blob/main/solr/solr-ref-guide/modules/deployment-guide/pages/shard-management.adoc) describes the command for a shard that has lost its leader and shows a successful response. The handler's defensive exception is thus expected *for its cached operand*, while failure of this test's leaderless request is not its expected outcome.

A bounded search of Apache Solr Jira and GitHub found related, distinct mechanisms: [SOLR-6405](https://issues.apache.org/jira/browse/SOLR-6405) concerns insufficient retries on ConnectionLoss; [SOLR-16257](https://issues.apache.org/jira/browse/SOLR-16257) concerns inconsistent collection-watch maps and stale state; [SOLR-11535](https://issues.apache.org/jira/browse/SOLR-11535) concerns duplicate StateWatcher registration; [SOLR-6591](https://issues.apache.org/jira/browse/SOLR-6591) concerns stale watched state after watch removal. The previously reviewed [SOLR-9181](https://issues.apache.org/jira/browse/SOLR-9181) is another watch-install race. None of these descriptions establishes the exact caught watcher read failure followed by the FORCELEADER ACTIVE-leader rejection. A bounded search cannot rule out an existing issue or a fix under another description.

**Decision:** retain `candidate_fault_induced_failure_novelty_unverified`. It is neither merely an expected exception nor a confirmed new bug. An upstream novelty claim would require checking applicable later Solr revisions/issues and reproducing the propagated-read-failure condition without bypassing the normal retry/reconnect behavior. No further JVM run or report-table change was made for this review.
