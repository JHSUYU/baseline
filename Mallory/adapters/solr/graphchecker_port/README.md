# Solr causal transport adaptation

This patch is for the Solr 8.11.4 source commit pinned by `Mallory/cases/inventory.json`: `e27f44e3d78dfcec230c97e0a1240e3751daeff9`. It changes protocol and embedded cluster boundaries only. The workload remains the selected original JUnit method.

The source changes derive from the GraphChecker Solr tree's transport design, but call Mallory's own `edu.uva.liftlab.mallory.graphchecker.runtime.MessageDoors` in `Mallory/graphchecker-runtime`. Build that Maven module first. Put its thin jar on Solr's **compile** classpath and the shaded `-all.jar` on the **trial JVM** classpath. The Ant source build accepts `-Dmallory.graphchecker.jar=<absolute-jar-path>`; the direct JUnit runner must put the rebuilt Solr `core`, `solrj`, and `test-framework` classes before distribution jars. Compiling only the selected JUnit against unmodified distribution jars does **not** exercise these hooks.

```sh
cd Mallory/graphchecker-runtime && mvn -q -DskipTests package
cd ../adapters/solr/graphchecker_port
./apply.sh /path/to/clean/solr-8.11.4 --check
./apply.sh /path/to/clean/solr-8.11.4
```

From the patched checkout's `solr/core` directory, compile the source and original tests with `ant -Dmallory.graphchecker.jar=<thin-jar> compile-test` (or invoke Ant Main with the checkout's Ant, Ivy, and JDK 8 tools jars). Compile `GraphJUnit.java` against the resulting test classpath, then run it with `MALLORY_GC_TRACE=<trial-dir>/trace.jsonl` and `-Dmallory.graph.cluster.automatic=true`. `GraphJUnit` selects the original test method through JUnit; it changes no test code. Copy the shaded runtime jar into each trial directory and place that immutable copy first on the trial classpath. Include `-Dtests.src.home=<patched-checkout>/solr/core`, `-Dtests.luceneMatchVersion=8.11.4`, and a writable `-Djava.io.tmpdir` as Solr's test runner does.

Set `-Dmallory.graph.cluster.automatic=true` for the trial JVM. The patch registers each `MiniSolrCloudCluster` Jetty node and its owner objects, roots Overseer queue turns in the election term, carries the prepared HTTP request context in headers, and receives it in `SolrDispatchFilter`. It joins ZooKeeper writes and reads by exact `path@mzxid`, and treats a watcher callback's first read of a stored version as the notification cause. `ZkDistributedQueue.peekElements` now retains the `mzxid` returned by the **same** `getData` call that yielded the queue bytes. `OverseerTaskQueue.QueueEvent` passes that version to the selected task; its `QUEUE_CONSUMED` joins only the matching versioned read. A missing version remains a graph gap. A queue poll alone is not treated as a selected-task handoff.

**Request and response evidence differ.** `MalloryHttp.prepareRequest` prepares an HTTP REQUEST but does not prove a send. Jetty's `onRequestSuccess` and an Apache HTTP response call `MessageDoors.sent`; an actual `SolrDispatchFilter` receive can confirm the request earlier. The patch emits no HTTP RESPONSE headers and therefore cannot claim a RESPONSE WIRE edge. It does not add a causal edge for a prepared request that was never sent or received. The common runtime must pair a prepared request with the actual inbound correlation ID and make `sent` idempotent if a receive confirmed it first.

The ZooKeeper store table and exchange receipt lookup in this runtime are JVM local. They fit `MiniSolrCloudCluster`, whose nodes run in one JVM. A separate process cluster needs durable/remote store provenance and cross-process receipt identity before these edges can be trusted.

The patch was checked against the clean pinned commit, then applied in an isolated worktree. Its full `compile-test` build passed. An unmodified `DeleteReplicaTest#deleteReplicaAndVerifyDirectoryCleanup` trial passed (`run=1 failures=0`, 14.2 seconds) with an immutable shaded runtime snapshot. Its trace had 518 rows; `TrialGraphMain` reconstructed 19 nodes and 25 edges, including three paired HTTP request sends and receives. Compressed trace and feedback are in `smoke_solr09/`. This smoke run did **not** include a target-region probe: feedback reported `targetReached=false`, so it verifies transport capture, not target closure. It also reported startup source-registration and background-scope gaps. Server-owned `SolrZkClient` instances must **not** be registered as generic clients in their constructor: the later node registration needs to bind them to their actual Solr node. The original JUnit selectors for the two main Solr regression cases are `DeleteReplicaTest#deleteReplicaAndVerifyDirectoryCleanup` (SOLR-09) and `TimeRoutedAliasUpdateProcessorTest#test` (SOLR-10/SOLR-40).

## Original JUnit target wiring pilot

The Solr patch also carries the exact selected Overseer queue-item scope through `OverseerTaskProcessor.Runner`'s executor handoff. Without this handoff, the selected `DeleteReplicaCmd.deleteCore` region executes on a worker thread with no source or request context, even though the queue WRITE/READ is visible.

For SOLR-09, a **target-only wiring pilot** used the generic Soot weaver on `DeleteReplicaCmd.deleteCore`: line 277's branch is target site `#u105`, and line 278's throw is `#u118`. The original, unchanged `DeleteReplicaTest#deleteReplicaAndVerifyDirectoryCleanup` passed (`run=1 failures=0 ignored=0`, 13.9 seconds). The trace has 510 rows including one attributed `TARGET_CHECK` with outcome `TRUE`, one branch coverage row, and no `TARGET_THROW`. Graph feedback reports `targetReached=true`, 24 nodes, 42 edges, and a target backward closure of five nodes and four edges: original JUnit client → HTTP receive node → exact ZooKeeper queue write/read → Overseer task → target region. The four edge kinds are WIRE, STATE, HANDOFF, and SCOPE; there is no queue mismatch gap. See `pilot_solr09_weave_manifest.json`, `pilot_solr09_trace.jsonl.gz`, `pilot_solr09_graph.jsonl.gz`, `pilot_solr09_feedback.json`, and `pilot_solr09_result.txt`. The weave selected only this target method and no fault doors, so this pilot is **not** a full static-scope fuzz campaign.

The exact `/overseer/collection-queue-work/...` WRITE and READ, `QUEUE_CONSUMED`, and carried task scope appear in the pilot trace. The runtime builds HANDOFF only from a unique prior queue READ with matching location/version and writer identity. The pilot used immutable runtime jar SHA-256 `286c34d93ab0dea47d918f6bb85ded9bdcd3bd5a24125e878f5180376789a5b4` and generic weaver jar SHA-256 `7a96c0fde65c162680d9762e9b57658bd37db56e2a8469d0e0f2e95dcc7bae00`.

For SOLR-40, the inventoried original `TimeRoutedAliasUpdateProcessorTest#test` is annotated through its base class with `@AwaitsFix(SOLR-13696)`, so the ordinary JUnit run is skipped. With standard `-Dtests.awaitsfix=true`, the unchanged test starts but fails **before** alias creation at `ConfigSetAdminRequest.Create`: `Can't create a configset with an unauthenticated request from a trusted baseConfigSet`. `getAliasProps` is never reached. See `solr40_original_test_failure.txt`. Source search found document ADD through a routed alias only in the `TimeRoutedAliasUpdateProcessorTest`, `CategoryRoutedAliasUpdateProcessorTest`, and `DimensionalRoutedAliasUpdateProcessorTest` families. All inherit the same `RoutedAliasUpdateProcessorTest.createConfigSet` setup and `@AwaitsFix` class annotation. `CreateRoutedAliasTest` and `ConcurrentCreateRoutedAliasTest` create routed aliases but do not ADD through them. Thus no verified, unchanged eligible cluster JUnit for this target is available under the current test configuration; a skipped or pre-target failure is not a healthy seed.

For a woven Solr trial, put the immutable shaded runtime jar **and** the immutable generic weaver jar before the rebuilt Solr classes on the JVM classpath. The woven classes call `edu.uva.liftlab.mallory.graphchecker.weave.TraceHooks`; omitting the weaver jar makes the original test fail with `NoClassDefFoundError` and can leave the embedded cluster retrying. Use `-ea` because Solr's RandomizedRunner expects assertions enabled, and use a fresh temporary directory per trial.

## V8 full-scope healthy gate and campaign

The final patch and runtime were used for a fresh full static scope and weave on node2. The generated manifest has 22,586 regions, 38,560 coverage sites, 709 typed fault doors, and the target branch/throw pair. The unchanged `DeleteReplicaTest#deleteReplicaAndVerifyDirectoryCleanup` JUnit passed in 36.846 seconds. It reached the healthy target check once with outcome `TRUE` and never threw at that site. Its graph has 13,625 nodes and 27,249 edges. The target backward closure has 3,510 nodes, 6,988 edges, 837 coverage sites, and 15 observed fault-door site IDs. The closure includes exact HTTP WIRE, ZooKeeper STATE, and selected Overseer queue HANDOFF edges; there is no queue identity gap. The pinned inputs, hashes, and counts are in `full_scope_solr09_v8_healthy.json`.

The healthy trace has 17 **global** `SOURCE_REGION_MISMATCH` gaps from other `SolrZkClient` reads/writes whose explicit client owner differs from the active woven region. These remain analysis limitations. They do not substitute for the selected queue read receipt or remove the exact WIRE→STATE→HANDOFF chain on this target path. The native generic scheduler is running a durable 64-trial, 1,800 cumulative JUnit second, maximum-four-fault campaign under the evidence root recorded in the v8 summary. A target throw is only a candidate when its own causal ancestry contains the last exact applied fault; a trial that destroys the target is discarded. The healthy gate alone does not mark the check complete.

## Inventory-driven preparation for another Solr check

`prepare_case.py` reads a Solr row from `Mallory/cases/inventory.json`. It verifies the pinned source commit, protocol patch, unchanged target source, and unchanged JUnit source; checks that both selected classes are compiled; extracts the branch and throw lines from the inventory; and preserves the exact ordered static/runtime classpath. The generic Soot planner selects regions, coverage sites, and typed fault doors. The script contains no per-check I/O list. A healthy seed still has to pass the original JUnit and reach its target before the generic campaign can count fault trials.

On a host with the pinned patched Solr build, use the validated SOLR-09 `scope-input.json` and `native-config.json` directory as the toolchain template. The template supplies jars and classpath order, not the next case's scope or fault points:

```sh
python3 prepare_case.py scope --case-id SOLR-01 \
  --source /path/to/pinned-patched-solr \
  --template /path/to/solr09-full-scope-v8 \
  --out /path/to/solr01-scope \
  --planner-jar /path/to/pinned-static-scope.jar \
  --planner-deps /path/to/static-scope-cp.txt
/path/to/solr01-scope/run_scope.sh
python3 prepare_case.py campaign --case-id SOLR-01 \
  --source /path/to/pinned-patched-solr \
  --template /path/to/solr09-full-scope-v8 \
  --out /path/to/solr01-scope \
  --project /durable/solr01-project \
  --core-pythonpath /path/to/pinned-mallory-core-root
/durable/solr01-project/run_campaign.sh
```

The two phases refuse changed pinned inputs. `scope` bounds the planner to 900 seconds and 6 GiB heap; `campaign` defaults to 64 fault trials, 1,800 cumulative JUnit seconds, and four faults per sequence, with a durable checkpoint. SOLR-09 preparation was dry-run against the full v8 build and reproduced its static input exactly; the campaign preparation read all 709 generated doors. SOLR-01, whose original test is in `solrj`, also passed the source/classpath preparation gate without a hand-selected door. Neither dry-run executed a new JUnit. The inventoried SOLR-40 test remains ineligible as a healthy workload under the current setup because its unchanged test is skipped or fails before the target, as documented above.
