Both checks run **in the constructor**, before the procedure is submitted (`ModifyTableProcedure.java:93-102,119-140`). The existing `TestModifyTableProcedure#testModifyWillNotReopenRegions` reaches each check but deliberately submits a changed family count and a changed coprocessor and catches the corresponding exception (`TestModifyTableProcedure.java:637-648,673-684`). Its selected throws are expected test behavior and cannot serve as bug observations.

The cleaner existing MiniCluster selector is `TestModifyTableProcedure#testModifyTableWithCoprocessorAndColumnFamilyPropertyChange`. It reads the old descriptor with `UTIL.getAdmin().getDescriptor(tableName)` at line 737, changes only a column-family compression property, and directly constructs `ModifyTableProcedure(..., htd, false, reopenRegions=false)` at lines 738-747. Both selected checks execute without throwing in the recorded healthy calibration. The `getDescriptor` call is a **source-level candidate for a target-retaining fault**: `HBaseAdmin.getTableDescriptor` sends `GetTableDescriptors` (`HBaseAdmin.java:614-630`), and `executeCallable` uses `RpcRetryingCaller.callWithRetries` (`HBaseAdmin.java:3174-3182`). The retry loop catches retryable failures and may return a descriptor on a later attempt (`RpcRetryingCallerImpl.java:93-143`). A single checked `IOException` at the server-side `RpcServer.call` dispatch for that exact read (`RpcServer.java:435-447`) could therefore be followed by the retry and the constructor check. This is a conditional source inference, not an observed injected result. A generic I/O fault during earlier table setup or after the constructor is not a qualified predecessor.

**Current admission: source candidate only; do not dispatch a full campaign.** The prior fault-free calibration of this selector records one JUnit test, the selected checks, no selected throw, and 46 eligible doors, but **zero observed-path doors and zero closure edges into either check** (`data/mallory/calibration_v8/HBASE-19/offline-causal-audit.json` and the corresponding HBASE-20 audit). The direct JUnit-thread constructor has no received `ModifyTable` RPC. Thus the existing generic graph cannot prove that a `GetTableDescriptors` retry and the later selected constructor refer to the same descriptor. It would be unsound to promote any of the 46 generic doors solely because they happened earlier in time.

To qualify the current selector, instrument and verify this exact event-time chain in a healthy run and one bounded injected run:

1. On the test client thread, record `GetTableDescriptors(tableName=T)` with a unique request token and a method-specific response token. Match each request to a named master receiver and the corresponding response; do not use an unscoped master RPC door.
2. Inject one `IOException` at the first `GetTableDescriptors` service dispatch for `T`. Verify exact actor, site, request token, and applied-fault event. Verify a later retry for the **same logical table read** succeeds and returns descriptor `D`; this requires a new transport token for the retry and the same client call scope.
3. At the selected constructor call, record the original descriptor `D`, modified descriptor `D'`, `reopenRegions=false`, table `T`, and the procedure-instance identity. The source-level use of the returned descriptor at test lines 737-746 is the bridge from response to constructor. Match the subsequent `@133` and `@138` checks to that procedure instance. Do not equate an unrelated master RPC or a later procedure with this target.
4. Require the selected check to occur after the applied fault and successful retry in the same test invocation. For HBASE-19, verify equal family counts in the healthy seed; for HBASE-20, verify equal coprocessor descriptors. A selected throw must be absent in the healthy seed and separately source-reviewed after any faulted run.

For a true client-to-master `ModifyTable` path, the existing client API can send `reopenRegions=false`: `HBaseAdmin.modifyTableAsync` builds the request with that value (`HBaseAdmin.java:393-409`), `MasterRpcServices.modifyTable` forwards it (`MasterRpcServices.java:1482-1490`), and `HMaster.modifyTable` constructs the procedure (`HMaster.java:2828-2849`). The pinned tests inspected in the earlier source search contain no active `Admin.modifyTable(..., false)` call. The nearby `TestTableDescriptorModificationFromClient#testModifyTable` uses the deprecated two-argument overload, which forwards `true` (`Admin.java:1533-1538`) and cannot reach these inner guards. A new MiniCluster test would be needed for that stronger RPC path; it has not been written or run.
