For HBASE-33/34, the source path is `ZKSecretWatcher` reading key znodes via
`ZKUtil`, then `AuthenticationTokenSecretManager.addKey` writing `allKeys`;
the selected predicate reads `allKeys`. Existing HBase RPC request/response
hooks do not prove that relation. Successful key publication and consumption
need a common znode/version and an exact `allKeys` element version. Equal key
IDs or trace order alone do not establish a read-from edge.

HBASE-34 also crosses a distinct transport phase. In the Netty server,
`NettyHBaseSaslRpcServerHandler.channelRead0` invokes
`HBaseSaslRpcServer.evaluateResponse`, whose DIGEST callback invokes
`AuthenticationTokenSecretManager.retrievePassword`. The handler installs the
ordinary RPC request decoder only **after** SASL completes. The present HBase
RPC hook propagates context in `RequestHeader.attribute` and therefore cannot
attribute the target's SASL invocation to that later header. The isolated
adapter now has a general Netty SASL response-frame envelope that preserves
the mechanism's original token bytes and confirms the transport boundary.
Its source patch, focused frame round-trip, and unchanged original
`testOnlyToken` protocol pilot passed. The pilot reconstructed eight exact
client/server `hbase-sasl.REQUEST` WIRE pairs from confirmed EXPORT and server
ATTACH rows. This pilot did not weave or observe the HBASE-34 target check;
direct ZooKeeper and `allKeys` versions remain a separate quality gate before
any case result or fault campaign.

The current campaign driver requires an observed healthy `TARGET_CHECK` before
fault trials. A missing healthy target therefore blocks the present run; it
does not prove the original JUnit cannot exercise the target under faults. A
future general target-absent bootstrap can seed from upstream I/O observed in
that same unmodified JUnit and use target reach as feedback. It must preserve
the exact inventory target, let Soot select eligible upstream doors, and keep
target-absent trials distinct from completed target-reaching campaigns.
