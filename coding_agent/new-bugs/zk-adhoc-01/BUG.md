# zk-adhoc-01: restoreFromSnapshot leaves the old session tracker's expiry thread running (and the new one unstarted), so about one session timeout after an admin restore every pre-existing live session is force-expired: in-flight writes get SESSIONEXPIRED and its ephemerals are deleted.

Severity (reviewer): **operation-failure**

## The ad hoc check (the prompt's only target)

- `zookeeper-server/src/main/java/org/apache/zookeeper/server/SessionTrackerImpl.java:317`, `SessionTrackerImpl.checkSession(long, Object)`, throws `org.apache.zookeeper.KeeperException.SessionExpiredException` when `session.isClosing()   (session = sessionsById.get(sessionId), non-null)`
- Starting test: `org.apache.zookeeper.server.quorum.QuorumPeerMainTest#testQuorum`

## Verified defect (independent reviewer, `../../data/REVIEW-RUBRIC.md`)

**Verdict:** BUG

**Trigger:** 3-node ensemble, client with a live global session on a follower keeps writing; operator runs the documented 'restore' admin operation (ZooKeeperServer.restoreFromSnapshot, the exact call Commands.RestoreCommand makes) on the live leader with a snapshot containing that session. The test's tracker subclass only observes and rethrows.

**Why (root cause in the source):** ZooKeeperServer.restoreFromSnapshot (ZooKeeperServer.java:611-635) calls createSessionTracker() (line 630) without shutting down the old tracker or starting the new one. The old SessionTrackerImpl thread (SessionTrackerImpl.java:154-168) keeps expiring sessions from an expiry queue that no longer gets touches, because all touches now go to the new tracker. It calls expirer.expire -> ZooKeeperServer.close (ZooKeeperServer.java:702-735), which submits closeSession. PrepRequestProcessor then marks the live session closing in the new tracker, so the client's next requests fail checkSession at SessionTrackerImpl.java:316-317 while the client is CONNECTED and pinging. A session that is being renewed should never be closing. Restore is enabled by default, documented, and used on live quorum members (RestoreQuorumTest), so the trigger is realistic.

## The agent's explanation (its `result.json`)

**Why it is a bug (agent):** The coordination behind the check is the session liveness protocol: a session is 'closing' only after the client closed it or after the server that owns session expiry (the leader) observed that no touch arrived within the session timeout. Here neither happened. ZooKeeperServer#restoreFromSnapshot (the 'restore' admin command) replaces the session tracker without shutting the old one down and without starting the new one: the pre-restore SessionTrackerImpl thread keeps expiring sessions from an expiry queue that no longer receives any touch, while all touches (pings relayed by the follower) go to the new tracker. So a session that is alive - the client is CONNECTED, its pings are answered, and the restore deliberately preserved it (the new tracker is built from the restored snapshot's session map, and ZookeeperServerRestoreTest asserts a pre-restore client's session is still tracked after a restore) - is force-expired by an orphaned thread, marked closing in the live tracker by the prep of that bogus closeSession, and then rejected by the ad hoc check. The check therefore rejects state that correct coordination could not produce: there is no interleaving of client closes and genuine timeouts in which a session that is being touched every ping interval is closing. Consequence in a real deployment: after an operator runs the 'restore' admin command on a running server (the documented recovery path, e.g. RestoreQuorumTest restores onto live quorum members), every session that existed before the restore is force-closed about one session timeout later even though its client is healthy: in-flight writes forwarded from followers fail with SESSIONEXPIRED while the connection still reports CONNECTED, all ephemeral nodes of those sessions (locks, leader-election and membership znodes) are deleted, and the clients see a spurious session expiry. The same defect also leaves the new tracker unstarted, so sessions created after a restore are never expired at all, and leaks the old tracker's thread.

**Execution (agent):** Nodes: a 3 node ensemble (servers 0,1,2; tickTime=1000, minSessionTimeout=4000, global sessions), one client. Steps: (1) The ensemble starts and elects a leader L; the other two are followers. (2) The client connects to a follower F with sessionTimeout=4000 and gets global session S; the createSession txn is committed, so L tracks S in its LeaderSessionTracker (tracker #0) and S is in L's committed session map. The client creates a persistent znode /restore-live-session, i.e. its writes are forwarded by F to L and prepped there (at the leader a forwarded request has cnxn==null, so ZooKeeperServer.submitRequestNow()'s touch() is a no-op and the request always reaches PrepRequestProcessor). (3) Fault / admin operation: an operator restores a snapshot on the live leader L - exactly what the 'restore' admin command does (Commands.RestoreCommand#runPost -> ZooKeeperServer#restoreFromSnapshot; org.apache.zookeeper.server.admin.RestoreQuorumTest does this over HTTP on live quorum members). The test takes the snapshot from L itself immediately before (leaderZks.takeSnapshot(false,false)) and feeds it back, so the restored state is identical to the current state and the snapshot contains the live session S. (4) restoreFromSnapshot() swaps in a new ZKDatabase and calls createSessionTracker(), which installs a brand new LeaderSessionTracker (tracker #1) that tracks S (the test asserts S is still tracked and the client is still CONNECTED). It neither shuts down tracker #0 nor starts tracker #1. (5) Concurrently the client keeps pinging and keeps writing (async setData on /restore-live-session, ~2000/s, forwarded by F to L). All session touches - the client pings relayed to L in F's PING reply, LearnerHandler -> Leader.touch -> LeaderZooKeeperServer.touch -> sessionTracker.touchSession - now go to tracker #1, whose expiry bucket for S keeps advancing; tracker #0's expiry queue is frozen on the bucket it had at restore time (visible in the test log: 'orphaned tracker expiry queue={1174460000=[S]} restored tracker expiry queue={..., 1174464000=[S]}'). (6) One session timeout (4s) after the restore, the orphaned tracker #0's still running expiry thread polls S: 'Expiring session 0x..., timeout of 4000ms exceeded' -> setSessionClosing on its own copy + ZooKeeperServer.expire(S) -> close(S) submits a closeSession request (cnxn==null) into L's live pipeline. (7) PrepRequestProcessor preps that closeSession and runs zks.sessionTracker.setSessionClosing(S) on tracker #1, i.e. the *current* tracker marks the live session closing. (8) The client's in-flight forwarded setData requests that are queued behind the closeSession in L's prep queue are prepped next: PrepRequestProcessor.pRequest2Txn (case OpCode.setData, line 378) -> LeaderSessionTracker.checkSession -> SessionTrackerImpl.checkSession finds S in sessionsById with isClosing==true and throws KeeperException.SessionExpiredException at SessionTrackerImpl.java:317. The test records the client's connection state at the instant of the throw: CONNECTED. (9) The closeSession txn then commits, S is removed and killed in the data tree, and the client - which never stopped pinging - loses its session (client state CLOSED).

**Stack frame (agent):** at org.apache.zookeeper.server.SessionTrackerImpl.checkSession(SessionTrackerImpl.java:317)
