# Coding-agent baseline on 14 known bugs, at their buggy versions

Same agent and prompt as the 84 checks (`../SETUP.md`): Claude Code 2.1.319, `claude-opus-5-5[1m]`, effort high, one prompt per bug that gives **only the ad hoc check** the bug makes fail and a starting test (no bug, no JIRA). Each tree is the parent of the bug's fix, one commit `base`, no history (`../data/known-SETUP.md`). Time is the agent's active time (usage-limit waits excluded); tokens are input + output + cache writes + cache reads, including subagents; cost is the CLI's list-price estimate.

**Result: 8 detected, 6 not detected.**

Detected = a validated reproduction (the check's exception at the check's line on the unmodified buggy tree) whose root cause is the bug's defect (`../data/CRITERIA.md`, written before the runs), judged by an independent source review against the JIRA's fix; `fixed version` is the agent's test re-run with the fix's production changes applied.

## Findings

- **hdfs-adhoc-k1 (HDFS-11741)**: A long-running encrypted balancer (one NameNodeConnector/KeyManager across iterations) keeps using the DataEncryptionKey it cached in iteration 0; after the NN rolls block keys and the DataNodes drop that key, every later replaceBlock SASL handshake fails BlockTokenSecretManager.retrieveDataEncryptionKey (allKeys.get(keyId)==null) and the balancer moves no more bytes.
- **hdfs-adhoc-k2 (HDFS-17383)**: The agent drops (via a Mockito spy that throws after the real sendHeartbeat) every heartbeat response carrying a KeyUpdateCommand to the replication-target DataNode, from both NameNodes, across two key rolls. The NameNode clears needKeyUpdate without an ack, so the target never learns the rolled keys. A later DN-to-DN replication then fails the key==null check in retrievePassword on the target.
- **hdfs-adhoc-k3 (HDFS-12931)**: In an HA cluster with encrypted transfer, the standby NN restarts and the DataNodes take its block key as currentKey; the standby then crashes and a target DN restarts with only the active NN's keys. NN-driven re-replication (DataNode.DataTransfer, DN->DN) then fails at the receiving DN's retrieveDataEncryptionKey check.
- **hdfs-adhoc-k4 (HDFS-5766)**: A long-running Balancer with encrypted data transfer caches one DataEncryptionKey forever in NameNodeConnector; after block keys roll, DataNodes reject it in BlockTokenSecretManager.retrieveDataEncryptionKey and every replaceBlock fails (this is HDFS-11741, not HDFS-5766).
- **hdfs-adhoc-k5 (HDFS-10609)**: In an HA cluster with encrypted transfer, the DataNodes take their currentKey from a restarted standby NN; after the standby crashes, a newly started DN knows only the active NN's keys. During append pipeline recovery the surviving replica holder DN1 transfers the block to the new DN3 using a DN-generated data encryption key built from the standby's key, DN3 rejects it in retrieveDataEncryptionKey, and the append fails with 'Failed to replace a bad datanode'.
- **hdfs-adhoc-k6 (HDFS-14075)**: A rollEditLog whose startLogSegment fails on all (non-required) edits dirs leaves FSEditLog in BETWEEN_LOG_SEGMENTS while the NameNode keeps running; the next rollEditLog fails Preconditions.checkState(isSegmentOpen()) in endCurrentLogSegment with IllegalStateException 'Bad state: BETWEEN_LOG_SEGMENTS'.
- **hdfs-adhoc-k7 (HDFS-14311)**: During a cTime upgrade of a DataNode with two volumes, volume 1's deferred upgrade callable (executor thread) sets the shared BlockPoolSliceStorage layoutVersion/cTime to the new values while the BP actor thread's doTransition for volume 2 is between readProperties and its version check. Volume 2 then takes the regular-startup path and gets VERSION(cTime=T1) with no previous/ snapshot. A later supported -rollback rejects volume 2 at BlockPoolSliceStorage.doTransition:422 ('Datanode state ... is newer than the namespace state') and the block pool fails to initialize.
- **solr-adhoc-k1 (SOLR-9440)**: A SPLITSHARD that fails because the parent-leader node is stopped right after CREATESHARD leaves sub-shard shard1_0 in CONSTRUCTION in state.json for good (SplitShardCmd does no rollback), so waitForRecoveriesToFinish sees a CONSTRUCTION slice on every poll and times out at AbstractDistribZkTestBase.java:185.
- **solr-adhoc-k2 (SOLR-6101)**: Once legacyCloud=false is set through CLUSTERPROP, a plain SPLITSHARD of shard1 fails every time. The Overseer sends the sub-shard leader core-admin CREATE without a coreNodeName, and CoreAdminHandler rejects it ('non legacy mode coreNodeName missing'), so the split aborts with 'SPLITSHARD failed to create subshard leaders'.
- **solr-adhoc-k3 (SOLR-6197)**: With legacyCloud=false set via the CLUSTERPROP API, MIGRATE fails because OverseerCollectionProcessor.migrateKey sends a raw core-admin CREATE for the temp collection's replica2 on the target leader node without coreNodeName, which CoreAdminHandler.handleCreateAction:563 rejects ('non legacy mode coreNodeName missing').
- **hbase-adhoc-k1 (HBASE-15039)**: After a key-master failover, the new leader (rs-B) rolls key 2 and signs a fresh token with it. A follower RPC server (rs-C), whose ZooKeeper tokenauth notifications are delayed, rejects that valid token over real SASL DIGEST-MD5 with InvalidToken 'Unknown master key for token (id=2)'.
- **hbase-adhoc-k2 (HBASE-20642)**: A single Admin.addColumnFamily whose master response is delayed past the client RPC timeout (after ModifyTableProcedure already added the family) is retried by RpcRetryingCaller; the retry hits the 'already exists' check in HMaster.addColumn and the client gets InvalidFamilyOperationException although the family was added by that same call.
- **zk-adhoc-k1 (ZOOKEEPER-710)**: A client's reconnect (session renew) to slow follower F1 is delayed on the network; the client times out, re-establishes the session on F2, and works there. The late ConnectRequest then reaches F1, F1 sends REVALIDATE to the leader, and the leader sets the session owner to F1's LearnerHandler. Every later request from the client over its only live connection (F2) is then rejected with SessionMovedException at SessionTrackerImpl.java:246, and the connection stays open (3/3 setData failures).
- **zk-adhoc-k2 (ZOOKEEPER-2886)**: A delayed REVALIDATE from a slow follower A (for a reconnect the client already abandoned) reaches the leader after the client reconnected to the leader, sets the session owner back to LearnerHandler(A), and the client's next plain setData on its live leader connection fails SessionTrackerImpl.checkSession:310 with SessionMovedException; the leader then closes the connection and the client sees ConnectionLoss.

## Notes

- **Same check, other bug.** Three non-detections reproduced a real failure of the same check through another known defect: hdfs-adhoc-k3 (HDFS-12931) and hdfs-adhoc-k5 (HDFS-10609) found HDFS-17383's root cause (a DataNode's currentKey taken from the standby NameNode, breaking DataNode-to-DataNode transfers), and hdfs-adhoc-k4 (HDFS-5766) found HDFS-11741 (the balancer's never-renewed encryption key). They do not count for their own case. hdfs-adhoc-k2 (HDFS-17383 itself) found a different weakness (lost key-update heartbeat responses, injected by a spy) that the fix does not change. solr-adhoc-k1 found a failed SPLITSHARD leaving a CONSTRUCTION sub-shard, not the stale watched-collection state. zk-adhoc-k2 found ZOOKEEPER-710's owner divergence through setData (connection torn down), not the multi-only path.
- **Fixed version.** For 7 of the 8 detected bugs the agent's test no longer fails the check once the fix's production changes are applied; for ZOOKEEPER-710 (a fix that handles the exception) the check fires once but the connection is closed, so the permanent error is gone. For all 6 non-detections the failure persists on the fixed version.
- **Model memory.** In hdfs-adhoc-k1 and hdfs-adhoc-k4 the agent named HDFS-11741 from memory, and in zk-adhoc-k2 named ZOOKEEPER-2886 as a possibility, each only in its final write-up after the reproduction; no tree, cache or prompt holds a JIRA key or fix hash (ZOOKEEPER-710 appears in a genuine source comment of the zk-adhoc-k2 tree, as in upstream). That the model may know these old bugs from training cannot be ruled out; the runs were fast (median 5.5 min of agent time, longest 17 min, no usage-limit waits).
- **Leakage audit:** no transcript mentions Specula, GraphChecker or Causym; no WebSearch/WebFetch call; no proxy denial during these runs; no agent changed production code.
- **Superseded run:** the first zk-adhoc-k1 run (5 min) was stopped and redone: its tree's history tracked build output of Specula's instrumented build (not published).
