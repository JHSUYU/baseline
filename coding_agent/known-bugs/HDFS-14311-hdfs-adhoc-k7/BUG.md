## Judgement (independent reviewer, `../../data/CRITERIA.md`)

**Detected:** yes

**What the agent found:** During a cTime upgrade of a DataNode with two volumes, volume 1's deferred upgrade callable (executor thread) sets the shared BlockPoolSliceStorage layoutVersion/cTime to the new values while the BP actor thread's doTransition for volume 2 is between readProperties and its version check. Volume 2 then takes the regular-startup path and gets VERSION(cTime=T1) with no previous/ snapshot. A later supported -rollback rejects volume 2 at BlockPoolSliceStorage.doTransition:422 ('Datanode state ... is newer than the namespace state') and the block pool fails to initialize.

**Same root cause as HDFS-14311?** This is the fix's defect. In the buggy DataStorage.loadBlockPoolSliceStorage (DataStorage.java:450-471) each volume's upgrade callables go to executor.submit(c) inside the per-volume loop, while later volumes are still loading through the same bpStorage. The callable runs BlockPoolSliceStorage.doUpgrade (BlockPoolSliceStorage.java:533-537: this.layoutVersion = DATANODE_LAYOUT_VERSION; this.cTime = nsInfo.getCTime()), which races with doTransition's readProperties(sd) (line 389) and its check against this.layoutVersion/this.cTime (lines 405-425) for the next volume. The fix hunk collects the callables in upgradeCallableMap and submits them only after the loop has finished loading every volume, which removes exactly this interleaving.

**Realistic?** Yes. The test uses a MiniDFSCluster, a NameNode -upgrade, a NameNode bounce while the DN starts (the DN's versionRequest fails and is retried), and then an admin -rollback of an un-finalized upgrade. All of these are supported operations. The interleaving comes only from delays: spied NamespaceInfo getters return the real values and just pause the actor thread after volume 2's readProperties, and pause the executor thread before it reads the new cTime. A slow hard-link phase on a big volume can produce this ordering under the real scheduler. The test fabricates no state and makes no direct calls to internal methods.

**On the fixed version** (buggy tree + the fix's production changes, `fix/prod.diff`): **NOT_REPRODUCED**. NOT_REPRODUCED in 2 of 2 runs (rc 0, about 44s each). With the fix the callables are submitted only after volume 2's doTransition. The actor thread's wait therefore times out (30s), and then both volumes are upgraded with previous/ snapshots, so the rollback succeeds and the check no longer fires.

**Reason:** The agent's failing execution comes from the race the fix removes: upgrade callables submitted while other volumes are still loading write the shared layoutVersion/cTime of the one BlockPoolSliceStorage. As a result a later volume is wrongly treated as already upgraded and is later rejected by the doTransition layout/cTime check. The consequence matches the JIRA: a volume is stamped with the new version but has no snapshot, and the DataNode rejects it at the 'is newer than the namespace state' check when rolling back. The JIRA's case is an LV-based variant of the same mechanism, and the agent's is cTime-based. The trigger is realistic, and the fixed version no longer fails.

## The agent's explanation (its `result.json`)

**Why it is a bug (agent):** Upgrade/rollback coordination between NN and DN guarantees that every DN volume that is upgraded to the NN's new cTime keeps a previous/ snapshot, so a later -rollback can go back to the pre-upgrade cTime. Here a volume carries the new cTime without ever being upgraded. The cause is that BlockPoolSliceStorage keeps one per-blockpool layoutVersion/cTime field pair that is shared by all volumes: the deferred parallel upgrade task of one volume (DataStorage executor, dfs.datanode.parallel.volumes.load.threads.num) writes these fields while the actor thread's doTransition for the next volume is between readProperties() and its version check. This is a plain data race that ordinary thread scheduling can produce, especially with many block files to hard-link and a slow/loaded disk. The state the check rejects (cTime newer than the NN's, with no previous dir) is not something a correct upgrade can produce, and the admin did nothing invalid: rollback of an un-finalized upgrade is a supported operation. Consequences: (a) the affected volume skipped the upgrade, so it has no pre-upgrade snapshot, and blocks deleted or modified on it after the upgrade cannot be restored by rollback; (b) on -rollback the DN rejects the volume with this IOException and marks it failed. With the default failed.volumes.tolerated=0 the DN cannot serve the block pool at all after the rollback, and an operator has to fix the VERSION file by hand or wipe the volume (losing its replicas).

**Execution (agent):** Setup as TestAdhocWorkload7: pre-upgrade NN storage, one DN with two volumes data1, data2 holding pre-upgrade block pool storage (LV current, cTime c0). (1) NN is started with -upgrade, generating a new cTime T1. (2) NN process is bounced; while it is down the DN starts, its versionRequest fails (connection refused) and BPServiceActor retries; NN restarts (regular, upgrade still un-finalized, cTime T1) and the DN gets NamespaceInfo(cTime=T1). (3) DataStorage.loadBlockPoolSliceStorage, on the BP actor thread, processes data1: BlockPoolSliceStorage.doTransition sees cTime c0 < T1, renames current->previous.tmp and submits the rest of the upgrade (linkAllBlocks, set this.layoutVersion/this.cTime=T1, write VERSION, rename previous.tmp->previous) as a Callable to the parallel-volume executor. It then goes on to data2 right away, on the same shared BlockPoolSliceStorage object. (4) Interleaving (forced in the test only by delaying threads: a spy on the NamespaceInfo returned by the versionRequest RPC pauses the actor thread right after data2's readProperties, and pauses the executor thread right before it reads the new cTime; no state is fabricated): the actor thread's readProperties(data2) sets the shared fields to (LV, c0). Then the executor thread for data1 sets the shared fields this.layoutVersion=LV, this.cTime=T1 and finishes. Then the actor thread's check for data2 reads the shared fields, sees LV==current && cTime==T1, and takes the 'regular startup' branch. loadStorageDirectory then writes VERSION(cTime=T1) into data2/current/<bpid>. data2 is never upgraded and gets no previous/ snapshot (test output: data1 .../previous exists=true, data2 .../previous exists=false). CTime = c0') at BlockPoolSliceStorage.java:422(-425). The volume is dropped, and with the default dfs.datanode.failed.volumes.tolerated=0 the block pool fails to initialize on the DN.
