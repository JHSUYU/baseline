## Judgement (independent reviewer, `../../data/CRITERIA.md`)

**Detected:** no

**What the agent found:** In an HA cluster with encrypted transfer, the DataNodes take their currentKey from a restarted standby NN; after the standby crashes, a newly started DN knows only the active NN's keys. During append pipeline recovery the surviving replica holder DN1 transfers the block to the new DN3 using a DN-generated data encryption key built from the standby's key, DN3 rejects it in retrieveDataEncryptionKey, and the append fails with 'Failed to replace a bad datanode'.

**Same root cause as HDFS-10609?** No. The failing handshake is DN-to-DN: DataNode$DataTransfer.run (DataNode.java:2375-2387, getDataEncryptionKeyFactoryForBlock -> BlockTokenSecretManager.generateDataEncryptionKey:393 using currentKey) connecting to DN3, and the log stack shows exactly that (DataNode.transferReplicaForPipelineRecovery -> DataTransfer.run:2387). The stale key comes from BlockTokenSecretManager.addKeys:186-192 letting the standby NN's key set overwrite the DN's currentKey. That is the HDFS-17383 defect (hdfs-adhoc-k2), not HDFS-10609. The HDFS-10609 fix changes only the client side: DataStreamer.transfer (buggy DataStreamer.java:1273) gets a RefetchEncryptionKeyPolicy that clears the DFSClient's cached data encryption key and retries when the client-to-source-DN SASL handshake throws InvalidEncryptionKeyException. In the agent's run the client-to-DN1 connection succeeds. The exception happens on a connection the client does not make, with a key the client did not supply, so the fix's hunk is never reached.

**Realistic?** Yes. It uses a MiniDFSCluster in HA, a standby NN restart and then a crash, a new DN joining, a DN shutdown, and an ordinary append, all with valid configuration. There is no reflection and no fabricated key state. But it is a realistic trigger for a different bug.

**On the fixed version** (buggy tree + the fix's production changes, `fix/prod.diff`): **REPRODUCED**. Still REPRODUCED on buggy+fix: the same InvalidEncryptionKeyException at BlockTokenSecretManager:420-422 on DN3, and the append still fails with 'Failed to replace a bad datanode on the existing pipeline'. The consequence is not removed, which fits the fix being client-side only and not touching the DN-to-DN key path.

**Reason:** The agent reproduced a real, realistically triggered failure of the check during pipeline recovery, and the consequence (the client's write is aborted) looks like the JIRA's. Its root cause, though, is a DN-generated key taken from the standby NN being sent DN-to-DN (HDFS-17383), not the client's stale cached data encryption key going without a refetch and retry in DataStreamer.transfer, which is what HDFS-10609 fixes. The fixed version still fails the same way, which confirms this is a different defect, so it does not detect HDFS-10609.

## The agent's explanation (its `result.json`)

**Why it is a bug (agent):** The client and the target DN are both behaving correctly and following protocol: the data encryption key is generated by a healthy DN from a key it got legitimately from a NameNode of the cluster, and the target DN registered correctly with the active NN. The coordination is wrong because a DN's 'current' block key is simply whichever NN's key set arrived last, which can be the standby's. Nothing makes sure a peer DN has that NN's keys, and nothing retries DN-to-DN transfers with another key (only DFSClient refetches a key on InvalidEncryptionKeyException). In a real deployment, while a standby NN is down (crash, maintenance, slow restart), every DN that joins or restarts rejects all encrypted DN-to-DN traffic from DNs whose current key came from the standby: pipeline mirroring, append/pipeline-recovery block transfers and re-replication (DNA_TRANSFER). This lasts until the active NN's next key roll (dfs.block.access.key.update.interval, 600 minutes by default). Writes and appends fail with 'Failed to replace a bad datanode', new or restarted DNs cannot receive replicas, and under-replicated blocks stay under-replicated, so the risk of data loss goes up.

**Execution (agent):** Configuration: HA HDFS (nn0 active, nn1 standby), dfs.encrypt.data.transfer=true, dfs.block.access.token.enable=true, 3 DNs. (1) A client writes /non-encrypted-file with replication 3 (DN0-DN2). (2) The standby nn1 restarts. In HA each NN generates its own block-key set (own serial range), and on re-registration every DN calls addKeys() with nn1's keys, which sets the DN's BlockTokenSecretManager.currentKey to nn1's key (a DN also takes standby keys from DNA_ACCESSKEYUPDATE). The test waits until every DN's current key is nn1's. (3) The standby nn1 crashes (shutdownNameNode(1)). (4) A new DataNode DN3 starts (the same happens with a restarted DN). It can only register with the active nn0, so its allKeys holds only nn0's keys. (5) DN0, which holds a replica, dies, and the client appends to the file. Pipeline recovery asks nn0 for a replacement DN, gets DN3, and tells a surviving replica holder (DN1) to TRANSFER_BLOCK to DN3. DataNode.DataTransfer builds the SASL encryption key with getDataEncryptionKeyFactoryForBlock -> generateDataEncryptionKey(), which uses DN1's currentKey, the key id of the crashed standby nn1. (6) DN3's SaslDataTransferServer calls retrieveDataEncryptionKey(keyId=<nn1 key>), allKeys.get() returns null, and InvalidEncryptionKeyException is thrown at BlockTokenSecretManager:420. The same failure happens on the normal write path when DN1 opens its mirror connection to DN3 in writeBlock. The client's append then fails with 'Failed to replace a bad datanode on the existing pipeline due to no more good datanodes being available to try'.

**Stack frame (agent):** at org.apache.hadoop.hdfs.security.token.block.BlockTokenSecretManager.retrieveDataEncryptionKey(BlockTokenSecretManager.java:422)  [the 'throw new InvalidEncryptionKeyException(' statement of the key == null check starts at line 420 and spans 420-422; javac attributes the throw to the last line of the multi-line message expression]
